## 0. 한 줄 요약

디바이스 자동 측정이 불가능한 웨이트 트레이닝을 **사진 기계 검증 + 팀원 상호 확인의 2계층**으로 검증하고,
예치금·상금을 **append-only 원장과 멱등 키**로 정합성 있게 정산하는 챌린지 플랫폼.

- 개발: 1인 풀사이클 (기획서 → 요구사항 명세 → 설계 명세 → 구현 → 시나리오 테스트), 2026.06 ~ 2026.07
- 스택: Java 17, Spring Boot 3.3.5, Spring Security (JWT stateless), Spring Data JPA, Oracle DB, Gradle
- 검증: Postman 시나리오 55개 요청 (회원 12 + 챌린지 43)

### 1.4 엔티티 지도 (챌린지 11개)

```
Challenge ──< Participation >── Team          (편성 결과)
                │
                ├── PendingApplication        (기준 측정 대기 중 신청 임시 보관)
                └──< Submission ──< Confirmation   (인증 제출 → 팀원 확인 판정)

DepositBalance (현재 잔액)  ←검산→  DepositLedgerEntry (append-only 원장)
Settlement ──< TeamPrize ──< MemberPrize      (정산 결과 3계층)
```

- 모든 PK는 `접두어_시퀀스번호` 문자열 (`chal_1`, `part_3`, `dep_7`) — `IdGenerator`가 DB 시퀀스로 발급
- 엔티티 간 JPA 연관관계(@ManyToOne) 없이 String FK 필드로만 참조 → 조인 필요 시 JPQL 암시적 조인 사용

### 1.5 생명주기 흐름 (스케줄러 60초 폴링)

```
[모집] → 정원 도달 → 팀 편성 → [시작] → 수행 기간 → 확인 윈도우 종료 → 정산 → [종료]
   └→ 모집 마감까지 미달 → [무산] + 예치금 전액 반환 (B-01)
```

정산(B-05)은 `SettlementService.expireAndSettle()`이 단 한 번 실행:
개인 판정(환급/차감) → 상금풀 확정(기본 + 차감분) → 팀 순위 분배(등차 가중) → 팀 내 기여도 분배.

## 2부. 핵심 설계 결정 (면접 대비 — "왜 이렇게 했는가")

### ① 검증 2계층 분리 — 기계 판정과 사람 판정

**문제**: 웨이트 무게·횟수는 디바이스가 측정 못 함 → 부정 제출을 막을 근거가 없음.
**결정**: 기계가 판정 가능한 것(사진 해시 중복, EXIF 메타데이터, 소급 24h 유예, 하루 상한/주기)은 시스템이,
수행의 진위는 같은 팀원의 상호 확인(정족수 1)이 판정. 팀 경쟁 구조가 곧 검증 유인이 되도록 설계.
**코드**: `SubmissionValidationService`(기계 5단계) → `PeerConfirmationService`(사람 판정·상태 전이)

### ② 예치금: append-only 원장 + 조회용 잔액 이원화

**문제**: 환급·차감·무산 반환이 얽히면 "돈이 어디로 갔는지" 추적 불가.
**결정**: 돈의 모든 이동은 `DEPOSIT_LEDGER`에 추가(append)로만 기록, 수정·삭제 없음. `DEPOSIT_BALANCE`는 조회용 현재 값.
회계 등식 "원장 amount 합 = 현재 잔액"이 항상 성립해야 하며, 정산 시 재원 등식 검산이 어긋나면 전체 롤백.
**코드**: `DepositService.appendLedger()` — 원장 기록의 단일 통로

### ③ 멱등 키(idempotency key)로 중복 이동 차단

**문제**: 스케줄러 재실행·장애 복구 시 같은 환급이 두 번 실행될 수 있음.
**결정**: 이동마다 의미 있는 키(`join:part_3`, `void:part_3`)를 부여하고, 같은 키가 원장에 있으면 조용히 무시.
**코드**: `DepositService.credit()`/`recordForfeit()`의 `existsByIdempotencyKey` 선두 검사

### ④ 참가 신청의 201/202 이단계 흐름 + PendingApplication

**문제**: 팀 편성에 실력값이 필요한데, 최근 30일 기록이 없는 신규 사용자는 실력을 계산할 수 없음.
**결정**: 기록 있으면 즉시 완료(201), 없으면 신청 내용(강도 계수·목표 주기)을 `PendingApplication`에 보관하고
기준 측정을 요청(202). 측정 통과 시 보관 내용과 합쳐 완료. 예치금은 완료 시점에만 차감.
**코드**: `ParticipationService.apply()` / `submitBaseline()`

### ⑤ 팀 편성: 이중 시작 배정 + 교환 개선 + 결정성 보장

**문제**: 실력 균형 팀 배정은 NP-hard 계열 — 최적해 대신 "재현 가능한 좋은 해"가 필요.
**결정**: 시작 배정 2개(지그재그 serpentine / 내림차순 그리디)를 만들고, 각각 2인 교환을 전수 평가해 개선한 뒤
제약(팀 합 격차 ≤ 허용폭) 우선으로 채택. 정렬·동률 규칙(참가자 ID 사전순)을 고정해 **같은 입력이면 항상 같은 결과**.
**코드**: `TeamFormationEngine` — 순수 계산만, DB 반영은 호출자(`ParticipationService`) 책임으로 분리

### ⑥ 동시성: 정원 판정~편성을 단일 실행으로

**문제**: 마지막 자리에 두 명이 동시 신청하면 둘 다 "정원 도달"로 판정해 편성이 두 번 실행될 수 있음.
**결정**: 판정~편성 구간을 `synchronized(formationLock)`으로 직렬화 (기준 구현: 서버 1대 전제를 명시).
정산도 SETTLEMENT 존재 확인 + challenge_id 유니크 제약의 2중 방어로 단일 실행 보장.
**코드**: `ParticipationService.checkFullAndFormTeams()`, `SettlementService`

### ⑦ 정산 4단계를 단일 트랜잭션 + 검산 롤백

**문제**: 개인 판정→상금풀→팀 분배→개인 분배 중간에 실패하면 돈이 어긋난 채로 남음.
**결정**: 전체를 하나의 트랜잭션으로 묶고, 마지막에 재원 등식을 검산해 어긋나면 예외로 전체 롤백.
분배는 내림(floor) 후 나머지 환수 방식으로 1원 단위 오차를 구조적으로 제거.
**코드**: `SettlementService.expireAndSettle()`

### ⑧ 판정 규칙의 단일 소스 — GoalEvaluator

**문제**: 개인 목표 달성 판정을 순위 조회(F008)와 정산(F009)이 각각 구현하면 결과가 어긋날 수 있음.
**결정**: 판정 규칙(완전 주기만 세는 내림 규칙 등)을 `GoalEvaluator` 컴포넌트 하나로 묶어 두 경로가 공유.
**코드**: `support/GoalEvaluator` ← `RankingService`·`SettlementService`가 공용

### ⑨ 그 밖의 결정

- **String PK (`접두어_번호`)**: DB 시퀀스로 동시성 안전 + ID만 봐도 소속 테이블 식별 (`IdGenerator`)
- **BigDecimal 일관 사용**: 볼륨·실력·금액 계산의 부동소수 오차 제거
- **스케줄러 폴링(60s 고정 지연)**: 이벤트 방식 대신 단순·복구 가능한 구조 선택, 한계는 개선 로드맵 P2-3에 기록
- **명세 기반 개발**: 기획서 → 요구사항 → 설계 명세 → 구현 변경사항 문서까지 전 과정 문서화, 코드 주석이 명세 조항(8.4.3 등)을 역참조

## 3부. 개선 지점 목록

> 상세 계획·계측 방법은 `docs/기타/포트폴리오_개선_로드맵.md` 참조. 여기서는 "무엇이 왜 한계인가"만 요약.
> 공통 원칙: 기준 구현은 "계측 전 최적화 배제"(명세 8.1.7)로 **의도적으로** 단순하게 두었음 — 이 자체가 설계 결정.

| 우선순위 | 지점 | 현재 한계 | 개선 방향 |
|---------|------|----------|----------|
| P0-1 | `TeamFormationEngine.improve()` | 교환 후보 전량 순차 평가 + 분산 전체 재계산, 신청 트랜잭션 안에서 실행 → 인원 커지면 신청 응답 지연 | 후보 프루닝 → 증분 재계산 O(1) → ForkJoinPool 병렬화 (결정성 유지가 관건) |
| P0-2 | 순위 집계·주기 판정 | 조회/제출마다 관련 기록 전량 로드 후 메모리 집계 | 범위 EXISTS/COUNT 쿼리, 증분 누적, 자료구조 교체 |
| P0-3 | 파일 업로드 | `photo.getBytes()` 전체 메모리 적재, 로컬 디스크 저장 | 스트리밍 처리, 크기·타입 검증 강화, 오브젝트 스토리지 |
| P1-1 | 동시성 방어 | `synchronized`는 서버 1대 전제 — 다중 인스턴스에서 무력화 | 레이스 3종 재현 실험 → DB 락/유니크 제약 비교 |
| P1-3 | 편성 엔진 테스트 | 시나리오 테스트(Postman)만 존재, 단위 테스트 부재 | 속성 기반 테스트로 4가지 보장(정원·결정성·제약·개선성) 증명 |
| P2-1 | 조회 성능 | String FK 구조라 N+1·다중 쿼리 발생 지점 존재, 목록 페이지네이션 없음 | fetch 전략·DTO 프로젝션·페이지네이션 |
| P2-2 | 정산 트랜잭션 | 참가자 수에 비례해 트랜잭션이 길어짐 | 경계 분석 후 재설계 |
| P2-3 | 스케줄러 | 60초 폴링 지연 + 다중 인스턴스 중복 실행 위험 | 이벤트 기반 전환 또는 분산 락 |
| P3-1 | JWT 보안 | 만료·무효화 정책 단순, CSRF/SameSite 미심화 | 리프레시 토큰·블랙리스트·쿠키 정책 |
| P3-2 | 관측성 | 계측 수단 없음 — 모든 개선의 선행 조건 | Actuator + Micrometer (가장 먼저 착수) |
| P3-3 | IdGenerator | ID 발급마다 시퀀스 왕복 1회 | 시퀀스 캐시/배치 발급 |

**착수 권장 순서**: P3-2(계측 인프라) → P0-1 → P1-3 → P0-2 → P0-3 → P1-1 → 나머지

## 4. 면접 예상 질문 자가 점검

1. 왜 원장(ledger)을 두었나? 잔액 컬럼 하나로는 왜 안 되나? → 2부 ②
2. 멱등 키는 어떤 장애 시나리오를 막나? → 2부 ③
3. 신청이 왜 두 단계인가? PendingApplication 없이 하면 어떻게 되나? → 2부 ④
4. 팀 편성이 같은 입력에서 항상 같은 결과인 이유는? 왜 그래야 하나? → 2부 ⑤
5. `synchronized`의 한계는? 서버가 2대가 되면? → 2부 ⑥, 3부 P1-1
6. 정산 중간에 서버가 죽으면? → 2부 ⑦ (단일 트랜잭션 롤백 + 재실행 시 멱등)
7. 편성 알고리즘의 시간 복잡도와 개선 계획은? → 3부 P0-1
8. 단위 테스트가 없는 이유와 보완 계획은? → 시나리오 55개 우선 전략 + 3부 P1-3
