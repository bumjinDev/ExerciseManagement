# Git 피처 브랜치 커밋 가이드

작성일: 2026-07-08
전제: 현재 브랜치 develop, 개발 산출물 전체가 미커밋(워킹 트리) 상태.
구조: develop에서 피처 브랜치 생성 → 해당 기능 파일만 커밋 → develop에 --no-ff 머지 → 반복 → 마지막에 main으로 머지.
피처 브랜치는 삭제하지 않고 원격에 push해 기능별 커밋 기록을 유지한다.

## 브랜치 구성 (머지 순서대로)

| # | 브랜치 | 내용 |
|---|--------|------|
| 1 | feature/db-schema | docs/sql/ DDL 스크립트 + .gitignore(data/ 제외) |
| 2 | feature/member-auth | JWT 인증·회원 관리 (auth/, members/) + 빌드·설정 파일 |
| 3 | feature/challenge-domain | 챌린지 공통·엔티티·리포지토리·DTO 계층 |
| 4 | feature/challenge-participation | 등록·조회·참가 신청·팀 편성·예치 |
| 5 | feature/challenge-submission | 인증 제출 기계 검증·팀원 확인·제출 조회 |
| 6 | feature/challenge-ranking-settlement | 순위 산출·정산·수명주기 스케줄러 |
| 7 | feature/ui | 정적 페이지 UI 9화면 |
| 8 | feature/docs | 가이드·설계·테스트 문서 |

순서 근거: 3→4→5→6은 의존 방향(도메인 계층 → 서비스)이라, 각 피처 브랜치 시점의 코드가 단독으로 컴파일된다.
build.gradle과 application.yaml은 여러 단계에 걸친 변경이 섞여 있어 2번(member-auth)에서 통째로 커밋한다.

## 명령 시퀀스 (Git Bash, 프로젝트 루트에서)

### 0. 시작 전 확인

```bash
git status          # 현재 develop, 산출물이 미커밋 상태인지 확인
git branch          # develop, main 존재 확인
```

### 1. feature/db-schema

```bash
echo "/data/" >> .gitignore      # 인증샷 런타임 저장 디렉토리는 커밋 제외

git checkout -b feature/db-schema develop
git add .gitignore docs/sql/01_create_user.sql docs/sql/02_member_tables.sql
git commit -m "feat: 전용 Oracle 계정·회원 관리 테이블 DDL 작성"
git add docs/sql/03_challenge_tables.sql docs/sql/03_challenge_tables_no_constraints.sql docs/sql/03_reset_challenge_tables.sql docs/sql/04_stage3_additions.sql
git commit -m "feat: 챌린지 도메인 테이블 DDL 작성 (제약·무제약 변형, 초기화 스크립트 포함)"

git checkout develop
git merge --no-ff feature/db-schema -m "merge: feature/db-schema → develop"
```

```bash

```

## 주의사항

- 미커밋 파일은 브랜치를 오가도 워킹 트리에 그대로 따라온다 — 정상 동작이며, 각 단계에서 그 기능의 파일만 add하면 된다.
- `--no-ff`를 빼면 fast-forward로 머지되어 피처 브랜치 구조가 히스토리에 남지 않는다.
- `data/`(인증샷 런타임 저장소)는 1번에서 .gitignore에 추가하므로 절대 add하지 말 것.
- 8번까지 끝난 뒤 `git status`에 미커밋 파일이 남아 있으면 어떤 파일인지 확인 후 적절한 브랜치 성격에 맞춰 추가 커밋한다.
