# P0-1. 팀 편성 CPU 바운드 구간 — 알고리즘 개선 + ForkJoinPool

## 현재 상태

`TeamFormationEngine.improve()` — 교환 반복 1회마다 후보 **K(K−1)/2 × N²개**(K: 팀 수, N: 정원)를 전량 순차 평가하고,
후보마다 전체 팀의 분산을 처음부터 재계산한다. 명세 8.1.7의 원칙(기준 구현은 정의 그대로, 최적화는 계측 후)에 따라 의도적으로 남겨둔 구간.

## 1단계 — 기준 계측

- 참가자 규모 스케일링: 2×2(4명) / 4×5(20명) / 10×10(100명) / 20×25(500명) / 40×25(1,000명)
- 실력 분포 3종: 균등 / 정규 / 이상치 포함(허용폭 달성 불가 풀 — 합 필터의 분기 경로가 다름)
- 측정: 편성 총 소요시간, 반복 횟수, 반복당 후보 평가 수. JMH 마이크로벤치마크(엔진이 순수 함수라 적합) + 운영 경로는 Micrometer `Timer`
- 산출물: 규모별 소요시간 곡선 → "몇 명부터 신청 응답 지연이 체감되는가"(편성이 신청 트랜잭션 안에서 실행됨을 상기)

## 2단계 — 알고리즘 개선 (병렬화보다 먼저)

1. **후보 프루닝**: 분산 최대 팀 또는 최소 팀이 낀 팀 짝만 평가 — 명세 8.1(F004)이 **결과 불변을 증명해 둔** 유일한 생략. 후보 수가 K(K−1)/2 → (2K−3)개 팀 짝 수준으로 감소
2. **증분 재계산**: 교환은 두 팀의 분산만 바꾼다 — 팀별 합·제곱합을 유지하면 분산 갱신이 O(N)→O(1). 단, 명세가 "결과가 변하지 않는 구현 선택"으로 열어둔 항목이므로 결과 동일성 회귀 테스트(P1-3) 필수
3. 부동소수 누적 오차 검토: 증분 방식은 덧셈 순서가 달라져 double 오차가 생길 수 있음 → 동률 판정 epsilon 설계 근거 문서화

## 3단계 — ForkJoinPool 병렬화

- 후보 평가 구간을 `RecursiveTask`로 분할: 후보 인덱스 구간을 쪼개 스레드별 지역 최선(best)을 구한 뒤 reduce
- **결정성 유지가 핵심 난제**: 동률 규칙(참가자 ID 사전순)이 병렬 reduce에서도 동일하게 적용되도록 비교자를 순차 버전과 완전히 일치시킬 것 — 병렬화가 결과를 바꾸면 명세의 결정성 보장 위반
- 공유 가변 상태 제거: 현재 구현은 swap→평가→복원 방식이라 병렬 불가. 후보 평가를 "배정 스냅샷 + 교환 좌표"의 무상태 계산으로 재구성해야 함 (이 재구성 자체가 이야깃거리)
- `parallelStream`(commonPool) vs 전용 ForkJoinPool 비교: 웹 요청 스레드에서 commonPool을 쓰면 다른 요청과 자원 경합 — 전용 풀 크기 선정 근거(코어 수, CPU 바운드)
- 트랜잭션 경계 검토: 편성이 신청 트랜잭션 내부에서 실행됨. 병렬 구간은 순수 계산이라 DB 자원을 안 쓰지만, 응답 지연이 크면 "편성을 트랜잭션 밖 비동기로 분리(신청 완료 응답 후 편성 이벤트)"까지 논의 확장 가능

## 4단계 — 검증과 산출물

- 순차/프루닝/증분/병렬 4개 구현의 **결과 완전 동일성**(P1-3 속성 테스트 재사용) + 규모별 속도 곡선 비교
- 예상 면접 질문: "왜 병렬화 전에 알고리즘부터 줄였나" / "병렬화로 결과가 달라질 뻔한 지점은" / "Amdahl 법칙 관점에서 한계는"

# P0-2. 자료구조·알고리즘 최적화

## 대상 1 — 순위 집계 (P1-2와 연동)

`RankingService.computeMemberVolumes()`·`computeTeamOrder()`: 조회마다 확인 완료 제출 전량 로드 → HashMap 집계 → 정렬.
개선 축: 확인 시점 증분 누적(명세 8.3.2의 접근 패턴 그대로) + 정렬 유지 자료구조(TreeMap/색인 리스트) 선택. 상세는 P1-2.

## 대상 2 — 인증 주기 판정

`SubmissionRepository.findCountableDates()`: 참가자의 인정 제출 날짜 **전체**를 매 제출마다 로드.
- '며칠에 한 번'(간격 n): 필요한 것은 `[수행일−n+1, 수행일+n−1]` 범위 존재 여부 1건 → 날짜 범위 EXISTS 쿼리로 대체
- '주 며칠': 해당 주 7일 범위의 DISTINCT 날짜 수만 필요 → 범위 COUNT 쿼리
- 수행 기간이 길어질수록(제출 수백 건) 전량 로드와 범위 쿼리의 격차 계측

## 대상 3 — 자잘한 컬렉션 선택

- `SubmissionQueryService.pendingSubmissions()`: `List.contains()` O(n) 필터 → `Set` 조회 O(1)
- `RankingService`의 정렬 Comparator 다중 생성 → 상수화
- 효과는 작지만 "컬렉션 선택 근거를 설명할 수 있는가"용 소재

## 검증

p6spy로 쿼리 수·로드 행 수 전/후 비교, 대상 2는 제출 수 스케일링(10/100/1,000건) 응답시간 곡선.

# P0-3. 파일 업로드 — 메모리·정합성·보안·저장 구조

## 현재 상태와 문제 지점

`SubmissionValidationService` / `ParticipationService` / `PhotoStorage`:

1. **메모리**: `photo.getBytes()`로 최대 10MB를 통째로 힙에 적재 → 해시 계산·EXIF 파싱·저장에 같은 배열 재사용. 동시 업로드 N건이면 N×10MB 힙 점유
2. **정합성 (파일 ↔ DB)**: 파일 저장 후 트랜잭션이 롤백되면(기준 측정의 잔액 부족 402가 실제 사례) **고아 파일이 디스크에 남는다** — 파일시스템은 트랜잭션 자원이 아님
3. **TOCTOU 레이스**: 해시 1차 대조(SELECT)와 INSERT 사이에 같은 사진이 동시 진입 가능 — 제약 스키마의 `UNIQUE(challenge_id, photo_hash)`가 최종 방어선 (P1-1과 연결)
4. **보안**: 확장자를 원본 파일명에서 신뢰. Content-Type·매직 바이트 검증 없음 → 위장 파일 업로드 여지 (EXIF 파싱 실패가 부분 방어이나 명시적이지 않음)
5. **확장성**: 로컬 디스크 직저장 — 미니 PC 이관·다중 인스턴스 시 공유 불가

## 개선 설계

1. **스트리밍 처리**: `DigestInputStream`으로 읽으면서 SHA-256 계산 + 임시 파일에 동시 기록 → 힙 점유를 버퍼 크기(예: 8KB)로 고정. JFR/VisualVM으로 동시 업로드 부하(예: 20건 병렬) 시 힙 사용량 전/후 비교
2. **원자성**: 임시 디렉토리에 쓰고 **트랜잭션 커밋 후 최종 경로로 move** (`TransactionSynchronization.afterCommit`) + 롤백 시 임시 파일 삭제. 보조 수단으로 고아 파일 청소 배치(DB에 photo_path 없는 파일 스캔)
3. **검증 강화**: 매직 바이트(JPEG/PNG 시그니처) 검사 → 실패 시 E-SUB-META-MISMATCH. 허용 형식·최대 크기를 설정 프로퍼티로 명시(명세 12.3 미확정 항목의 확정)
4. **저장 추상화**: `PhotoStorage`를 인터페이스로 승격 → 로컬 구현 / (선택) MinIO·S3 호환 구현. "왜 DB BLOB가 아닌가"(백업·캐시·트랜잭션 로그 비대화) 비교 논거 문서화

## 예상 면접 질문

"10MB 파일 100개가 동시에 올라오면?" / "파일은 저장됐는데 DB가 롤백되면?" / "확장자 검증만으로 충분한가?"

# P1-1. 동시성 레이스 3종 재현과 방어선 비교

**이 프로젝트 고유의 실험 환경**: DDL이 제약 포함 원본(`docs/sql/03_challenge_tables.sql`)과 무제약 변형 두 벌로 준비되어 있어,
"애플리케이션 검증만 vs DB 제약 최종 방어"를 같은 코드로 A/B 계측할 수 있다.

| 레이스 | 재현 방법 | 현재 방어 | 비교할 대안 |
|--------|----------|----------|------------|
| 모집 마지막 자리 경합 (정원 초과·편성 이중 실행) | `synchronized` 제거 후 마지막 1자리에 동시 신청 (JMeter/Postman 병렬) | `synchronized` + 단일 인스턴스 전제 | ① 비관적 락(`SELECT FOR UPDATE` 후 카운트) ② 낙관적 락+재시도 ③ 유니크 제약 활용 |
| 팀원 확인 이중 가산 (정족수 1 위반) | 무제약 스키마에서 같은 제출에 동시 확인 2건 | 앱 존재 확인 (check-then-act 갭 존재) | `UNIQUE(submission_id)` 복원 → DataIntegrityViolation을 E-CFM-ALREADY-TERMINAL로 변환 |
| 예치 잔액 lost update | 같은 계정에 동시 충전+차감 반복 → 원장 SUM ≠ balance 검출 | read-modify-write (무방비) | ① `@Version` 낙관적 락 ② 원자적 `UPDATE balance = balance ± ?` ③ 원장 재계산 방식 |

- 성공 판정 지표: 레이스 발생률(전/후), 처리량 저하폭(락 방식별), 원장 검산 일치율
- 산출물: "정합성 방어선을 어느 계층에 둘 것인가" 의사결정 보고서 — 명세 8.3.3("저장 단계 제약과 통상적인 트랜잭션 처리로 달성")의 실증
- 예상 질문: "synchronized는 서버 2대면 왜 무력한가" / "낙관적·비관적 락 선택 기준" / "유니크 제약 위반을 어떻게 도메인 에러로 바꾸나"

# P1-2. 순위 조회 경로 계측과 저장 전략 결정

명세 8.3.3·10.3이 "계측 후 결정"으로 미룬 항목을 **실제로 계측해서 확정**하는 소재. 명세 서사를 완성한다.

1. **부하 모델**: 참가자 P × 제출 S × 폴링 동시 사용자 C 스케일링 (UI 폴링 5초 주기가 부하 증폭기)
2. **기준 계측**: 현재 구현(조회마다 전량 로드·재집계)의 응답시간·쿼리 행 수·DB CPU
3. **후보 비교**:
   - A. DB 집계로 위임: `GROUP BY` 합계 쿼리 + 인덱스
   - B. 증분 누적 테이블: 확인 확정 시 개인·팀 누적 UPDATE (명세 8.3.2의 접근 패턴 그대로 구현) — 동시 확인의 누적 갱신 경합은 P1-1과 연결
   - C. 애플리케이션 캐시: 폴링 주기(5s)와 TTL 정합, 무효화 시점(확인 확정) 설계
4. **동점 규칙 비용**: "먼저 도달한 팀 우위" 판정이 요구하는 확인 시각 추적을 각 후보에서 어떻게 유지하는지 비교
5. 산출물: 후보별 응답시간 곡선 + 선택 근거 → `명세서_대비_구현_변경사항.md`에 확정 기록

# P1-3. 편성 엔진 속성 기반 테스트 — 4가지 보장의 증명

현재 자동화 테스트 부재(Postman 시나리오만 존재). `TeamFormationEngine`은 의존성 없는 순수 함수라 최적의 시작점이다.

- 무작위 입력 생성(팀 수 2~40, 정원 1~25, 실력 분포 균등/정규/이상치) × 수천 케이스로 명세의 보장을 속성으로 검증:
  1. **정원 유지**: 모든 팀 크기 == N
  2. **무실패**: 어떤 입력에도 예외 없이 배정 반환
  3. **종료**: 시간 상한 내 종료 (반복 무한루프 부재)
  4. **결정성**: 같은 입력 2회 실행 결과 완전 동일 + 입력 순서 셔플 후에도 동일
  5. 채택 규칙: 두 시작점 결과 중 채택된 쪽이 규칙(허용폭 우선)을 만족
- 도구: JUnit 5 + jqwik(속성 기반) 또는 무작위 시드 반복 + 시드 로깅(실패 재현성)
- **P0-1의 회귀 방어망**: 프루닝·증분·병렬 구현마다 "순차 원본과 결과 동일" 속성 추가
- 확장: `SettlementService` 검산 단위 테스트(임의 참가 구성에서 `분배 합+환수 == 상금풀` 항상 성립), `GoalEvaluator` 내림 규칙 경계값 테스트

# P2-1. N+1 쿼리 제거와 목록 페이지네이션

- `ChallengeQueryService.list()`: 챌린지마다 참가자 수 COUNT 1회 → 챌린지 100개면 쿼리 101번. `LEFT JOIN + GROUP BY` 단일 쿼리로 개선
- `DepositService.getStatus()`: 참가 건마다 원장 조회 → IN 절 일괄 로드 후 메모리 그룹핑
- 페이지네이션 부재(명세 12.3 미확정): offset 방식 vs 커서(keyset) 방식 비교 후 확정
- 계측: p6spy/hibernate statistics로 쿼리 수, 데이터 100/1,000건 스케일 응답시간

# P2-2. 정산 롱 트랜잭션 분석과 경계 재설계

- 현재: 4단계 전체 단일 트랜잭션 — 참가자 수천 명이면 트랜잭션 내에서 참가자별 목표 판정(각자 제출 조회) + 원장 기록 전부 수행
- 계측: 참가자 100/1,000/5,000명 시딩 → 정산 소요시간, undo 사용량, 락 유지 시간
- 개선 논의: 판정 단계(읽기)를 트랜잭션 밖 사전 계산으로 분리 / 청크 커밋 + **멱등 키 기반 재개**(이미 구현된 idempotency_key가 부분 실패 후 재실행을 안전하게 만듦 — 기존 설계가 확장을 예비한 사례로 어필) / 전량 재검산으로 완료 판정
- 명세 8.4.2 "원자성 보장 방법은 구현 확정" 항목의 심화 확정

# P2-3. 스케줄러 구조 — 폴링 한계와 분산 환경

- 현재: 60초 fixedDelay + STARTED 전수 조회 후 코드 필터링, 단일 인스턴스 전제
- 소재 ①: 챌린지 수 증가 시 스캔 비용과 최대 60초 정산 지연 → 마감 시각 조건을 쿼리로 밀기(`windowEnd <= now` 계산 컬럼/식) vs 이벤트 스케줄링(마감 시각 예약 실행) 비교
- 소재 ②: 서버 2대면 tick 중복 실행 — 현재 멱등 장치(settlement 존재 확인·멱등 키)가 어디까지 막는지 분석 → ShedLock(DB 락 기반 스케줄러 상호배제) 도입
- P1-1(동시성)과 함께 "단일 인스턴스 전제 걷어내기" 묶음 서사

# P3-1. JWT 보안 심화

- 만료 14일(테스트값)의 위험 정량화 → 짧은 access + refresh token 회전 설계
