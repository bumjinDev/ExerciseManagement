# 코드 검토 순서 가이드

목적: 프로젝트 전체 코드를 흐름 순서대로 숙지한다. 각 단계의 [ ]를 체크하며 진행.
방법 권장: 그냥 눈으로 읽지 말고 **IDE 디버거로 브레이크포인트를 걸고 Postman/브라우저에서 요청을 쏘며 스텝 실행** — 계층 통과를 눈으로 보는 것이 가장 빠른 숙지법이다.
각 단계에 "자가 점검 질문"이 있다 — 답할 수 있으면 다음 단계로.

---

## 0단계. 지도 펴기 (15분)

- [ ] `build.gradle` — 의존성 목록이 곧 기능 목차다 (security/jjwt=인증, data-jpa/ojdbc=영속, metadata-extractor=사진 검증)
- [ ] `src/main/resources/application.yaml` — 포트·컨텍스트 경로, ddl-auto:none(스키마는 DDL로만), 네이밍 전략, jwt/app 프로퍼티. **여기 있는 설정 하나하나가 어느 코드에서 읽히는지**를 이후 단계에서 계속 연결하게 된다
- [ ] `docs/sql/03_challenge_tables.sql` — 테이블 11개를 훑기만. 컬럼 상세는 3단계에서 엔티티와 대조

**자가 점검**: 이 서버의 베이스 URL이 왜 `http://localhost:8186/exercise`인가?

## 1단계. 요청의 관문 — 인증 (auth 패키지, 1~2시간)

읽기 순서 (요청이 통과하는 순서다):

- [ ] `auth/config/SecurityConfig.java` — **필터체인 4개 = 시스템의 문 4개** (/login, /logout, /members/**, /api/**). 각 체인의 securityMatcher와 permitAll/authenticated 구분이 곧 권한 체계 1계층
- [ ] `auth/filter/LoginFilter.java` — 로그인 요청 처리: JSON 파싱 → AuthenticationManager 위임 → 성공 시 JWT 쿠키 발급 + 리다이렉트
- [ ] `auth/provider/UserAuthenticationProvider.java` + `auth/service/UserEntityDetailService.java` — 실제 인증: userid로 조회 → BCrypt 대조 → 인증 토큰 구성 (details에 userId를 심는 이유 주목)
- [ ] `auth/util/JWTUtil.java` — 토큰 생성·검증·클레임 추출. 만료 14일이 어디서 오는지(yaml)
- [ ] `auth/filter/JwtAuthProcessorFilter.java` — **매 요청의 인증 복원**: 쿠키에서 JWT 추출 → 검증 → SecurityContext에 (userId, 권한) 세팅. 챌린지 컨트롤러들의 `authentication.getName()`이 여기서 만들어진 userId다
- [ ] `auth/handler/` 4종 — 로그인 실패 401 / 인증 실패 401 / 인가 실패 403의 JSON 응답 지점
- [ ] `auth/entity/AuthenticationEntity.java` — userentity + roles 컬렉션 테이블

**디버깅 실습**: `JwtAuthProcessorFilter.doFilterInternal`에 브레이크포인트 → 브라우저 로그인 후 아무 API 호출 → 쿠키에서 SecurityContext까지 스텝 실행.

**자가 점검**: ① 로그인 안 한 사용자가 `GET /api/challenges`를 호출하면 어느 체인의 어떤 규칙 덕에 통과되나? ② `POST /api/deposits`는 어디서 401이 만들어지나?

## 2단계. 가장 단순한 수직 슬라이스 — 회원 가입 (members 패키지, 1시간)

**이 단계의 목적은 회원 기능 자체가 아니라 "계층 호출 패턴" 학습이다.** Controller → Service(도메인 검증) → Repository → Entity 패턴이 챌린지 도메인에서 그대로 반복된다 — 여기서 패턴을 익히면 챌린지는 "같은 패턴 × 더 많은 규칙"일 뿐이다.

- [ ] `members/controller/MembersAPIController.java` — join/edit/loginSuccess 엔드포인트, @Valid의 역할
- [ ] `members/service/MemberService.java` — validJoin: 예약어 → 중복 → BCrypt → 두 테이블 동시 저장(@Transactional). editMember: 닉네임 검증 + JWT 재발급
- [ ] `members/dao/MembersRepository.java` + `MemberEntityRepository.java` — 회원·인증 테이블 이원 갱신 구조
- [ ] `members/exception/` — @RestControllerAdvice가 예외를 HTTP 응답으로 바꾸는 지점 (챌린지의 GlobalChallengeExceptionHandler와 같은 패턴)

**자가 점검**: 가입 시 INSERT가 몇 번 일어나는가? (힌트: 테이블 3개)

---

## 3단계. 챌린지 도메인의 공통 어휘 (2~3시간)

서비스 로직을 읽기 전에 어휘(타입·에러·엔티티)부터. **명세서 7.1(데이터 모델)과 6.8(에러 코드)을 옆에 띄워놓고 1:1 대조하며** 읽을 것.

- [ ] `challenge/common/` 열거형 7종 — 특히 `SubmissionStatus`(확인 대기→확인 완료/반려/만료 상태 기계)와 `CycleMode`(@JsonValue로 JSON은 한글, DB는 영문 상수인 이중 표현)
- [ ] `challenge/exception/ErrorCode.java` — 에러 코드 24종 = 명세 6.8 + 신설분. 코드↔HTTP 상태 매핑
- [ ] `challenge/exception/GlobalChallengeExceptionHandler.java` — 모든 실패가 `{errorCode, message}`로 통일되는 지점
- [ ] `challenge/entity/` 11종 — 명세 7.1 표와 대조. **Challenge의 시각 계산 메서드**(submissionFullDeadline, confirmWindowEnd — 마감 체계의 심장), Participation.intensityFloor()
- [ ] `challenge/repository/` — 쿼리 메서드 이름이 곧 비즈니스 질문이다. 특히 `SubmissionRepository`의 @Query 3개(하루 상한 카운트, 주기 판정용 날짜 목록, 최근 30일 종목 집계)
- [ ] `challenge/config/ChallengeProperties.java` — yaml의 app.* 바인딩 (한글 Map 키 대괄호 표기 이슈 회고)
- [ ] `challenge/support/` — IdGenerator(시퀀스+접두어), PhotoStorage(해시·저장), PhotoMetadataValidator(EXIF), GoalEvaluator(목표 판정 — 순위 조회와 정산이 공용)

**자가 점검**: ① 제출 완전 마감과 확인 윈도우 종료는 각각 어떻게 계산되나? ② 기준 측정 행은 어느 테이블에 어떻게 구분 저장되나?

## 4단계. 챌린지 한 개의 일생 — 서비스 계층 (핵심, 4~6시간)

**챌린지 데이터의 수명주기 순서 = 읽기 순서**다. 각 서비스마다 대응 컨트롤러를 짝으로 같이 읽는다.

1. - [ ] `ChallengeRegistrationService` (+Controller) — 성립 검증(닫힌 종목 목록), creator 기록, 상금풀 프로퍼티
2. - [ ] `ChallengeQueryService` (+Controller) — 읽기 경로가 쓰기와 분리된 이유(명세 5.1). N+1 지점(개선 로드맵 P2-1) 눈도장
3. - [ ] `DepositService` (+Controller) — **원장 회계 규칙**: 원장 amount 합 = 잔액, FORFEIT는 0원 상태 기록. 멱등 키의 쓰임
4. - [ ] `ParticipationService` (+Controller) — 가장 복잡한 서비스. 읽는 축 3개:
   - apply()의 201/202 분기 (최근 30일 기록 유무 → 즉시 완료 vs PendingApplication 보관)
   - submitBaseline() → completeParticipation() (기계 검증 → 기준값 확정 → 예치 차감 → 참가 생성)
   - checkFullAndFormTeams() (synchronized + 인원 판정 + 편성 실행 + STARTED 전이 — 동시성 소재 P1-1의 무대)
5. - [ ] `TeamFormationEngine` — **명세 8.1.4를 옆에 두고 별도 정독**: 시작 배정 2개 → 합 필터 → 최선 교환 → 채택 규칙. 동률 규칙(결정성)이 코드 어디인지 짚기 (P0-1 최적화의 대상)
6. - [ ] `SubmissionValidationService` (+SubmissionController) — 기계 검증 5종의 **순서**(마감→해시→메타→소급→빈도)와 각 순서의 이유(명세 8.2.1), multipart 처리
7. - [ ] `PeerConfirmationService` (+ConfirmationController) — 권한 검사 순서(같은 팀→본인→종착), append 전용 기록, 상태 전이 = 점수 반영
8. - [ ] `SubmissionQueryService` — me(날짜별 묶음)/pending(팀원 확인 대상)/photo(인가 후 파일 반환)
9. - [ ] `RankingService` + `GoalEvaluator` 재방문 — 볼륨 집계, 동점 규칙(먼저 도달 우위), 공동 순위, 목표 내림 규칙. "조회 때마다 전량 재집계"인 현재 구조 인지 (P1-2 소재)
10. - [ ] `ChallengeLifecycleScheduler` → `SettlementService` — B-01 무산·반환 / B-03~05 만료→정산. 정산 4단계와 **검산식 2개**, 단일 실행 장치(존재 확인+멱등 키), ENDED 전이

**디버깅 실습**: Postman 챌린지 컬렉션 폴더 03(참가 신청)을 다시 돌리며 `ParticipationService.apply`와 `checkFullAndFormTeams`에 브레이크포인트 — 4번째 신청에서 편성이 실행되는 순간을 직접 관찰.

**자가 점검**: ① 확인이 이중으로 들어오면 막는 장치가 두 계층에 있다 — 각각 어디인가? ② 예치 잔액의 "원본"은 어느 테이블인가? ③ 정산이 두 번 실행되지 않는 이유 두 가지는? ④ 반려된 제출을 다시 올리면 기존 건은 어떻게 되나?

## 5단계. UI — 백엔드의 거울 (1~2시간)

- [ ] `static/js/api.js` — 함수 4개가 전부. api()가 서버 에러 포맷을 JS 예외로 바꾸는 것 = GlobalChallengeExceptionHandler의 거울상
- [ ] `deposits.html` (가장 단순한 화면 원형) → `index.html` → `submit.html` (FormData multipart) → `challenge-detail.html` (201/202 분기가 화면 분기로) → `confirm.html` (사진 img 태그 = photo 엔드포인트) → `rankings.html` (setInterval 폴링 = 명세 6.6)

**실습**: 브라우저 F12 Network 탭 켜고 화면 조작 — 각 클릭이 만드는 API 요청을 Postman에서 본 것과 대조.

## 6단계. 종합 — 능동 검증 (1시간)

- [ ] Postman 컬렉션 요청 하나를 골라(추천: 팀원 확인 POST) **종이에 통과 경로를 그리기**: 필터체인 → 필터 → 컨트롤러 → 서비스(검사 순서) → 리포지토리 → 응답/예외 핸들러
- [ ] `docs/설계/명세서_대비_구현_변경사항.md` 33개 항목을 훑으며 각 항목이 코드 어디인지 떠올려보기 — 떠오르지 않는 항목이 남은 복습 지점이다
- [ ] `docs/기타/포트폴리오_개선_로드맵.md`의 P0~P1 소재 위치를 코드에서 직접 찾아보기 — 개선 작업의 사전 답사

## 요약 로드맵

| 단계 | 내용 | 예상 시간 |
|------|------|----------|
| 0 | 설정·의존성·DDL 지도 | 15분 |
| 1 | 인증 관문 (auth) | 1~2h |
| 2 | 수직 슬라이스 패턴 (members) | 1h |
| 3 | 도메인 어휘 (enums·entity·repository) | 2~3h |
| 4 | 수명주기 순서 서비스 정독 | 4~6h |
| 5 | UI 대조 | 1~2h |
| 6 | 능동 검증 | 1h |

하루 2시간 기준 약 5~6일 분량. 단계 4가 절반이니 4-1~4-5(참가·편성까지) / 4-6~4-10(제출~정산)으로 이틀에 나누는 것을 권장.
