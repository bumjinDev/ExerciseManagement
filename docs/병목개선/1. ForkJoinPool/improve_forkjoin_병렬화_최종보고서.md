## 개요

### 대상 작업

개선 알고리즘은 이미 만들어진 팀 배정에서, 서로 다른 두 팀에서 한 명씩 맞바꿔 보며 배정이 좋아지는지 확인하는 작업을 반복한다. 이 보고서에서 쓰는 용어는 다음과 같다.

| 용어 | 뜻 |
|---|---|
| 검사 | 교환 후보 하나를 실제로 맞바꿔 보고, 배정이 좋아졌는지 확인한 뒤 되돌리는 작업 1회. 관련 성능 분석 문서에서는 같은 동작을 평가라고 부른다 |
| 스캔 | 모든 팀 쌍의 모든 교환 후보를 검사하고, 그중 가장 좋은 교환 1건을 적용하는 과정. 호출 1회는 배정이 더 좋아지지 않을 때까지 스캔을 반복한다 |
| 말단 작업 | 팀 쌍 목록을 나눈 작업 단위. fork-join 풀의 워커 스레드들이 말단 작업을 나눠 실행한다 |
| 분할 개수 | 팀 쌍 목록을 몇 개의 말단 작업으로 나눌지 정하는 값 |
| 워커 스레드 개수 | fork-join 풀을 만들 때 지정한 병렬도. 관련 성능 분석 문서에서는 풀 병렬도라고 부른다. 실제로 말단 작업을 실행한 워커가 이 값보다 많았던 실행이 있다(5.2절) |
| 경과 시간 | `improve()` 호출 1회가 시작해서 끝날 때까지 실제로 흐른 시간 |
| 프로세스 CPU 시간 | `improve()` 호출 1회 동안 프로세스의 모든 스레드가 쓴 CPU 시간의 합 |
| 워커 CPU 시간 | `improve()` 호출 1회 동안 fork-join 풀의 워커 스레드들이 쓴 CPU 시간의 합 |
| 배율 | 순차 실행의 경과 시간 ÷ 병렬 실행의 경과 시간. 병렬 실행이 순차 실행보다 몇 배 빠른지를 나타낸다 |

병렬화한 것은 스캔 1회 안의 전수 조사다. 다음 스캔은 앞 스캔이 적용한 교환 결과에서 시작하므로, 스캔끼리는 순차로 실행한다.

### 결과 요약

결과는 세 가지다.

1. 물리 코어 6개인 환경에서 벤치마크 도구(JMH)로 측정한 병렬화 배율은 인원 200명과 300명에서 모두 2.42배였다.
2. 배율을 낮춘 원인이 편차 계산에서 검사마다 스트림을 생성하며 새로 할당하는 객체라는 것을 측정으로 확정했다.
3. 편차 계산을 맞바꾼 두 팀의 합과 제곱합만 갱신하는 증분 재계산으로 바꾸자, 병렬화하지 않은 순차 실행도 빨라졌다.

### 측정 목록

측정은 아홉 가지이고 다음 순서로 진행했다. 본문에서는 값을 적을 때마다 이 이름으로 출처를 밝힌다.

| 단계 | 측정 이름 | 측정 대상과 방법 |
|---|---|---|
| 얼마나 빨라졌는가 | 기준 측정 | 벤치마크 도구(JMH)로 인원을 20명에서 300명까지 바꿔 가며 순차와 병렬의 경과 시간을 측정해 배율을 구했다. CPU 시간을 함께 읽는 테스트 프로그램으로 인원 120명과 200명에서 워커 스레드 개수(6, 12)와 말단 작업 개수(16, 32)를 조합한 네 실행도 측정했다 |
| 얼마나 빨라졌는가 | 분할 개수별 측정 | CPU 시간을 함께 읽는 테스트 프로그램으로 워커 스레드 개수(6과 12)와 분할 개수(1부터 36까지)를 바꿔 가며 전 구간을 측정했다 |
| 원인 후보 제외 | 카운터 측정 | 검사 횟수와 합 편차를 보고 거르는 필터를 통과한 횟수를 세는 카운터를 넣고, 분할 개수별 측정과 같은 워커 스레드 개수(6과 12)에서 분할 1부터 12까지와 18, 24, 36을 다시 측정했다 |
| 원인 후보 제외 | 상세 기록 측정 | 검사마다 시각을 읽는 기록을 추가해 다시 측정했다 |
| 원인 후보 제외 | 클럭 측정 | 운영체제 성능 카운터로 실행 중의 CPU 클럭을 함께 기록하며 다시 측정했다 |
| 원인 확정 | for문 대조 측정 | 합 편차 계산과 분포 편차 계산을 스트림 대신 명령형 반복문(for문)으로 바꾼 구현을 같은 조건으로 측정해 원래 구현과 비교했다 |
| 원인 확정 | JFR 측정 | 할당이 발생하는 문장을 실행 기록기(JFR)의 할당 표본으로 확인했다. 같은 기록에 순차 실행도 들어 있다 |
| 개선 확인 | 증분 재계산 측정 | 편차 계산을 증분 재계산으로 바꾸고, 순차 실행과 워커 스레드 6개·12개 각각의 분할 1부터 12까지와 18, 24, 36 설정 전체를 여섯 번 실행해 측정했다 |
| 개선 확인 | JFR 재측정 | 증분 재계산 구현의 할당을 실행 기록기로 다시 확인했다 |

계측 코드는 그 자체로 시간을 쓴다. 그래서 계측 코드가 서로 다른 측정끼리는 시간 값을 정밀한 배수로 비교하지 않는다. 함께 볼 때는 어느 측정인지 밝히고 규모만 비교한다.

for문 대조 측정은 다음 세 실행으로 이루어져 있다. 표마다 어느 실행의 값인지 적는다.

- 스트림 분할 36 실행: 스트림 구현을 분할 36에서 측정한 실행
- for문 분할 36 실행: for문 구현을 분할 36에서 측정한 실행
- for문 전체 분할 실행: for문 구현을 분할 1부터 12까지와 18, 24, 36의 열다섯 가지에서 측정한 실행

테스트 프로그램으로 측정한 값은 설정마다 워밍업을 버린 뒤 측정 5회를 평균한 것이다. 버린 워밍업은 증분 재계산 측정 전까지의 측정이 2회, 증분 재계산 측정이 5회(여섯 실행 중 한 실행은 10회), JFR 재측정이 100회다. 할당량만 예외로, 각 실행에서 처음 측정한 병렬 설정은 측정 순번 1을 빼고 측정 2~5번째를 평균한다. 이 측정 순번 1은 할당량이 약 3.8MB 더 크게 측정된다. 워밍업에서 꺼 두었던 상세 기록 코드가 이때 처음 실행되면서 생긴 할당으로 보인다. 근거는 0편 5절에 있다.

## 1. 벤치마크 도구로 측정한 병렬화 배율은 인원 200명과 300명에서 모두 2.42배였다

병렬화를 마친 뒤 가장 먼저 측정한 것은 순차 대비 배율이다. 벤치마크 도구(JMH)로 인원을 바꿔 가며 순차 실행과 병렬 실행의 평균 경과 시간을 측정했다. 이 측정이 기준 측정이다.

| 인원 | 순차 평균 경과 시간(improve() 호출 1회, ms) | 병렬 평균 경과 시간(improve() 호출 1회, ms) | 배율(배) |
|---:|---:|---:|---:|
| 20 | 0.090 | 0.315 | 0.29 |
| 120 | 651.458 | 210.754 | 3.09 |
| 200 | 3,628.497 | 1,496.298 | 2.42 |
| 300 | 25,727.455 | 10,610.148 | 2.42 |

※ 배율 = 순차 평균 경과 시간 ÷ 병렬 평균 경과 시간.

배율은 인원 120명에서 3.09까지 오른 뒤, 200명과 300명에서는 2.42다. 이 작업은 입출력을 기다리는 구간이 없는 CPU 바운드 작업이므로, 사용하는 코어 수에 반비례해 경과 시간이 줄어드는 것이 기대치다. 워커 스레드는 12개지만, 12는 풀에 둔 스레드의 개수이고 6은 그 스레드들이 실행될 물리 코어의 개수이므로 기대치를 6배로 잡았다. 실제 배율 2.42는 기대치 6배의 40%다. 이 보고서가 설명해야 할 값은 200명과 300명의 2.42다.

인원 20명에서는 배율이 1보다 작아 병렬 실행이 오히려 느리다. 인원이 적으면 fork-join 풀 생성, 말단 작업마다의 팀 배정 복사, 말단 작업 결과의 병합에 드는 시간의 비중이 커지기 때문으로 보인다.

## 2. 코어는 유휴 상태가 아니었고, 동시에 실행되는 말단 작업이 늘수록 프로세스 CPU 시간이 늘었다

### 2.1 병렬 실행 중 코어는 평균 7.85개가 사용되고 있었다

먼저 배율을 낮춘 원인이 코어를 충분히 쓰지 못한 데 있는지 확인했다. 같은 인원 200명을 CPU 시간을 함께 읽는 테스트 프로그램으로 다시 측정했다(기준 측정).

| 값 | 순차(풀을 쓰지 않음) | 병렬(워커 스레드 12개, 분할 16개) |
|---|---:|---:|
| 경과 시간(improve() 호출 1회, ms) | 3,378.91 | 764.76 |
| 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ms) | 3,375.00 | 6,006.25 |

※ 표의 값

- 값: 호출 1회당 값이고, 워밍업 2회를 버린 측정 5회의 평균이다.
- 분할 16개: 말단 작업 하나가 맡는 팀 쌍이 12개 이하가 될 때까지 팀 쌍 190개를 절반씩 나눈 결과다.

측정 결과는 다음과 같다.

- 배율은 4.42배(3,378.91 ÷ 764.76)다. 같은 인원, 같은 워커 스레드 개수를 JMH로 측정한 1절의 배율 2.42배와 값이 다르다.
- 프로세스 CPU 시간은 순차 실행의 1.78배(6,006.25 ÷ 3,375.00)가 됐다. 병렬화는 검사 자체를 바꾸지 않았으므로, 추가 비용이 없다면 병렬 실행의 프로세스 CPU 시간은 순차 실행과 같아야 한다.
- 순차 대비 CPU 효율(순차 실행의 프로세스 CPU 시간 ÷ 병렬 실행의 프로세스 CPU 시간)은 56%(3,375.00 ÷ 6,006.25)였다.
- 평균 사용 코어 수(프로세스 CPU 시간 ÷ 경과 시간)는 7.85개(6,006.25 ÷ 764.76)다.

평균 사용 코어 수 7.85와 순차 대비 CPU 효율 0.56을 곱한 값은 배율 4.42와 거의 같다. 순차 실행에서는 프로세스 CPU 시간과 경과 시간이 거의 같기 때문이다. 코어는 평균 7.85개가 사용되고 있었으므로, 배율을 낮춘 것은 사용한 코어 개수가 아니라 순차 대비 CPU 효율이다.

### 2.2 분할을 늘리면 경과 시간은 줄지만 프로세스 CPU 시간은 늘어난다

2.1절에서 병렬 실행이 순차 실행보다 프로세스 CPU 시간을 1.78배 쓴다는 것을 확인했다. 이 시간이 동시에 실행되는 말단 작업 개수에 따라 어떻게 변하는지 보려고, 워커 스레드를 12개로 두고 분할 개수를 1부터 12까지 바꿔 가며 경과 시간과 프로세스 CPU 시간을 측정했다(상세 기록 측정). 워커 스레드가 12개이므로 이 구간에서는 동시에 실행되는 말단 작업 개수가 분할 개수와 같다.

| 분할 개수 | 경과 시간(improve() 호출 1회, ms) | 직전 분할 대비 감소량(ms) | 순차 대비 배율(배) | 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ms) |
|---:|---:|---:|---:|---:|
| 1 | 4,445.3 | | 0.93 | 4,434.4 |
| 2 | 2,733.4 | 1,711.9 | 1.51 | 5,368.8 |
| 3 | 2,217.7 | 515.8 | 1.87 | 6,415.6 |
| 4 | 2,055.1 | 162.5 | 2.01 | 7,640.6 |
| 5 | 2,036.4 | 18.7 | 2.03 | 9,337.5 |
| 6 | 1,931.5 | 104.9 | 2.14 | 10,675.0 |
| 7 | 1,815.8 | 115.7 | 2.28 | 11,625.0 |
| 8 | 1,710.3 | 105.5 | 2.42 | 12,534.4 |
| 9 | 1,620.1 | 90.1 | 2.55 | 13,165.6 |
| 10 | 1,542.0 | 78.1 | 2.68 | 14,175.0 |
| 11 | 1,496.7 | 45.3 | 2.76 | 14,443.8 |
| 12 | 1,520.8 | -24.1 | 2.72 | 14,318.8 |

※ 표의 값

- 값: 호출 1회당 값이고, 워밍업 2회를 버린 측정 5회의 평균이다.
- 직전 분할 대비 감소량: 직전 분할의 경과 시간 − 그 분할의 경과 시간. 분할 1은 직전 분할이 없어 빈칸이다.
- 순차 대비 배율: 순차 실행의 경과 시간 ÷ 그 행의 경과 시간. 순차 실행의 경과 시간은 같은 측정에서 4,137.2ms다.

경과 시간은 분할을 늘릴수록 줄지만, 분할 개수에 비례해 줄지는 않는다. 직전 분할 대비 감소량은 분할 2와 분할 3에서 크고, 분할 4부터는 162.5ms를 넘지 않는다.

가장 빠른 지점은 분할 11이고 순차 대비 2.76배다. 분할 12의 경과 시간은 분할 11보다 오히려 길다. for문 구현에서도 분할 12의 경과 시간이 분할 11보다 길어지며, 이 내용은 9절에서 다룬다.

프로세스 CPU 시간은 경과 시간과 반대로 분할 11까지 분할을 늘릴 때마다 커진다. 분할 12의 프로세스 CPU 시간은 분할 11보다 작지만, 분할 1의 3.23배(14,318.8 ÷ 4,434.4)다. 두 분할이 실행한 검사 횟수는 같으므로(3절), 늘어난 프로세스 CPU 시간은 같은 횟수의 검사를 실행하는 데 추가로 쓴 시간이다.

## 3. 분할을 늘려도 검사 횟수는 같은데 워커 CPU 시간의 합은 3.26배가 됐다

## 4. CPU 클럭 하락은 검사 1회 시간이 늘어난 주된 원인이 아니다

여러 코어가 동시에 사용되면 클럭이 내려가고, 클럭이 내려가면 같은 코드가 같은 명령을 실행해도 실행 시간이 더 길어질 것이다. 그래서 CPU 클럭을 확인했다.

측정 방법은 다음과 같다.

- 운영체제의 성능 카운터로 실행 중의 클럭을 1초 간격으로 기록했다. 수집 명령은 PowerShell의 `typeperf "\Processor Information(*)\% Processor Performance" -si 1`이다.
- 기록한 클럭 값을 워커 스레드 개수별로 아래 두 표에 정리했다. 클럭 세 열은 클럭 측정에서, 검사 1회 평균 시간 열은 상세 기록 측정에서 나왔다. 두 측정은 서로 다른 회차다.

두 표의 열은 다음과 같다. 분할 1 행은 비교 대상이 없어 분할 1 대비 값 세 칸이 비어 있다.

- 클럭: 병렬 구간의 평균 클럭
- 떨어진 클럭: 분할 1의 클럭 − 그 행의 클럭
- 클럭 하락률: (분할 1의 클럭 − 그 행의 클럭) ÷ 분할 1의 클럭

## 5. 검사 1회 시간이 늘어난 원인은 편차 계산의 스트림이 검사마다 만드는 객체였고, 그 양은 호출 1회에 9.5GB였다

### 5.1 후보 제외 과정

원인은 후보를 하나씩 측정해 제외하는 방식으로 찾았다.

1. 늘어난 프로세스 CPU 시간이 어느 스레드에서 발생했는지 확인했다. 워커 스레드 12개에서 분할 1과 분할 12를 비교하면(상세 기록 측정), 늘어난 프로세스 CPU 시간 9,884.4ms 중 99.8%인 9,865.6ms가 워커 CPU 시간의 증가분이다. GC 시간, main 스레드도 워커 스레드도 아닌 스레드의 CPU 시간, 말단 작업마다 팀 배정을 복사하는 시간도 측정했고, 어느 것도 늘어난 시간을 설명할 크기가 아니었다.
2. 늘어난 시간은 워커 스레드의 대기 시간도 아니다. 워커 스레드가 검사 반복문을 실행하는 동안 흐른 경과 시간의 90%에서 98%는 코어에서 실제로 실행된 CPU 시간이다(상세 기록 측정).
3. 3절에서 본 것처럼 호출 1회의 검사 횟수 855,000회와, 합 편차를 보고 거르는 필터를 통과한 횟수 352,485회는 모든 분할에서 같다.

그래서 남는 설명은 검사 1회에 걸리는 시간 자체가 늘었다는 것이다. 2.2절에서 분할을 늘릴 때 경과 시간 감소량이 급격히 작아진 것도 검사 1회에 걸리는 시간이 늘었기 때문이다.

검사 1회 평균 시간을 결정하는 것은 워커 스레드 개수가 아니라, 그 순간 실제로 동시에 실행되는 말단 작업 개수다. 4절 두 표에서 분할 2부터 6까지는 워커 스레드 6개와 12개의 검사 1회 평균 시간 차이가 2% 안이다. 동시에 실행되는 말단 작업이 6개가 될 때까지는 하나 늘 때마다 검사 1회 평균 시간이 약 1.2배씩 커졌고, 6개에서 12개로 늘 때는 1.467배가 됐다. 그 결과 워커 스레드 12개에서 분할 1의 5,192ns가 분할 12에서 18,425ns로 3.55배가 됐다(상세 기록 측정).

검사 1회 시간의 99% 안팎은 팀 사이의 합 편차를 구하는 계산과 분포 편차를 구하는 계산이 쓴다(상세 기록 측정). 두 계산은 자바 스트림으로 합계와 평균을 구하는데, 스트림은 만들 때마다 객체가 생긴다. 같은 설정에서 스트림 구현의 총 할당량에서 for문 구현의 총 할당량을 빼면 두 계산이 할당하는 양이 나오고, 그 값은 호출 1회에 9.52GB였다(for문 대조 측정).

검사 1회는 분할과 상관없이 같은 코드에 같은 입력으로 같은 횟수만큼 실행되므로, 실행하는 명령어 개수는 같다. 그런데 검사 1회 시간이 늘었으므로 명령어 하나의 실행 시간이 늘어난 것이고, 그 후보는 CPU 클럭과 두 편차 계산이 검사마다 만드는 스트림 객체 두 가지였다. 클럭은 4절에서 제외됐으므로 남은 후보는 스트림 객체다. 이 객체가 실제 원인인지는 객체를 없앤 뒤 다시 측정하면 확인할 수 있다.

- 스트림 구현이 호출 1회에 할당한 양은 워커 스레드 6개 설정의 총 할당량 9,521.3MB이고, for문 구현에서는 3.46MB다.

둘째, 동시에 실행되는 말단 작업이 늘 때마다 검사 1회 시간과 워커 CPU 시간이 커지던 현상이 for문 구현에서는 사라졌다.

- 워커 스레드를 6개에서 12개로 늘리면 스트림 구현은 워커 CPU 시간이 커지는데, for문 구현은 그대로다.

### 5.3 편차 계산 1회 평균 시간

아래 표는 두 구현에서 합 편차 계산과 분포 편차 계산이 각각 1회에 쓴 시간이다. 값은 위 두 표와 같은 실행(스트림 분할 36 실행, for문 분할 36 실행)의 상세 기록에서 구했다. 분포 편차 계산은 합 편차를 보고 거르는 필터를 통과한 검사에서만 실행된다.

| 구현 | 워커 스레드 개수 | 분할 개수 | 합 편차 계산 1회 평균 시간(ns) | 분포 편차 계산 1회 평균 시간(ns) |
|---|---:|---:|---:|---:|
| 스트림 | 6 | 36 | 7,310 | 14,806 |
| 스트림 | 12 | 36 | 9,003 | 18,281 |
| for문 | 6 | 36 | 1,387 | 3,200 |
| for문 | 12 | 36 | 1,435 | 3,284 |

워커 스레드를 6개에서 12개로 늘릴 때 스트림 구현은 두 편차 계산의 1회 평균 시간이 커지는데, for문 구현은 거의 그대로다.

5.2절에서 워커 스레드 6개의 분할 1 대비 분할 6의 검사 1회 평균 시간 배수는 스트림 구현이 2.58배, for문 구현이 1.02배였다. 따라서 동시에 실행되는 말단 작업이 6개가 될 때까지 하나 늘 때마다 검사 1회를 약 1.2배씩 느리게 만들던 원인은 스트림이 검사마다 만드는 객체다.

동시에 실행되는 말단 작업이 6개에서 12개로 늘어나는 구간은 물리 코어 하나를 논리 프로세서 두 개가 함께 쓰는 구간이어서, 이 구간의 증가는 for문 구현에서도 나타날 것으로 예상했다. 그런데 워커 스레드 12개에서 분할 6 대비 분할 12의 검사 1회 평균 시간 배수는 스트림 구현이 1.467배(12,563ns에서 18,425ns), for문 구현이 1.035배(2,733ns에서 2,828ns, for문 전체 분할 실행)로, for문 구현에서는 이 증가가 거의 나타나지 않았다.

## 6. 맞바꾼 두 팀의 합과 제곱합만 다시 계산하는 증분 재계산으로 편차 계산 1회 시간이 수십 ns로 줄었다

### 6.1 증분 재계산 방식

5절에서 검사 1회 평균 시간이 늘어난 원인은 스트림이 검사마다 만드는 객체라는 것을 확인했다. 그래서 다음 작업은 편차 계산에서 스트림 객체가 생기지 않도록 계산 방식을 바꾸는 것이다.

원인 확인에 쓴 for문 구현은 객체를 만들지 않지만, 값이 바뀌지 않은 팀까지 다시 계산한다. 교환 하나를 검사할 때마다 팀 20개 전체의 합과 분산을 처음부터 다시 계산하는데, 한 명씩 맞바꿔서 값이 바뀌는 팀은 2팀뿐이다. 나머지 18팀에 대한 계산은 매번 같은 값을 다시 구하는 작업이다.

증분 재계산은 값이 바뀌지 않은 18팀의 재계산을 없앤다.

1. 스캔을 시작할 때 팀별 합, 팀별 제곱합, 팀별 인원 수를 배열 세 개로 한 번 계산해 둔다.
2. 검사에서는 맞바꾼 두 팀의 합과 제곱합만 갱신한 뒤, 그 배열로 편차를 계산한다.
3. 배정이 좋아졌는지 확인한 뒤 두 팀의 합과 제곱합을 교환 전 값으로 되돌린다.
4. 말단 작업은 팀 배정 복사본을 만들 때 합 배열과 제곱합 배열도 함께 복사한다. 팀별 인원 수 배열은 검사 중에 값이 변하지 않으므로 복사하지 않고 함께 읽는다.

순차 구현도 같은 방식으로 바꿨다.

### 6.2 증분 재계산 측정 결과

증분 재계산 구현의 성능은 증분 재계산 측정으로 확인했다. 설정은 순차 실행과, 워커 스레드 6개와 12개 각각에 분할 1부터 12까지와 18, 24, 36이다. 이 절의 값은 모두 테스트 프로그램의 콘솔 로그(설정별 표 행과 상세 기록 줄)에서 나왔다.

아래 표는 5.2절의 두 구현 표와 같은 구성이고, 증분 재계산 구현을 분할 36에서 측정한 값이다.

- 실행: 증분 재계산 측정의 여섯 실행 중 콘솔 로그 이름 끝이 20260814_1045인 실행의 값이다.
- 워커 하나의 검사 반복문 시간: 5회 측정 전체의 범위로 적었다.

| 값(호출 1회당, 측정 5회 평균) | 순차 | 워커 스레드 6개, 분할 36 | 워커 스레드 12개, 분할 36 |

※ 표의 값

- 총 할당량: main 할당량 + 워커 할당량 + 기타 할당량

  - 테스트 프로그램은 호출 직전과 직후에 main 스레드에서 모든 스레드의 CPU 시간과 할당량을 읽는다.
  - main 할당량이 커지는 것은, 측정 중에는 풀을 닫지 않아 이전 호출의 워커 스레드가 종료되지 않고 남아서, 뒤에 측정한 설정일수록 main 스레드가 읽는 스레드 개수가 많아지기 때문으로 보인다.
  - JFR 재측정의 main 스레드 표본에도 엔진의 검사 코드는 없었다.

편차 계산 시간이 얼마나 줄었는지는 편차 계산 1회 평균 시간으로 확인한다. 표에는 7.2절의 JFR 재측정과 같은 설정인 워커 스레드 6개, 분할 36의 값만 적는다.

- for문 행: 5.3절 표의 값이다. 5.3절 표에는 검사 1회 평균 시간이 없어 빈칸이다.
- 증분 재계산 행: 위 표와 같은 실행의 값이다.
- 분포 편차 계산: 합 편차를 보고 거르는 필터를 통과한 검사에서만 실행된다.

for문 구현에서 1,387ns와 3,200ns이던 합 편차 계산과 분포 편차 계산의 1회 평균 시간이 증분 재계산 구현에서 49ns와 82ns가 됐다. 두 값은 계측 코드가 다른 측정에서 나왔으므로 규모로만 비교하면, 편차 계산 1회 시간이 수천 ns에서 수십 ns로 줄었다.

편차 계산이 만들던 객체가 실제로 사라졌는지, 병렬 실행에서 할당이 어디서 나오는지는 실행 기록기로 다시 확인했다. 이 내용은 7절에서 다룬다.

## 7. 스트림 구현의 할당 9.5GB는 스트림을 만드는 세 문장에서 나왔고, 증분 재계산 구현의 워커 할당 4.0MB는 대부분 말단 작업마다 만드는 복사본에서 나왔다

### 7.1 스트림 구현이 호출 1회에 할당하는 9.5GB는 세 문장에서 나온다

스트림 구현이 호출 1회에 할당하던 9.52GB가 코드의 어느 문장에서 나오는지는 스레드별 할당량 계측으로 알 수 없다. 이 계측은 스레드마다 할당한 바이트의 누적값만 읽기 때문이다. 그래서 실행 기록기(JFR)를 켜고 스트림 구현을 워커 스레드 6개, 분할 36으로 한 번 더 실행했다. 이것이 JFR 측정이다.

두 편차 계산이 스트림을 만드는 문장은 세 개다. 합 편차 계산에서 팀별 합계를 구하는 문장 하나, 분포 편차 계산에서 팀별 평균을 구하는 문장과 그 평균으로 팀별 분산을 구하는 문장 두 개다.

| 할당 위치 | 객체 클래스 | 바이트 비중(%) |
|---|---|---:|
| 합계 문장 (합 편차 계산) | 스트림 객체와 double[] | 52.3 |
| 평균 문장 (분포 편차 계산) | 스트림 객체와 double[] | 25.2 |
| 분산 문장 (분포 편차 계산) | 스트림 객체와 double[]와 mean을 담는 캡처 람다 | 22.5 |
| 세 문장 밖 | 작업 객체 등 | 0.03 |

※ 표의 값

- 바이트 비중: 같은 기록에 앞서 실행한 순차 실행도 들어 있어, 순차 실행과 병렬 실행의 표본을 합친 값이다.
- 병렬 실행의 워커 스레드 표본만 보면 합계 문장 50.8%, 평균 문장 25.2%, 분산 문장 24.0%다.

세 문장이 할당하는 것은 스트림을 구성하고 합계와 평균을 계산하는 데 필요한 객체들이다. 할당 표본 무게(표본마다 기록된, 그 표본이 대표하는 바이트 수의 합) 기준으로 자바 표준 라이브러리 클래스 여덟 개가 98.03%이고, 분산 문장에서 mean을 담는 캡처 람다가 1.94%다.

### 7.2 증분 재계산 구현의 워커 할당 4.0MB는 대부분 말단 작업마다 만드는 복사본에서 나온다

증분 재계산으로 바꾼 뒤에도 병렬 실행은 호출 1회에 4.4MB를 새로 할당한다(증분 재계산 측정, 워커 스레드 6개와 분할 36의 총 할당량). 그중 워커 스레드 할당이 4.01MB, main 스레드 할당이 0.42MB다. main 스레드 할당은 테스트 프로그램이 만든 것으로 보이므로, 워커 스레드 할당이 어디서 나오는지를 실행 기록기로 확인했다. 이것이 JFR 재측정이고, 설정은 같은 워커 스레드 6개, 분할 36이다.

워커 스레드 할당의 99.56%가 ImproveTask의 compute() 안 다섯 곳에서 나온다. 그중 하위 작업 객체를 만드는 곳은 구간을 나누는 단계에서, 나머지 네 곳은 말단 작업에서 실행된다. 아래 비중은 워커 스레드 표본 무게 기준이다.

| 할당 위치 | 객체 클래스 | 바이트 비중(%) |
|---|---|---:|
| 팀 배정 복사본 | Object[]와 ArrayList | 69.63 |
| 합과 제곱합 배열의 복사본 | double[] | 14.44 |
| 계측용 기록 문자열 (구성 분석에서 제외) | byte[] 등 | 7.53 |
| 분할 단계의 하위 작업 객체 | ImproveTask | 6.93 |
| 말단 작업의 결과 객체 | ImproveTaskResult | 1.03 |
| 다섯 곳 밖(fork, join, 팀 목록 순회 등) | ForkJoinTask$Aux 등 | 0.43 |

※ 계측용 기록 문자열은 엔진이 아니라 계측 코드가 만드는 것이어서 구성 분석에서 뺐다.

표에서 비중이 가장 큰 두 항목은 복사본 할당이다.

- 말단 작업마다 팀 배정을 복사하는 것(바깥 리스트와 팀별 리스트를 새로 만든다)이 69.63%로 가장 크다.
- 증분 재계산에서 새로 만든 팀별 합 배열과 제곱합 배열을 말단 작업마다 복사하는 것이 14.44%로 그다음이다.

워커 스레드 표본에는 스트림 계열 클래스가 하나도 없다. 편차 계산이 검사마다 만들던 스트림 객체가 실제로 사라졌다는 뜻이다.

## 8. 결론: 병렬 효율을 결정한 것은 코어 개수가 아니라 편차 계산의 스트림이 검사마다 만드는 객체였다

### 8.1 원인

fork-join 병렬화 배율은 물리 코어 6개인 환경에서 벤치마크 도구(JMH)로 측정했을 때 인원 200명과 300명 모두 2.42배였다. 원인은 유휴 코어가 아니었다. 동시에 실행되는 말단 작업이 늘수록 검사 1회에 걸리는 시간 자체가 커져서, 워커 스레드 12개의 분할 12에서는 검사 1회 평균 시간이 분할 1의 3.55배가 됐다(상세 기록 측정).

검사 1회 시간이 늘어난 원인은 GC도 CPU 클럭도 아니다. 원인은 두 편차 계산이 검사마다 만드는 객체, 즉 호출 1회에 9.5GB에 이르는 스트림 객체였다. 객체를 만들지 않는 for문으로 바꾸자 동시에 실행되는 말단 작업이 6개가 될 때까지 검사 1회가 약 1.2배씩 느려지던 현상이 사라져, 그 구간의 원인이 확정됐다.

### 8.2 개선 결과

빨라진 정도는 아래 표와 같다.

| 값(호출 1회당) | 스트림 구현 | 증분 재계산 |
|---|---:|---:|
| 순차 경과 시간(improve() 호출 1회, ms) | 4,137.2 | 59.1 |
| 병렬 총 할당량(MB, 워커 스레드 6개, 분할 36) | 9,521.3 | 4.44 |

※ 값의 출처

- 스트림 구현의 순차 경과 시간: 상세 기록 측정
- 스트림 구현의 병렬 총 할당량: for문 대조 측정의 스트림 분할 36 실행. 측정 순번 1을 제외했다.
- 증분 재계산의 순차 경과 시간: 증분 재계산 측정의 여섯 실행 평균
- 증분 재계산의 병렬 총 할당량: 증분 재계산 측정의 여섯 실행 중앙값

두 구현의 값은 계측 코드가 서로 다른 측정에서 나왔으므로, 정밀한 배수 대신 규모로 비교한다. 순차 경과 시간은 4,000ms 규모에서 60ms 규모가 됐고, 호출 1회에 할당하는 객체는 9.5GB에서 4.4MB가 됐다.

증분 재계산으로 순차 실행이 빨라진 뒤, 순차 대비 병렬 배율은 for문 구현보다 오히려 작아졌다. 증분 재계산에서 가장 빠른 병렬 설정의 배율은 실행에 따라 2.23에서 2.78이고, for문 구현에서 가장 빠른 설정의 배율은 8.84다(for문 대조 측정). 스트림 구현에서 가장 빠른 설정의 배율 2.76(상세 기록 측정)은 증분 재계산의 범위 안에 있다.

여섯 실행 중 다섯 번은 워커 스레드 12개에 분할 9가 가장 빨랐고, 이 설정의 경과 시간 여섯 실행 평균은 24.6ms다. 엔진의 운영 경로는 이 측정을 근거로 워커 스레드를 논리 프로세서 수로, 분할을 9로 설정한다.

이 사례에서 병렬 효율을 결정한 것은 코어 개수가 아니라 편차 계산의 스트림이 검사마다 만드는 객체였다. 검사마다 만드는 객체를 없애자 순차 실행과 병렬 실행이 함께 빨라졌고, 경과 시간 단축의 대부분은 병렬화가 아니라 편차 계산 방식을 바꾼 데서 나왔다.

※ 여섯 실행에 넣지 않은 실행

- 증분 재계산 측정의 폴더(부록의 7번 폴더)에는 같은 조건의 실행이 하나 더 있다(콘솔 로그 이름 끝이 20_57인 실행).
