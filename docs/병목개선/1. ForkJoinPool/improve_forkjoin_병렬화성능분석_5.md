# improve() 증분 재계산 JFR 할당 분석 보고서 (1회차)

|---|---|
| 분석 대상 | TeamFormationEngine의 증분 재계산 구현이 실행 중 만드는 객체(메모리 할당) |
| 기록 일시 | 2026-08-14 14:00 (기록 길이 약 11초) |
| 기록 조건 | 인원 200명, 정원 10명, 시드 42, 허용폭 10%, greedy 시작 / 워밍업 100회, 측정 5회 / 풀 병렬도 6, 분할 36 |

## 1. 개요

두 편차 메서드의 스트림을 제거하고 평가 경로를 증분 재계산으로 전환한 뒤 처음 수행한 할당 분석이다.

improve()를 한 번 호출할 때 워커 스레드들이 새로 만드는 객체의 총 크기는, 구현마다 프로브의 카운터로 측정해 두었다. 두 값 모두 측정 5회를 평균한 것이다(출처: `1_2. JFR_증분재계산_병렬도6_분할36_ConsoleLog_20260814_14_03.txt`, `콘솔로그_for문전환_합편차계산및팀편차재계산_1부터36전부재테스트_20260804_1845.txt`). 이 값이 for문 구현에서는 3,420,237바이트였는데, 증분 재계산 구현에서는 3,977,245바이트로 557,008바이트 늘었다.

이 보고서는 워커 할당이 어떤 클래스로 구성되며 엔진 코드의 몇 행에서 발생하는지 확인한다.

늘어난 557,008바이트의 출처 확인은 추가 재측정 없이 여기서 종료하기로 결정했다.

핵심 결과는 다음 세 가지다.

- 워커 할당은 전부 말단 작업(compute())의 다섯 개 코드 위치에서 발생한다.
- 스트림 구현에서 총 할당의 약 39%를 차지하던 ReferencePipeline 계열 클래스는 평가 경로에서 표본 0개로 사라졌다.

## 2. 분석 방법

동일한 기록 파일을 두 방법으로 읽고 결과를 대조했다.

1. **JMC 화면 확인.** Memory 화면에서 클래스별로 스택 트레이스를 펼쳐, 할당이 발생한 엔진 코드의 행 번호를 확인했다.
2. **표본 집계.** `jfr print --events jdk.ObjectAllocationSample --stack-depth 64`로 추출한 표본 1,326개를, 스택에서 가장 안쪽에 있는 엔진 프레임의 행 번호 기준으로 분류했다.

두 방법에서 행 번호와 비중이 모두 일치했다.

수치 판독 기준은 다음과 같다.

- **비중**은 표본 무게(Sample Weight) 기준으로 읽는다. 표본 개수는 스레드별로 편향될 수 있기 때문이다.
- **절대량**은 프로브의 카운터 실측(getThreadAllocatedBytes)을 기준으로 한다. 이 기록은 표본 무게 합계가 실제 총량의 37%에 그쳐 절대량 지표로 쓰기 어렵기 때문이다.

## 3. 워커 할당의 구성과 발생 위치

### 3.1 클래스별 집계

워커 스레드의 표본은 전부 말단 작업의 compute() 안에서 발생했다.

클래스는 여섯 개, 발생 위치는 다섯 곳이다.

| 클래스 | Alloc Total(MiB) | 비중(%) | 발생 행 | 용도 |
|---|---:|---:|---|---|
| java.lang.Object[] | 76.5 | 48.9 | 1160, 1158 | 팀 배정 복사본의 내부 배열 |
| java.util.ArrayList | 30.5 | 19.5 | 1160 (1158 소량) | 팀 배정 복사본의 리스트 객체 |
| double[] | 21.9 | 14.0 | 1165, 1166 | 합·제곱합 배열의 복사본 |
| ImproveTask | 10.5 | 6.7 | 1121, 1124 | 분할 단계의 하위 작업 객체 |
| byte[] | 9.3 | 6.0 | 1292 | 계측용 문자열 (분석 제외, 3.3 참조) |
| ImproveTaskResult | 1.6 | 1.0 | 1174 | 말단의 결과 객체 |

### 3.2 발생 위치별 상세

**(1) 팀 배정 복사본 (java.lang.Object[] 48.9% + java.util.ArrayList 19.5%): 1158~1161행**

```java
1158:  List<List<Member>> local = new ArrayList<>(teams.size());
1159:  for (List<Member> team : teams) {
1160:      local.add(new ArrayList<>(team));
1161:  }
```

여러 워커가 같은 배정을 동시에 수정하지 않도록 말단마다 팀 배정 전체를 깊은 복사하는 코드다.

1160행의 `new ArrayList<>(team)` 한 줄이 리스트 객체(ArrayList)와 그 내부 배열(Object[])을 함께 생성하므로, 표의 상위 두 클래스는 같은 코드에서 발생한 것이다.

Object[]의 스택 트레이스 기준 세부 구성은 다음과 같다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 무게(바이트) | 비중(%) |
|---|---|---|---:|---:|
| 1160 | 안쪽 팀 리스트 복사 | Arrays.copyOf | 70,502,936 | 87.9 |
| 1158 | 바깥 리스트 생성 | ArrayList 생성자 | 7,628,368 | 9.5 |
| 기타 | JVM 내부 코드(엔진 무관) | Object.clone 등 | 2,043,760 | 2.6 |

행별 호출 경로는 다음과 같다.

각 경로의 마지막 메서드가 JMC 스택 트레이스의 최상위 프레임이다.

- 1160행: `new ArrayList<>(team)` → `ArrayList.<init>(Collection)` 생성자 → toArray() → **Arrays.copyOf()** 에서 배열 생성
- 1158행: `new ArrayList<>(teams.size())` → **`ArrayList.<init>(int)` 생성자**
- 기타: JVM 내부 코드(java.lang.invoke 계열, **Object.clone** 등). 엔진 코드와 무관

**(2) 합·제곱합 배열의 복사본 (double[] 14.0%): 1165~1167행**

```java
1165:  double[] localSum = teamSum.clone();
1166:  double[] localSqSum = teamSqSum.clone();
1167:  int[] localSize = teamSize;            // 값이 변하지 않으므로 복사하지 않음
```

증분 재계산 전환으로 새로 생긴 코드다.

합과 제곱합은 평가 중에 수정했다가 되돌리는 값이므로 말단마다 복사본을 가진다.

double[]의 스택 트레이스 기준 세부 구성은 다음과 같다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 표본(개) | 비중(%) |
|---|---|---|---:|---:|
| 1165 | teamSum 복사 | 없음 (해당 행의 clone이 직접 할당) | 107 | 54.9 |
| 1166 | teamSqSum 복사 | 없음 (해당 행의 clone이 직접 할당) | 73 | 37.4 |
| 기타 | 위 두 행과 동일 | Object.clone | 15 | 7.7 |

행별 호출 경로는 다음과 같다.

- 1165행: `teamSum.clone()` 이 그 행에서 직접 배열을 생성
- 1166행: `teamSqSum.clone()` 이 그 행에서 직접 배열을 생성
- 기타: 최상위 프레임이 **Object.clone()** 으로 기록된 표본. 스택을 펼치면 1165행과 1166행으로 이어짐

두 배열은 크기가 같으므로 비중이 절반씩에 가까운 것이 코드와 일치한다.

복사하지 않는 int[]는 화면에 나타나지 않았다.

**(3) 분할 단계의 하위 작업 객체 (ImproveTask 6.7%): 1121행, 1124행**

```java
1121:  ImproveTask leftTask  = new ImproveTask(teams, pairA, pairB, lo,  mid, ...);
1124:  ImproveTask rightTask = new ImproveTask(teams, pairA, pairB, mid, hi, ...);
```

작업을 반씩 나눌 때마다 하위 작업 두 개를 생성하는 코드다.

ImproveTask의 스택 트레이스 기준 세부 구성은 다음과 같다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 표본(개) | 비중(%) |
|---|---|---|---:|---:|
| 1121 | leftTask 생성 | 없음 (해당 행의 new가 직접 할당) | 52 | 53.6 |
| 1124 | rightTask 생성 | 없음 (해당 행의 new가 직접 할당) | 45 | 46.4 |

분할할 때마다 두 객체를 하나씩 만들므로 비중이 절반씩에 가까운 것이 코드와 일치한다.

이 두 행 외의 생성 위치는 없었다.

**(4) 말단의 결과 객체 (ImproveTaskResult 1.0%): 1174행**

```java
1174:  ImproveTaskResult improveTaskResult = new ImproveTaskResult();
```

말단마다 결과 객체를 하나 생성한다.

ImproveTaskResult의 스택 트레이스 기준 세부 구성은 다음과 같다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 표본(개) | 비중(%) |
|---|---|---|---:|---:|
| 1174 | 결과 객체 생성 | 없음 (해당 행의 new가 직접 할당) | 20 | 100 |

**(5) 계측용 문자열 (byte[] 6.0%, 분석 제외): 1292행**

```java
1291:  if (dlogOn) {
1292:      detailLog.add("IMPLOG,leaf," + Thread.currentThread().getName() + ... );
```

상세 기록(IMPLOG) 한 건을 문자열로 조립해 버퍼에 넣는 코드다.

byte[] 표본 79개 중 75개가 이 행에서 발생했다.

엔진 로직이 아니라 계측이 만드는 할당이므로 구성 분석에서 제외한다.

### 3.3 스트림 클래스 제거 확인

스트림 구현 회차에서 총 할당의 약 39%를 차지했던 ReferencePipeline$Head와 ReferencePipeline$6은 이번 기록에서 표본 0개다.
