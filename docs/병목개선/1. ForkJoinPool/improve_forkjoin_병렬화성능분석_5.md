## 1. 개요

두 편차 계산 메서드에서 스트림을 제거하고, 평가마다 맞바꾼 두 팀의 합과 제곱합만 갱신하는 증분 재계산으로 바꾼 뒤 처음 수행한 할당 분석이다.

improve()를 한 번 호출할 때 워커 스레드들이 새로 만드는 객체의 총 크기(워커 할당량)는 구현마다 테스트 프로그램이 스레드별 할당 바이트를 읽어 측정했다. 아래 표의 두 구현 워커 할당량은 모두 측정 5회의 평균이다.

| 구현 | 워커 할당량(바이트) | 출처 |
|---|---:|---|
| for문 구현 | 3,420,237 | `콘솔로그_for문전환_합편차계산및팀편차재계산_1부터36전부재테스트_20260804_1845.txt` |
| 증분 재계산 구현 | 3,977,245 | `1_2. JFR_증분재계산_병렬도6_분할36_ConsoleLog_20260814_14_03.txt` |
| 차이(증분 재계산 구현 − for문 구현) | 557,008 | |

이 보고서는 워커 할당이 어떤 클래스로 구성되고, 엔진 코드의 몇 행에서 발생하는지 확인한다.

주요 결과는 다음과 같다.

- 워커 스레드 할당의 99.6%(표본 무게 기준)가 ImproveTask의 compute()에 있는 다섯 개 코드 위치에서 발생한다.
- 스트림 구현의 JFR 측정에서 표본 무게의 약 39%를 차지하던 ReferencePipeline$Head와 ReferencePipeline$6은 이번 기록에서 표본이 0개다.

## 2. 분석 방법

같은 기록 파일을 두 가지 방법으로 읽고 결과를 대조했다.

1. **JMC 화면 확인.** Memory 화면에서 클래스별로 스택 트레이스를 펼쳐, 할당이 발생한 엔진 코드의 행 번호를 확인했다.
2. **표본 집계.** `jfr print --events jdk.ObjectAllocationSample --stack-depth 64`로 추출한 표본 1,326개를, 스택에서 가장 안쪽에 있는 엔진 프레임의 행 번호 기준으로 분류했다.

두 방법의 결과를 비교하면 다음과 같다.

- 행 번호: 두 방법이 일치했다.
- 비중: Object[]의 세부 구성에서 차이가 있었다. JMC 화면은 표본을 최상위 프레임(할당이 실제로 일어난 JDK 메서드와 행)으로 묶기 때문에, 1160행에서 나온 표본 일부가 다른 묶음으로 보였다.

이 보고서의 Object[] 세부 표는 표본 집계 값을 쓴다. 두 방법의 값 차이는 3.2절 (1)의 ※ 주석에 있다.

수치는 다음 기준으로 읽는다.

| 수치 | 기준 | 이유 |
|---|---|---|
| 비중 | 표본 무게(Sample Weight) | 표본 개수는 스레드별로 편향될 수 있다 |
| 절대량 | 테스트 프로그램이 읽은 스레드별 할당 바이트(getThreadAllocatedBytes) | 이 기록은 표본 무게 합계가 실제 총량의 37%에 그쳐 절대량 지표로 쓰기 어렵다 |

※ 표별 값의 기준

- 3.1절 클래스 표의 Alloc Total과 전체 스레드 비중: JMC 화면의 무게(Sample Weight) 기준이다.
- 3.1절 클래스 표의 워커 스레드 비중과 3.2절 (1)의 Object[] 세부 표: 표본 집계의 무게 기준이다.
- 3.2절 (2)~(4)의 double[], ImproveTask, ImproveTaskResult 세부 표: 표본 개수(Samples) 기준이다.
- 어느 기준으로 읽어도 행 번호는 같다.

## 3. 워커 할당의 구성과 발생 위치

### 3.1 클래스별 집계

워커 스레드 표본 1,308개의 구성은 다음과 같다.

- 스택 기준: 1,306개는 스택에 ImproveTask의 compute()가 있다. 나머지 2개는 스택에 엔진 코드가 없는 String이다.
- 클래스 기준: 워커 표본의 클래스는 16개이고, 아래 표의 여섯 클래스가 워커 표본 무게의 97.4%를 차지한다.
- 발생 위치 기준: 워커 표본 무게의 99.6%가 3.2절의 다섯 곳에서 나온다. 나머지 0.4%는 fork(1128행), join(1130행), 팀 목록 순회(1159행)에서 만든 객체와 엔진 코드가 없는 표본이다.

| 클래스 | Alloc Total(MiB, 전체 스레드) | 비중(%, 전체 스레드) | 비중(%, 워커 스레드) | 발생 행 | 용도 |
|---|---:|---:|---:|---|---|
| java.lang.Object[] | 76.5 | 48.9 | 49.5 | 1160, 1158 | 팀 배정 복사본의 내부 배열 |
| java.util.ArrayList | 30.5 | 19.5 | 20.2 | 1160 (1158 소량) | 팀 배정 복사본의 리스트 객체 |
| double[] | 21.9 | 14.0 | 14.4 | 1165, 1166 | 합·제곱합 배열의 복사본 |
| ImproveTask | 10.5 | 6.7 | 6.9 | 1121, 1124 | 분할 단계의 하위 작업 객체 |
| byte[] | 9.3 | 6.0 | 5.4 | 1292 | 계측용 문자열 (분석 제외, 3.2의 (5) 참조) |
| ImproveTaskResult | 1.6 | 1.0 | 1.0 | 1174 | 말단 작업의 결과 객체 |

※ 표의 값

- Alloc Total과 비중(%, 전체 스레드): JMC 클래스 표의 값이다. main 스레드 표본을 포함한다(예: Object[]에 main 스레드 표본 1.55MiB 포함).
- 비중(%, 워커 스레드): 표본 집계로 구했다.

### 3.2 발생 위치별 상세

#### (1) 팀 배정 복사본 (java.lang.Object[] 48.9% + java.util.ArrayList 19.5%): 1158~1161행

```java
1158:  List<List<Member>> local = new ArrayList<>(teams.size());
1159:  for (List<Member> team : teams) {
1160:      local.add(new ArrayList<>(team));
1161:  }
```

여러 워커 스레드가 같은 배정을 동시에 수정하지 않도록, 말단 작업마다 팀 배정을 복사하는 코드다. 바깥 리스트와 팀별 리스트를 새로 만들고, Member 객체는 새로 만들지 않고 원래 객체를 그대로 가리킨다.

1160행의 `new ArrayList<>(team)` 한 줄이 리스트 객체(ArrayList)와 그 내부 배열(Object[])을 함께 생성한다. 따라서 표의 상위 두 클래스는 같은 코드에서 발생한 것이다.

Object[]의 세부 구성은 다음과 같다. 표본 집계로, 스택에서 가장 안쪽에 있는 엔진 프레임의 행을 기준으로 나눴다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 무게(바이트) | 비중(%) |
|---|---|---|---:|---:|
| 1160 | 안쪽 팀 리스트 복사 | Arrays.copyOf | 70,921,776 | 88.5 |
| 1158 | 바깥 리스트 생성 | ArrayList 생성자 | 7,628,368 | 9.5 |
| 기타 | main 스레드의 JDK 내부 코드(엔진 무관) | Object.clone | 1,624,920 | 2.0 |

※ JMC 화면에서는 1160행 표본 3개(418,840바이트)가 최상위 프레임이 다른 묶음으로 표시되었다. 그래서 JMC 화면의 값은 위 표의 표본 집계 값과 다음과 같이 다르다.

| 행 | 표본 집계 무게(바이트) | 표본 집계 비중(%) | JMC 화면 무게(바이트) | JMC 화면 비중(%) |
|---|---:|---:|---:|---:|
| 1160 | 70,921,776 | 88.5 | 70,502,936 | 87.9 |
| 기타 | 1,624,920 | 2.0 | 2,043,760 | 2.6 |

행별 호출 경로는 다음과 같다. 각 경로의 마지막 메서드가 JMC 스택 트레이스의 최상위 프레임이다.

- 1160행: `new ArrayList<>(team)` → `ArrayList.<init>(Collection)` 생성자 → toArray() → **Arrays.copyOf()** 에서 배열 생성
- 1158행: `new ArrayList<>(teams.size())` → **`ArrayList.<init>(int)` 생성자**
- 기타: main 스레드에서 람다 폼을 만드는 JDK 내부 코드(java.lang.invoke 계열)의 **Object.clone**. 엔진 코드와 무관

#### (2) 합·제곱합 배열의 복사본 (double[] 14.0%): 1165~1167행

```java
1165:  double[] localSum = teamSum.clone();
1166:  double[] localSqSum = teamSqSum.clone();
1167:  int[] localSize = teamSize;
```

증분 재계산으로 바꾸면서 새로 생긴 코드다. 합과 제곱합은 평가 중에 수정했다가 되돌리는 값이므로, 말단 작업마다 복사본을 만든다. 팀 인원 배열(teamSize)은 값이 변하지 않아 복사하지 않고 원본을 함께 읽는다(코드 1163~1164행 주석).

double[]의 스택 트레이스 기준 세부 구성은 다음과 같다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 표본(개) | 비중(%) |
|---|---|---|---:|---:|
| 1165 | teamSum 복사 | 없음 (해당 행의 clone이 직접 할당) | 107 | 54.9 |
| 1166 | teamSqSum 복사 | 없음 (해당 행의 clone이 직접 할당) | 73 | 37.4 |
| 기타 | 위 두 행과 동일 | Object.clone | 15 | 7.7 |

행별 호출 경로는 다음과 같다.

- 1165행: `teamSum.clone()`이 그 행에서 직접 배열을 생성
- 1166행: `teamSqSum.clone()`이 그 행에서 직접 배열을 생성
- 기타: 최상위 프레임이 **Object.clone()** 으로 기록된 표본. 스택을 펼치면 1165행과 1166행으로 이어짐

1165행과 1166행은 크기가 같은 두 배열을 하나씩 복사하므로, 코드상 두 행의 할당량은 같다.

복사하지 않는 int[](teamSize)는 JMC 화면에 나타나지 않았다.

#### (3) 분할 단계의 하위 작업 객체 (ImproveTask 6.7%): 1121행, 1124행

```java
1121:  ImproveTask leftTask  = new ImproveTask(teams, pairA, pairB, lo,  mid, ...);
1124:  ImproveTask rightTask = new ImproveTask(teams, pairA, pairB, mid, hi, ...);
```

작업을 반씩 나눌 때마다 하위 작업 두 개를 생성하는 코드다.

ImproveTask의 스택 트레이스 기준 세부 구성은 다음과 같다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 표본(개) | 비중(%) |
|---|---|---|---:|---:|
| 1121 | leftTask 생성 | 없음 (해당 행의 new가 직접 할당) | 52 | 53.6 |
| 1124 | rightTask 생성 | 없음 (해당 행의 new가 직접 할당) | 45 | 46.4 |

분할할 때마다 leftTask와 rightTask를 하나씩 만들므로, 비중이 거의 절반씩으로 나뉜 것은 코드와 일치한다. 이 두 행 외의 생성 위치는 없었다.

#### (4) 말단 작업의 결과 객체 (ImproveTaskResult 1.0%): 1174행

```java
1174:  ImproveTaskResult improveTaskResult = new ImproveTaskResult();
```

말단 작업마다 결과 객체를 하나 생성한다.

ImproveTaskResult의 스택 트레이스 기준 세부 구성은 다음과 같다.

| 행 | 코드 | 할당이 실행되는 JDK 메서드 | 표본(개) | 비중(%) |
|---|---|---|---:|---:|
| 1174 | 결과 객체 생성 | 없음 (해당 행의 new가 직접 할당) | 20 | 100 |

#### (5) 계측용 문자열 (byte[] 6.0%, 분석 제외): 1292행

```java
1291:  if (dlogOn) {
1292:      detailLog.add("IMPLOG,leaf," + Thread.currentThread().getName() + ... );
```

상세 기록(IMPLOG) 한 건을 문자열로 조립해 버퍼에 넣는 코드다. byte[] 표본 79개 중 75개가 이 행에서 발생했다.

엔진 로직이 아니라 계측 코드가 만드는 할당이므로 구성 분석에서 제외한다.
