## 개요

팀 편성 엔진의 개선 알고리즘을 fork-join으로 병렬화했지만, 순차 실행 대비 배율이 인원 200명과 300명에서 모두 2.42배로 기대보다 훨씬 낮았다. 그 원인을 찾아 확정하기까지의 과정은 성능 분석 1편부터 4편까지 나눠 기록했다.

1편부터 5편과 최종 보고서의 제목과 다루는 내용, 이 문서들이 같은 뜻으로 쓰는 용어와 측정 기준은 0편 `improve_forkjoin_병렬화성능분석_0.md`에 있다.

이 문서에서 확인한 내용은 다음과 같다. 근거와 계산은 각 항목에 있다.

1. JMH로 인원을 20명에서 300명까지 바꿔 측정한 배율은 인원 200명과 300명에서 2.42배다(워커 스레드 12개). 물리 코어 6개로 기대한 6배에 못 미친다.
   - 배율: 순차 실행의 경과 시간 ÷ 병렬 실행의 경과 시간. 병렬 실행이 순차 실행보다 몇 배 빠른지를 나타낸다.
2. 같은 200명을 CPU 시간을 읽는 테스트 프로그램으로 측정하면, 병렬 실행은 순차 실행과 같은 팀 배정 결과를 내면서 프로세스 CPU 시간을 1.78배 썼다(워커 스레드 12개, 말단 작업 16개).
3. 병렬 실행 중 코어는 평균 7.85개가 사용되고 있었다. 배율을 제한한 것은 사용한 코어 개수가 아니라 순차 대비 CPU 효율이다.
4. 동시에 실행되는 말단 작업이 늘 때 증가한 프로세스 CPU 시간의 99.45%는 워커 스레드에서 발생했다.
5. 프로세스 CPU 시간과 경과 시간을 결정하는 것은 풀에 둔 워커 스레드 개수가 아니라, 실제로 동시에 실행되는 말단 작업 개수다.
6. 상세 기록 측정의 모든 병렬 설정에서 평가 횟수와 통과 횟수는 같다. 그런데 풀 병렬도 12에서 평가 1회 평균 시간은 분할 1의 5,192ns에서 분할 12의 18,425ns로 3.55배가 됐다.

## 1. 배율이 낮은 원인은 코어 부족이 아니다

병렬화의 목적은 실행 시간 단축이다. 그래서 구현을 마친 뒤 가장 먼저 순차 실행보다 얼마나 빨라졌는지를 측정했다. 이 실행이 0편 5절 회차 목록의 기준 측정이고, 이 절의 값은 모두 기준 측정에서 나왔다. 기준 측정은 도구가 다른 두 측정으로 이루어져 있다.

- 벤치마크 도구(JMH): 워커 스레드를 12개로 고정하고 인원을 20명에서 300명까지 바꿔 가며 순차 실행과 병렬 실행의 경과 시간을 측정했다. 배율은 이 측정에서 나온다.
- CPU 시간을 읽는 테스트 프로그램: 인원 120명과 200명에서 풀 병렬도(6, 12)와 workSize(12, 6)를 조합한 네 실행을 측정했다. workSize 12이면 말단 작업이 16개, workSize 6이면 32개다. CPU 시간은 이 측정에서 나온다.

인원을 바꾼 것은 기준 측정뿐이다. 다음 회차부터는 인원을 200명으로 고정하고 분할 개수와 풀 병렬도를 바꿔 가며 측정했다.

이 측정에서 설명이 필요한 값이 두 개 나왔다.

1. JMH로 측정한 순차 대비 배율이 인원 200명과 300명에서 모두 2.42배였다. 물리 코어 개수 6의 절반에도 못 미치는 값이다.
2. 테스트 프로그램으로 측정한 병렬 실행이 순차 실행과 같은 팀 배정 결과를 내면서 순차 실행의 1.78배에 해당하는 프로세스 CPU 시간을 썼다.

이 절에서는 배율과 프로세스 CPU 시간을 살펴보고, 먼저 배율이 낮은 원인이 코어를 충분히 사용하지 못한 데 있는지 확인한다.

### 1.1 배율은 인원 200명과 300명에서 모두 2.42배다

배율은 벤치마크 도구(JMH)로 측정한 순차 실행과 병렬 실행의 평균 경과 시간으로 계산했다.

측정 조건은 다음과 같다.

- 호출 1회는 개선 알고리즘 1회 실행이며 스캔 반복 전체를 포함한다.
- 표본은 설정마다 10개다. JVM 2개에서 각각 1초짜리 워밍업 5회를 버리고 3초짜리 측정 5회를 수행했다.
- 인원만 20명에서 300명까지 바꾸고 나머지 입력은 고정했다.
- 순차 구현과 병렬 구현 모두 전달받은 배정을 복사하지 않고 직접 수정한다. 그래서 호출마다 같은 greedy 시작 배정의 새 복사본을 만들어 전달했다.

| 인원 | 팀 수 | 팀 쌍 수 | 풀 병렬도(개) | 순차 평균 경과 시간(improve() 호출 1회, ms) | 병렬 평균 경과 시간(improve() 호출 1회, ms) | 배율(배) |
|---:|---:|---:|---:|---:|---:|---:|
| 20 | 2 | 1 | 12 | 0.090 | 0.315 | 0.29 |
| 40 | 4 | 6 | 12 | 3.088 | 2.677 | 1.15 |
| 60 | 6 | 15 | 12 | 25.391 | 11.252 | 2.26 |
| 120 | 12 | 66 | 12 | 651.458 | 210.754 | 3.09 |
| 200 | 20 | 190 | 12 | 3,628.497 | 1,496.298 | 2.42 |
| 300 | 30 | 435 | 12 | 25,727.455 | 10,610.148 | 2.42 |

※ 배율 = 순차 평균 경과 시간 ÷ 병렬 평균 경과 시간. 배율이 클수록 병렬 실행이 빠르다.

배율은 인원 120명에서 3.09까지 오른 뒤, 200명과 300명에서는 둘 다 2.42다. 성능 분석 1편부터 4편까지 설명해야 할 값은 인원 200명과 300명의 배율 2.42배다.

기대한 배율은 6배였다. 이 작업은 입출력을 기다리는 구간이 없는 CPU 바운드 작업이므로, 사용하는 코어 수에 반비례해 경과 시간이 줄어드는 것이 기대치다. 물리 코어는 6개다.

풀 병렬도는 12인데 기대치를 6배로 잡은 이유는 12와 6이 세는 대상이 다르기 때문이다. 12는 풀에 둔 스레드의 개수이고, 6은 그 스레드들이 실행될 실행 유닛의 개수다.

실제 배율을 기대치로 나누면 2.42 ÷ 6 = 0.40이어서, 코어 6개로 기대치의 40%만 얻었다.

### 1.2 프로세스 CPU 시간은 순차 실행의 1.78배로 늘었다

같은 인원 200명을 테스트 프로그램으로 다시 측정해 CPU 시간을 확인했다. 아래는 기준 측정의 네 실행 중 풀 병렬도 12, 말단 작업 16개(workSize 12) 실행의 값이다.

| 구현 | 풀 병렬도(개) | 분할 개수(개) | 경과 시간(improve() 호출 1회, ms) | 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ms) |
|---|---:|---:|---:|---:|
| 순차 | 풀을 쓰지 않음 | 없음 | 3,378.91 | 3,375.00 |
| 병렬 | 12 | 16 | 764.76 | 6,006.25 |
| 병렬 ÷ 순차 | | | 0.23 | 1.78 |

※ 분할 개수 16은 workSize 12로 실행한 결과다.

병렬 실행의 경과 시간은 764.76ms로, 순차 실행의 3,378.91ms보다 짧다. 순차 대비 배율은 3,378.91 ÷ 764.76 = 4.42배다.

반면 프로세스 CPU 시간은 병렬 실행이 더 많이 썼다.

- 예상한 값: 병렬화는 스캔 안의 평가를 여러 말단 작업에 나눠 실행하도록 바꾼 것이고, 평가 자체는 바꾸지 않았다. 그래서 병렬 실행에 추가 비용이 없다면 프로세스 CPU 시간의 합은 순차 실행과 같아야 한다.
- 실제 값: 병렬 실행은 6,006.25ms를 써서 순차 실행 3,375.00ms의 1.78배였다.
- 차이: 병렬 실행이 순차 실행보다 2,631.25ms(6,006.25 − 3,375.00)를 더 썼다.

이 2,631.25ms가 어디서 발생했는지가 이후 분석에서 확인할 내용이다.

### 1.3 병렬 실행 중 코어는 평균 7.85개가 사용되고 있었다

배율이 낮은 원인이 코어를 충분히 사용하지 못한 데 있는지, 병렬 실행이 순차 실행보다 CPU 시간을 더 쓴 데 있는지는 1.2절 표의 측정값 네 개로 확인할 수 있다.

- 순차 실행: 경과 시간 3,378.91ms, 프로세스 CPU 시간 3,375.00ms
- 병렬 실행: 경과 시간 764.76ms, 프로세스 CPU 시간 6,006.25ms

이 네 값으로 다음 세 값을 계산했다.

| 값 | 계산식 | 크기 |
|---|---|---:|
| 평균 사용 코어 수(개) | 병렬 프로세스 CPU 시간 ÷ 병렬 경과 시간 = 6,006.25 ÷ 764.76 | 7.85 |
| 순차 대비 CPU 효율 | 순차 프로세스 CPU 시간 ÷ 병렬 프로세스 CPU 시간 = 3,375.00 ÷ 6,006.25 | 0.562 |
| 실측 배율(배) | 순차 경과 시간 ÷ 병렬 경과 시간 = 3,378.91 ÷ 764.76 | 4.42 |

논리 프로세서 12개 중 평균 7.85개가 동시에 사용되고 있었다.

순차 대비 CPU 효율은 순차 실행이 쓴 CPU 시간을 병렬 실행이 쓴 CPU 시간으로 나눈 값이다. 이 값이 1이면 병렬 실행이 순차 실행과 같은 CPU 시간으로 작업을 끝낸 것이고, 0.562면 병렬 실행이 순차 실행의 두 배 가까운 CPU 시간을 쓴 것이다.

평균 사용 코어 수와 순차 대비 CPU 효율을 곱하면 실측 배율이 나온다. 그 이유는 다음과 같다.

1. 평균 사용 코어 수는 병렬 프로세스 CPU 시간 ÷ 병렬 경과 시간이다.
2. 순차 대비 CPU 효율은 순차 프로세스 CPU 시간 ÷ 병렬 프로세스 CPU 시간이다.
3. 둘을 곱하면 병렬 프로세스 CPU 시간이 약분되고, 순차 프로세스 CPU 시간 ÷ 병렬 경과 시간만 남는다.
4. 순차 실행에서는 프로세스 CPU 시간과 경과 시간이 거의 같으므로, 남은 값은 실측 배율(순차 경과 시간 ÷ 병렬 경과 시간)과 같다.

즉 병렬 실행은 코어를 평균 7.85개 사용했고, 순차 대비 CPU 효율은 0.562(56%)였다. 평균 사용 코어 수 7.85와 순차 대비 CPU 효율 0.562를 곱한 결과가 실측 배율 4.42배다. 배율을 제한한 것은 코어 개수가 아니라 순차 대비 CPU 효율이다.

### 1.4 늘어난 CPU 시간은 풀 병렬도를 12로 올렸을 때만 크게 발생한다

늘어난 CPU 시간의 원인 후보는 두 가지다.

1. 분할, 복사, 병합처럼 병렬화 때문에 추가되는 처리
2. 풀 병렬도를 12로 올렸을 때만 생기는 요인

두 후보를 구분하려면 분할, 복사, 병합을 실행하는 횟수가 같고 풀 병렬도만 다른 두 실행을 비교하면 된다. 말단 작업 개수가 같으면 분할, 복사, 병합을 실행하는 횟수도 같다.

기준 측정에는 이런 비교 쌍이 두 개 있다. 아래 표의 네 실행 모두 인원 200명이고, 실행마다 순차 실행도 함께 측정했다.

| 풀 병렬도 | 분할 개수 | 병렬 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ms) | 순차 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ms) | 순차 대비(배) | 초과분(배) |
|---:|---:|---:|---:|---:|---:|
| 6 | 16 | 4,256.25 | 3,418.75 | 1.24 | 0.24 |
| 12 | 16 | 6,006.25 | 3,375.00 | 1.78 | 0.78 |
| 6 | 32 | 4,403.13 | 3,293.75 | 1.34 | 0.34 |
| 12 | 32 | 6,853.13 | 3,793.75 | 1.81 | 0.81 |

※ 표의 값

- 프로세스 CPU 시간: 개선 알고리즘 호출 1회 동안 프로세스의 모든 스레드가 코어에서 실행된 시간의 합이다. 측정 5회의 평균이다.
- 순차 대비: 병렬 프로세스 CPU 시간 ÷ 순차 프로세스 CPU 시간
- 초과분: 순차 대비 − 1. 병렬 실행이 순차 실행보다 더 쓴 CPU 시간이 순차 실행 CPU 시간의 몇 배인지를 나타낸다.
- 분할 개수: 분할 개수 16은 workSize 12로, 분할 개수 32는 workSize 6으로 실행한 결과다. workSize 6에서는 팀 쌍 11~12개짜리 구간이 한 번 더 나뉘어 5~6개가 되므로 말단 작업이 32개가 된다.

말단 작업 개수가 같은 두 행끼리 초과분을 비교하면 다음과 같다.

| 말단 작업 개수 | 풀 병렬도 6의 초과분 | 풀 병렬도 12의 초과분 | 풀 병렬도 12 ÷ 풀 병렬도 6 |
|---:|---:|---:|---:|
| 16 | 0.24 | 0.78 | 3.18배 |
| 32 | 0.34 | 0.81 | 2.39배 |

※ 마지막 열은 반올림하기 전의 초과분(0.2450, 0.7796, 0.3368, 0.8064)으로 계산했다.

말단 작업 개수가 같은데도 풀 병렬도만 6에서 12로 올리면 초과분이 풀 병렬도 6의 2.39배에서 3.18배가 된다. 따라서 초과분의 대부분은 분할, 복사, 병합이 아니라 풀 병렬도를 12로 올렸을 때만 생기는 요인에서 나온다.

### 1.5 워커 스레드 밖에서 늘어난 CPU 시간의 비중은 이 회차의 값으로 정할 수 없다

늘어난 CPU 시간이 워커 스레드에서 발생했는지, 다른 스레드에서 발생했는지도 구분할 수 있다. 아래 표는 1.2절과 같은 실행의 값이고, 인원은 200명이다.

| 구현 | 풀 병렬도(개) | 분할 개수(개) | 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ms) | main 스레드 CPU 시간(improve() 호출 1회 동안, ms) | 워커 CPU 시간(improve() 호출 1회 동안 워커 스레드 합, ms) | 워커 스레드 밖 CPU 시간(improve() 호출 1회 동안, ms) |
|---|---:|---:|---:|---:|---:|---:|
| 순차 | 풀을 쓰지 않음 | 없음 | 3,375.00 | 3,334.38 | 0.00 | 40.62 |
| 병렬 | 12 | 16 | 6,006.25 | 0.00 | 5,500.00 | 506.25 |

※ 표의 값

- 워커 스레드 밖 CPU 시간: 프로세스 CPU 시간 − main 스레드 CPU 시간 − 워커 CPU 시간
- 병렬 행의 워커 CPU 시간 5,500.00ms: 측정 5회의 평균이 아니다. 측정 5회가 끝난 뒤 워커별 CPU를 읽으려고 같은 설정으로 한 번 더 실행한 호출 1회의 값이다. 이 회차의 출력에는 측정 5회의 워커 CPU 시간이 없다.

병렬 실행이 순차 실행보다 더 쓴 CPU 시간 중 워커 스레드 밖에서 늘어난 비중은 다음과 같이 계산했다.

- 프로세스 CPU 시간의 증가분: 6,006.25 − 3,375.00 = 2,631.25ms
- 워커 스레드 밖 CPU 시간의 증가분: 506.25 − 40.62 = 465.63ms
- 워커 스레드 밖에서 늘어난 비중: 465.63 ÷ 2,631.25 = 17.7%

이 비중을 그대로 받아들이면, 추가로 쓴 CPU 시간의 17.7%가 워커 스레드 밖에서 늘어난 것이다. 워커 스레드 안에서 늘어난 시간과 구분해서 살펴봐야 할 크기다.

다만 이 계산은 서로 다른 실행의 값을 섞었다. 프로세스 CPU 시간은 측정 5회의 평균이고 워커 CPU 시간은 따로 실행한 호출 1회의 값이어서, 17.7%를 워커 스레드 밖에서 늘어난 비중으로 확정할 수 없다. 같은 실행에서 프로세스 CPU 시간과 워커 CPU 시간을 함께 측정한 분할 개수별 측정에서는, 풀 병렬도 12의 분할 1에서 분할 12로 갈 때 늘어난 CPU 시간 중 워커 스레드 밖에서 늘어난 비중이 0.55%였다(2.1절).

### 1.6 코어 부족은 원인이 아니지만, 기준 측정으로는 풀 병렬도와 말단 작업 개수의 영향을 구분할 수 없다

성능 분석 1편부터 4편까지 설명해야 할 값은 두 가지다.

- JMH로 측정한 인원 200명과 300명의 배율 2.42배
- 테스트 프로그램으로 측정한 인원 200명의 순차 대비 프로세스 CPU 시간 1.78배

같은 인원 200명, 워커 스레드 12개라도 테스트 프로그램으로 측정한 배율은 4.42배다. 두 도구로 측정한 배율은 서로 다르다.

병렬 실행 중 코어는 평균 7.85개가 동시에 사용되고 있었으므로, 배율이 낮은 원인을 코어를 사용하지 못한 데서 찾을 수 없다. 늘어난 CPU 시간의 대부분은 병렬화로 추가되는 분할, 복사, 병합이 아니라, 풀 병렬도를 12로 올렸을 때만 생기는 요인에서 나온다.

다만 이 회차에서는 말단 작업 개수를 workSize로 간접 지정했기 때문에, 풀 병렬도와 말단 작업 개수를 따로 바꿀 수 없었다. 그래서 다음 회차부터는 분할 개수를 호출 인자로 직접 지정했다.

## 2. 프로세스 CPU 시간과 경과 시간을 결정하는 것은 풀 병렬도가 아니라 동시 실행 말단 작업 개수다

1절의 결과 중 하나는 늘어난 CPU 시간이 풀 병렬도를 올렸을 때만 크게 발생한다는 것이었다. 그런데 기준 측정에서는 분할 개수가 항상 풀 병렬도보다 크게 설정되어 있었다. 그래서 풀 병렬도를 올리면 워커 스레드 개수와 동시 실행 말단 작업 개수가 함께 늘었다.

워커 스레드 개수와 동시 실행 말단 작업 개수의 영향을 구분하기 위해 분할 개수를 호출 인자로 지정하고, 풀 병렬도와 분할 개수를 하나씩 바꿔 가며 분할 개수별 측정과 카운터 측정을 진행했다.

- 분할 개수별 측정: 풀 병렬도 6과 12에서 분할 1부터 36까지 전 구간을 측정했다.
- 카운터 측정: 그중 분할 개수 열다섯 가지에서 카운터를 넣어 측정했다.

### 2.1 늘어난 CPU 시간의 99.45%는 워커 스레드에서 발생했다

분할 개수별 측정에서 풀 병렬도 12의 분할 1과 분할 12를 비교했다. 동시에 실행되는 말단 작업이 가장 적은 지점과 가장 많은 지점이다.

| 값 | 순차 | 풀 병렬도 12, 분할 1 | 풀 병렬도 12, 분할 12 | 증가분(ns) | 증가분 비중(%) |
|---|---:|---:|---:|---:|---:|
| 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ns) | 3,584,375,000 | 3,453,125,000 | 10,815,625,000 | 7,362,500,000 | 100 |
| 워커 CPU 시간(improve() 호출 1회 동안 워커 스레드 합, ns) | 0 | 3,396,875,000 | 10,718,750,000 | 7,321,875,000 | 99.45 |
| main 스레드 CPU 시간(improve() 호출 1회 동안, ns) | 3,543,750,000 | 6,250,000 | 3,125,000 | -3,125,000 | -0.04 |
| 자바가 아닌 스레드 CPU 시간(improve() 호출 1회 동안, ns) | 40,625,000 | 50,000,000 | 93,750,000 | 43,750,000 | 0.59 |

※ 표의 값

- 증가분: 분할 12의 값 − 분할 1의 값
- 증가분 비중: 그 행의 증가분 ÷ 프로세스 CPU 시간의 증가분
- 자바가 아닌 스레드 CPU 시간: GC 작업 스레드, JIT 컴파일러 스레드, VM 내부 스레드의 CPU 시간이 이 행에 포함된다.
- 순차 열: 순차 실행은 풀을 쓰지 않는다. 그래서 워커 CPU 시간이 0이고, 프로세스 CPU 시간의 대부분이 main 스레드 CPU 시간으로 측정됐다.

늘어난 CPU 시간의 99.45%가 워커 스레드에서 발생했고, 워커 스레드 밖에서 늘어난 비중은 0.55%뿐이다. 워커 스레드 밖에서는 자바가 아닌 스레드 CPU 시간의 비중이 0.59%이고, main 스레드 CPU 시간은 오히려 줄어 비중이 -0.04%다.

따라서 늘어난 프로세스 CPU 시간은 워커 스레드가 쓴 것이고, 다른 스레드가 쓴 것이 아니다. 워커 스레드가 이 시간을 평가를 실행하는 동안 썼는지는 2편에서 확인한다.

### 2.2 워커 스레드를 두 배로 늘려도 분할 개수가 같으면 프로세스 CPU 시간이 같다

이번에는 풀에 둔 워커 스레드 개수가 프로세스 CPU 시간을 바꾸는지 확인한다. 분할 6에서는 두 풀 병렬도 모두 분할 개수가 풀 병렬도보다 작거나 같으므로, 동시 실행 말단 작업 개수가 6으로 같아진다.

| 설정 | 프로세스 CPU 시간(improve() 호출 1회 동안 프로세스 전체 스레드 합, ns) |
|---|---:|
| 풀 병렬도 6, 분할 6 | 7,009,375,000 |
| 풀 병렬도 12, 분할 6 | 6,978,125,000 |

두 값의 비는 6,978,125,000 ÷ 7,009,375,000 = 0.996으로, 차이는 0.4%다. 풀 병렬도가 두 배인데 값은 거의 같다.

워커별 CPU 기록도 참고할 수 있다. 이 기록은 측정 5회가 끝난 뒤 같은 설정으로 한 번 더 실행한 호출 1회의 값이다.

- 풀 병렬도 12, 분할 6: 워커 스레드 6개가 각각 전체 워커 CPU 시간의 15.2%에서 17.0%를 썼고, 나머지 여섯 개는 합쳐 4.2%를 썼다.
- 풀 병렬도 12, 분할 3: CPU를 쓴 워커 스레드가 9개였고, 상위 두 개가 전체 워커 CPU 시간의 36.0%와 30.6%를 썼다.

CPU를 쓴 워커 스레드 수가 분할 개수와 정확히 맞지는 않는다.

따라서 이 절의 근거는 워커별 CPU 기록이 아니라 위 표의 0.4% 차이다. 분할 개수가 같으면 풀에 워커 스레드를 두 배로 두어도 프로세스 CPU 시간이 같으므로, 풀에 워커 스레드를 몇 개 두었는지는 그 자체로 프로세스 CPU 시간을 결정하지 않는다.

### 2.4 동시 실행 말단 작업 개수 하나가 프로세스 CPU 시간과 경과 시간을 결정한다

늘어난 CPU 시간은 워커 스레드에서 발생한다. 워커 스레드 밖에서 늘어난 비중은 0.55%다.

프로세스 CPU 시간과 경과 시간을 결정하는 요인도 하나로 한정된다. 분할 개수가 같으면 풀에 워커 스레드를 두 배로 두어도 프로세스 CPU 시간이 같고, 동시 실행 말단 작업 개수가 그대로면 분할만 늘려서는 경과 시간이 줄지 않는다. 두 결과를 모두 설명하는 것은 그 순간 실제로 함께 실행되는 말단 작업 개수 하나다.

그렇다면 다음으로 확인할 것은 동시에 실행되는 말단 작업이 늘 때 워커 스레드의 어떤 처리 시간이 늘어나는지다. 2절에서 쓴 분할 개수별 측정과 카운터 측정의 값으로는 말단 작업마다 4중 루프에서 쓴 시간과 평가 횟수를 알 수 없다.

- 분할 개수별 측정: 계측 코드가 없다.
- 카운터 측정: 카운터가 평가 횟수, 통과 횟수, 복사 시간, 4중 루프 시간을 개선 알고리즘 호출 1회 전체의 합계로만 센다.

3절에서는 4중 루프 시간과 평가 횟수를 말단 작업마다 기록하도록 계측 코드를 추가해 다시 측정한 회차를 다룬다.

## 3. 평가 횟수와 통과 횟수가 같은데 평가 1회 평균 시간이 3.55배가 된다

2절까지의 분석으로 프로세스 CPU 시간과 경과 시간을 결정하는 요인을 동시 실행 말단 작업 개수 하나로 한정했다. 동시 실행 말단 작업 개수가 늘 때 워커 스레드의 어떤 처리 시간이 늘어나는지 확인하려면, 말단 작업마다 4중 루프에서 쓴 시간과 평가 횟수를 기록해야 한다. 상세 기록 측정에서는 이 기록을 추가하고, 카운터 측정과 같은 풀 병렬도와 분할 개수로 다시 측정했다.

이 절에서는 이 회차에서 나온 세 가지 현상을 다룬다. 세 현상은 서로 관계없는 것처럼 보이지만, 2편과 3편에서 하나의 원인으로 설명한다. 아래 값은 모두 상세 기록 측정 결과이고 풀 병렬도는 12다.

### 3.1 평가 횟수와 통과 횟수는 그대로인데 평가 1회 평균 시간이 3.55배가 된다

그런데 평가 1회 평균 시간은 분할 1의 5,192ns에서 분할 12의 18,425ns로 3.55배가 되었다. 분할 1에서 6까지는 분할이 하나 늘 때마다 평가 1회 평균 시간이 1.14배에서 1.22배씩 늘고, 한 분할에서만 크게 늘어나는 경우는 없다.

### 3.4 동시에 실행되는 말단 작업이 늘수록 평가 1회 평균 시간이 커진다

동시에 실행되는 말단 작업이 늘수록 평가 1회 평균 시간이 커진다. 평가 855,000회와 통과 352,485회는 고정인데, 평가 1회 평균 시간은 분할 1에서 분할 12까지 3.55배가 됐다. 2편과 3편에서 설명해야 할 값은 이 3.55배다.

분할 3부터 경과 시간이 크게 줄지 않는 것처럼 보이는 현상도 동시 실행 말단 작업 개수가 늘어날 때 나타난다. 분할을 하나 늘리면 말단 작업 하나가 맡는 평가 횟수가 줄어 경과 시간이 짧아지지만, 동시에 평가 1회 평균 시간이 늘어 경과 시간이 길어지기 때문이다.

다음으로 확인할 것은 평가 1회 평균 시간의 증가분이 어느 처리에서 발생하는지다. 워커 스레드가 평가 코드를 실행하는 것과 관계없이 시간이 드는 처리가 여러 가지 있으므로, 워커 스레드 밖의 처리부터 확인해야 한다. 이 내용은 2편에서 다룬다.

## 4. 결론

측정한 값은 다음 두 가지다.

- JMH로 측정한 병렬화 배율: 인원 200명과 300명에서 2.42배(워커 스레드 12개)
- 테스트 프로그램으로 측정한 순차 대비 프로세스 CPU 시간: 인원 200명에서 1.78배(워커 스레드 12개, 말단 작업 16개). 병렬 실행은 순차 실행과 같은 팀 배정 결과를 냈다.

두 값의 원인은 하나다. 동시에 실행되는 말단 작업이 늘수록 평가 1회 평균 시간이 커진다.

원인 후보는 다음 네 단계를 거쳐 한정했다.

1. 유휴 코어가 있는지 확인했다. 코어는 평균 7.85개가 동시에 사용되고 있었다. 배율을 제한한 것은 코어 개수가 아니라 순차 대비 CPU 효율이다.
2. 늘어난 CPU 시간이 어느 스레드에서 발생했는지 확인했다. 99.45%가 워커 스레드에서 발생했고, 워커 스레드 밖은 0.55%다.
3. 무엇이 프로세스 CPU 시간과 경과 시간을 결정하는지 확인했다. 분할 개수가 같으면 풀에 워커 스레드를 두 배로 두어도 프로세스 CPU 시간이 같고, 동시 실행 말단 작업 개수가 그대로면 분할만 늘려서는 경과 시간이 줄지 않는다. 결정 요인은 동시 실행 말단 작업 개수 하나다.
4. 동시 실행 말단 작업 개수가 늘 때 어떤 값이 커지는지 측정했다. 평가 855,000회와 통과 352,485회는 모든 설정에서 그대로인데, 평가 1회 평균 시간은 5,192ns에서 18,425ns로 3.55배가 됐다.
