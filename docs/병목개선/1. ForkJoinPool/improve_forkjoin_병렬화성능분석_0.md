## 개요

팀 편성 엔진의 개선 알고리즘을 fork-join으로 병렬화했지만, 순차 실행 대비 배율이 인원 200명과 300명에서 모두 2.42배로 기대보다 훨씬 낮았다. 1편부터 4편은 그 원인을 찾아 확정하기까지의 과정을 기록하고, 5편과 최종 보고서는 원인을 확정한 뒤의 작업을 다룬다. 이 문서는 1편부터 5편이 같은 뜻으로 쓰는 용어와 측정 기준을 정리하고, 1편부터 5편에서는 이 내용을 다시 설명하지 않는다. 최종 보고서는 이 문서 없이 읽을 수 있도록 필요한 용어와 측정 기준을 자체 개요에 다시 적었다. 최종 보고서의 측정 이름과 집계 규칙은 이 문서와 같고, 평가를 검사로, 풀 병렬도를 워커 스레드 개수로 부른다.

## 1. 스캔과 평가

개선 알고리즘은 이미 만들어진 팀 배정 하나를 입력으로 받는다. 서로 다른 두 팀에서 한 명씩 맞바꿔 보고 배정이 좋아지는지 확인하는 작업을 반복한다.

교환은 항상 두 팀 사이에서만 일어나므로, 어느 두 팀을 비교할지 정한 목록이 필요하다. 이 목록의 원소 하나를 팀 쌍이라고 한다. 팀 쌍 하나에서 두 사람을 실제로 맞바꾸고, 배정이 좋아졌는지 확인한 뒤 원래대로 되돌리는 작업이 평가 1회다.

모든 팀 쌍의 모든 교환 후보를 한 번씩 평가하는 과정이 스캔이다. 스캔 1회는 그중 가장 좋은 교환 1건만 실제로 적용하고 끝난다. 교환을 적용한 배정에서 다시 전수 조사해야 하므로 스캔은 여러 번 반복되고, 어떤 교환으로도 배정이 더 좋아지지 않으면 반복을 끝낸다.

스캔 1회를 실행하는 반복문은 네 겹이어서 4중 루프라고 부른다. 바깥 두 겹이 팀 쌍을 순회하고, 안쪽 두 겹이 그 팀 쌍의 두 팀에서 사람을 각각 순회한다. 평가 1회는 가장 안쪽 반복문의 본문이 한 번 실행되는 것이다.

평가 1회는 다음 여섯 단계로 실행된다.

1. 두 팀에서 한 명씩 맞바꾼다.
2. 팀 사이의 합 편차를 계산한다.
3. 합 필터로 이 후보를 더 검토할지 결정한다.
4. 합 필터를 통과한 경우에만 팀 사이의 분포 편차를 계산한다.
5. 최선 후보를 갱신할지 결정한다.
6. 맞바꾼 두 사람을 되돌린다.

이 과정에서 쓰는 용어는 다음과 같다.

| 용어 | 뜻 |
|---|---|
| 합 편차 계산 | 팀 사이의 합 편차를 구하는 메서드(`sumDeviation`) |
| 분포 편차 계산 | 팀 사이의 분포 편차를 구하는 메서드(`distributionDeviation`) |
| 합 필터 | 합 편차만 보고 그 후보를 더 검토할 가치가 있는지 거르는 조건. 여기서 걸러진 후보는 분포 편차를 계산하지 않는다 |
| 통과 횟수 | 합 필터를 통과해 분포 편차 계산까지 진행한 횟수 |
| 통과율 | 통과 횟수 ÷ 평가 횟수 |

## 2. 팀 쌍을 나눠 맡는 병렬 구조

개선 알고리즘 호출 1회는 여러 번의 스캔으로 이루어진다. 이 중 병렬로 바꾼 것은 스캔 1회 안의 전수 조사다. 한 스캔에서 다음 스캔으로 넘어가는 바깥 반복은 순차 실행으로 그대로 두었다.

두 부분을 다르게 처리한 기준은 앞 단계의 결과를 기다려야 하는지다. 두 번째 스캔은 첫 번째 스캔이 고른 최선 교환을 적용한 배정에서 시작한다. 첫 번째 스캔이 끝나기 전에는 두 번째 스캔이 조사할 배정이 없으므로, 스캔끼리는 동시에 실행할 수 없다.

반면 한 스캔 안의 평가는 모두 같은 배정을 대상으로 후보 하나를 평가하고 되돌리는 작업이어서 서로 선후 관계가 없다. 어느 평가가 먼저 실행되어도 다른 평가의 입력이 바뀌지 않으므로, 스캔 안의 전수 조사는 여러 작업으로 나눠 맡길 수 있다.

나누는 대상은 팀 쌍 목록이다. 팀 쌍을 번호 순서로 나열하고 번호 구간을 절반씩 나누는 과정을 반복하다가, 구간이 충분히 짧아지면 더 나누지 않고 그 구간의 팀 쌍을 모두 평가한다. 이 마지막 작업을 말단 작업이라고 부른다.

말단 작업은 시작할 때 팀 배정 전체를 복사해, 다른 말단 작업과 공유하지 않는 복사본을 만든다. 그다음 담당 구간의 팀 쌍을 모두 평가하고, 그 구간에서 가장 좋은 교환 1건(부분 최선)을 반환한다. 복사본을 따로 두는 이유는 여러 말단 작업이 같은 팀 배정을 동시에 수정하지 않게 하기 위해서다.

병렬 구조에서 쓰는 용어는 다음과 같다.

| 용어 | 뜻 |
|---|---|
| fork | 구간을 반으로 나눠 한쪽을 새 작업으로 내보내는 것 |
| 작업 훔치기(work stealing) | 작업 큐가 빈 워커 스레드가 다른 워커 스레드의 작업 큐에 있는 작업을 가져와 실행하는 것 |
| 병합 | 나뉘어 실행된 두 부분 최선을 순차 실행과 같은 규칙으로 비교해 하나로 합치는 것 |
| 분할 개수 | 팀 쌍을 몇 개의 말단 작업으로 나눌지 정하는 값 |
| 풀 병렬도 | fork-join 풀에 둔 워커 스레드의 개수 |
| 동시 실행 말단 작업 개수 | 어느 순간 실제로 함께 실행되고 있는 말단 작업의 개수. 분할 개수와 풀 병렬도 중 작은 값이다 |
| workSize | 말단 작업 하나가 맡는 팀 쌍의 최대 개수. 담당 구간이 이 값보다 길면 구간을 다시 반으로 나눈다 |
| 스트림 구현 | 두 편차 계산 메서드가 자바 스트림으로 합계와 평균을 구하는 원래 코드 |
| for문 구현 | 같은 계산을 명령형 for문으로 바꾼 코드 |

분할 개수와 동시 실행 말단 작업 개수는 서로 다른 값이다. 풀 병렬도 6에 분할 12를 주면 동시에 실행되는 말단 작업은 6개이고, 나머지 6개는 앞의 작업이 끝난 뒤에 실행된다.

기준 측정에서는 workSize를 바꿔 말단 작업 개수를 간접적으로 정했고, 그다음 회차부터는 분할 개수를 호출 인자로 직접 지정했다.

스트림 구현과 for문 구현의 비교는 3편에서 원인을 확정하는 데 쓴다.

## 3. 고정 입력에서 계산되는 개수

아래 값은 인원 200명, 정원 10명일 때의 개수다. 설정으로 지정한 값이 아니라 이 입력에서 계산되는 값이다.

| 값 | 개수 | 계산 근거 |
|---|---:|---|
| 팀 개수 | 20개 | 200 ÷ 10 |
| 팀 쌍 개수 | 190개 | 20 × 19 ÷ 2 |
| 팀 쌍 하나의 교환 후보 수 | 100가지 | 10 × 10 |
| 스캔 1회의 평가 횟수 | 19,000회 | 190 × 100 |
| 스캔 반복 횟수 | 45회 | 교환을 적용한 44회와, 더 이상 개선이 없어 끝나는 마지막 1회 |
| 호출 1회의 평가 횟수 | 855,000회 | 19,000 × 45 |
| 호출 1회의 통과 횟수 | 352,485회 | 실측값 |
| 통과율 | 0.412263 | 352,485 ÷ 855,000 |

※ 값의 출처

- 인원과 정원에서 바로 계산되는 값: 팀 개수, 팀 쌍 개수, 팀 쌍 하나의 교환 후보 수, 스캔 1회의 평가 횟수
- 이 입력으로 실행해서 얻은 결과값: 스캔 반복 횟수 45회, 호출 1회의 통과 횟수
- 위의 결과값으로 계산한 값: 호출 1회의 평가 횟수(19,000 × 45), 통과율(352,485 ÷ 855,000)

## 4. 측정 항목

측정에 쓴 테스트 프로그램은 설정마다 표 한 행을 출력한다. 시간 값은 모두 개선 알고리즘 호출 1회 동안 늘어난 양(증가분)이다.

측정 구간은 다음과 같다. 1편부터 5편과 최종 보고서의 표는 열 이름에 이 구간을 "improve() 호출 1회"로 적는다.

- 개선 알고리즘 호출 1회는 엔진의 개선 메서드 호출 1회다. 병렬 구현은 `improve()`(분할 개수를 지정하는 회차는 `improveBySplitCount()`), 순차 구현은 `improveSequential()`이다.
- 테스트 프로그램은 이 메서드를 호출하기 직전과 직후에 값을 읽는다. 병렬 구현에서는 fork-join 풀 생성과 말단 작업의 fork, 실행, 병합이 측정 구간에 들어간다.
- 호출마다 새로 만드는 시작 배정 복사본은 호출 전에 만들므로 측정 구간에 들어가지 않는다.
- JMH로 측정한 기준 측정의 경과 시간도 같은 구간이다. 시작 배정 복사는 JMH의 측정 밖 준비 단계(`@Setup(Level.Invocation)`)에서 한다.

| 1편부터 5편과 최종 보고서에서 쓰는 이름 | 뜻 | 측정 출력의 열 이름 |
|---|---|---|
| 경과 시간 | 개선 알고리즘 호출 1회(`improve()` 호출 1회)가 시작해서 끝날 때까지 실제로 흐른 시간 | elapsed |
| 프로세스 CPU 시간 | 개선 알고리즘 호출 1회 동안 프로세스의 모든 스레드(main 스레드, 워커 스레드, GC·JIT 같은 JVM 내부 스레드)가 코어에서 실행된 시간의 합 | procCPU |
| main 스레드 CPU 시간 | 개선 알고리즘 호출 1회 동안 main 스레드가 사용한 CPU 시간 | mainCPU |
| 워커 CPU 시간 | 개선 알고리즘 호출 1회 동안 fork-join 워커 스레드들이 사용한 CPU 시간의 합 | workerCPU |
| 기타 자바 스레드 CPU 시간 | 개선 알고리즘 호출 1회 동안 main 스레드도 워커 스레드도 아닌 자바 스레드가 사용한 CPU 시간의 합 | 기타 자바 스레드 |
| 자바가 아닌 스레드 CPU 시간 | 프로세스 CPU 시간에서 자바 스레드의 CPU 시간 합을 뺀 나머지. GC 작업 스레드, JIT 컴파일러 스레드, VM 내부 스레드의 CPU 시간이 여기에 포함된다. 측정 오차도 섞여 있어 음수가 나오기도 한다 | 자바 아닌 스레드 |
| GC 시간 | 개선 알고리즘 호출 1회 동안 GC가 사용한 시간. CPU 시간이 아니라 실제로 흐른 시간 기준이다 | GC |
| 평균 사용 코어 수 | 프로세스 CPU 시간 ÷ 경과 시간. 개선 알고리즘 호출 1회 동안 평균 몇 개의 코어가 동시에 사용됐는지를 나타내고, 상한은 논리 프로세서 수인 12다 | busyCore |
| 총 할당량 | 개선 알고리즘 호출 1회 동안 새로 만든 객체의 누적 바이트 | 총 할당 |

CPU 시간은 스레드마다 별도의 누적값으로 기록된다. 이 누적값은 그 스레드가 코어에서 실제로 실행되는 동안에만 증가하고, 코어에서 실행되지 않는 동안에는 증가하지 않는다. 테스트 프로그램은 호출 직전과 직후에 이 누적값을 읽어 차이를 구한다. 여러 스레드가 동시에 실행되면 각 스레드의 시간이 모두 더해지므로, 프로세스 CPU 시간은 경과 시간보다 클 수 있다.

말단 작업과 스캔마다 한 줄씩 남기는 상세 기록에서는 다음 값을 얻는다.

| 이름 | 뜻 |
|---|---|
| 평가 횟수 | 가장 안쪽 반복문 본문이 실행된 총횟수 |
| 4중 루프 시간 합 | 말단 작업들이 4중 루프를 실행하는 데 걸린 시간의 합. 여러 말단 작업이 동시에 실행되면 겹치는 시간이 각각 더해진다 |
| 복사 시간 합 | 말단 작업들이 팀 배정 복사본을 만드는 데 쓴 시간의 합 |
| 평가 1회 평균 시간 | 4중 루프 시간 합 ÷ 평가 횟수 |
| 평가 1회 평균 워커 CPU 시간 | 워커 CPU 시간 ÷ 평가 횟수 |
| 편차 계산 1회 평균 시간 | 편차 계산 메서드가 쓴 시간의 합 ÷ 그 메서드의 호출 횟수. 합 편차 계산과 분포 편차 계산에 각각 구한다 |

## 5. 측정 회차와 집계 규칙

측정은 한 번의 실행으로 끝나지 않았다. 앞 실행의 측정값으로 원인을 구분할 수 없을 때마다, 그 원인을 구분할 값을 측정하는 코드를 추가했다. 측정 코드를 바꿀 때마다 전체를 처음부터 다시 측정했다. 이렇게 나뉜 실행 하나를 회차라고 부른다. 본문에서는 값을 적을 때마다 어느 회차의 값인지 밝힌다.

| 회차 | 측정 대상 | 포함된 계측 |
|---|---|---|
| 기준 측정 | 인원 여섯 가지에서의 배율, 풀 병렬도(6, 12)와 workSize(12, 6)를 조합한 네 실행의 CPU 시간 | 없음 |
| 분할 개수별 측정 | 풀 병렬도 6과 12에서 분할 1부터 36까지 전 구간 | 없음 |
| 카운터 측정 | 풀 병렬도 6과 12에서 분할 개수 열다섯 가지(표 아래 참조) | 평가 횟수, 통과 횟수, 복사 시간, 4중 루프 시간을 세는 카운터 |
| 상세 기록 측정 | 카운터 측정과 같은 풀 병렬도와 분할 개수 | 위 계측에 더해, 평가마다 두 편차 계산의 시각을 읽는 기록 |
| 클럭 측정 | 카운터 측정과 같은 풀 병렬도와 분할 개수에서 실행 중의 CPU 클럭 | 상세 기록에 구간 시작 시각을 더한 것 |
| for문 대조 측정 | 카운터 측정과 같은 풀 병렬도와 분할 개수를 for문 구현으로 측정하고, 분할 36에서는 스트림 구현도 다시 측정. 실행 세 개로 이루어진다(표 아래 참조) | 위 계측에 더해 할당 바이트 계측 |
| JFR 측정 | 할당이 코드의 어느 문장에서 발생하는지. 순차 실행과 풀 병렬도 6·분할 36 병렬 실행을 한 기록에 담았다 | 위 계측에 더해 실행 기록기(JFR)의 할당 표본 |
| 증분 재계산 측정 | 편차 계산을 증분 재계산으로 바꾼 구현의 순차 실행과, 풀 병렬도 6과 12의 분할 열다섯 가지. 같은 조건으로 여섯 번 실행했다 | for문 대조 측정과 같은 계측(상세 기록, 할당 바이트) |
| JFR 재측정 | 증분 재계산 구현의 할당이 코드의 어느 문장에서 발생하는지. 순차 실행과 풀 병렬도 6·분할 36 병렬 실행을 한 기록에 담았다 | 증분 재계산 측정과 같은 계측에 더해 실행 기록기(JFR)의 할당 표본 |

분할 개수 열다섯 가지는 1부터 12까지와 18, 24, 36이다. 1부터 12까지를 모두 넣은 이유는 이 구간에서 동시 실행 말단 작업 개수가 변하기 때문이다. 13 이상에서는 측정값이 그대로 유지되는지 확인하려고 세 지점만 두었다.

for문 대조 측정은 실행 세 개로 이루어져 있다. 여러 실행에 함께 들어 있는 설정이라도 실행마다 값이 조금씩 다르다. 1편부터 5편과 최종 보고서에서는 세 실행을 다음 이름으로 구분한다.

| 실행 | 구현 | 설정 |
|---|---|---|
| 스트림 분할 36 실행 | 스트림 구현 | 순차, 풀 병렬도 6과 12의 분할 36 |
| for문 분할 36 실행 | for문 구현 | 순차, 풀 병렬도 6과 12의 분할 36 |
| for문 전체 분할 실행 | for문 구현 | 순차, 풀 병렬도 6과 12의 분할 열다섯 가지 |

집계 규칙은 세 가지다.

1. 테스트 프로그램으로 측정한 값은 설정마다 워밍업을 버리고 측정 5회를 평균한 것이다. 버린 워밍업은 증분 재계산 측정 전까지의 회차가 2회, 증분 재계산 측정이 5회(여섯 실행 중 한 실행은 10회), JFR 재측정이 100회다.
2. 배율을 측정한 벤치마크 값은 표본 10개를 평균한 것이다.
3. 할당량은 예외다. 각 실행에서 처음 측정한 병렬 설정은 측정 순번 1(측정 5회 중 첫 번째 측정)의 할당량을 빼고 측정 2~5번째를 평균한다.

측정 1회는 개선 알고리즘 호출 1회다. 따라서 이 문서의 값은 따로 밝히지 않는 한 호출 1회당 값이다.

3번 규칙은 할당량에만 적용한다. 처음 측정한 병렬 설정의 측정 순번 1은 할당량이 약 3.8MB 더 크게 측정된다. 워밍업에서 꺼 두었던 상세 기록 코드가 이때 처음 실행되면서 생긴 할당으로 보인다. 워밍업에서도 상세 기록을 켜도록 바꾼 뒤의 실행에서는 이 차이가 나타나지 않았다.

각 절이 사용하는 회차는 다음과 같다.

| 회차 | 값을 사용하는 절 |
|---|---|
| 기준 측정 | 1편 1절 |
| 분할 개수별 측정 | 1편 2절 |
| 카운터 측정 | 1편 2절 |
| 상세 기록 측정 | 1편 3절, 2편 전체, 3편 1절, 3편 3절, 3편 4절, 4편 2절, 4편 3절 |
| 클럭 측정 | 4편 1절, 4편 2절, 4편 3절 |
| for문 대조 측정 | 3편 2절, 3편 4절, 3편 5절, 4편 4절 |
| JFR 측정 | 4편 5절 |
