## 질문 1. JMH 자체에 대한 설명 요청

**질문.** 매뉴얼 페이지 두 개(시간 복잡도와 Big-O 표기법 / 실측 측정: JMH, JFR, jcmd, async-profiler)를 기준으로 시간 복잡도 테스트를 진행할 예정이나, 해당 페이지에는 JMH 자체에 대한 구체적 설명이 없다. JMH가 무엇인지 설명을 요청했다.

**답변.**

### JMH는 무엇인가

- 정의: JMH(Java Microbenchmark Harness). 작은 코드 단위의 실행 시간을 재는 마이크로벤치마크 실행 프레임워크.
- 제작: OpenJDK 프로젝트. JVM의 JIT 컴파일러를 만드는 사람들이 직접 만들었다.
- 존재 이유: 메소드 하나의 실행 시간을 재는 일을 JVM 위에서 단순한 방법으로 하면 반드시 틀린다. 그 왜곡 요인들을 절차적으로 제거해 주는 측정 전용 도구다.
- 위상: JUnit이 정답 검증의 표준이라면 JMH는 실행 시간 측정의 표준이다.

### 왜 System.nanoTime()으로 직접 재면 안 되는가

소박한 측정 코드가 실제로 무엇을 재게 되는지가 문제다.

```java
long t0 = System.nanoTime();
for (int i = 0; i < 100_000; i++) {
    seedGreedy(sorted, 3, 2);       // 재고 싶은 대상
}
long elapsed = System.nanoTime() - t0;
```

이 코드가 왜곡되는 경로 네 가지.

| # | 왜곡 요인 | 무슨 일이 벌어지나 |
|---|---|---|
| 1 | JIT 워밍업 | JVM은 처음엔 인터프리터로 실행하다가, 호출이 누적되면 C1, C2 컴파일러로 점점 빠른 기계어로 바꾼다. 루프의 앞 수천 회와 뒤 수만 회는 서로 다른 코드가 실행된다. 평균을 내면 느린 초기와 빠른 후기가 섞인 무의미한 값이 나온다 |
| 2 | 죽은 코드 제거(DCE) | 반환값을 아무도 안 쓰면 C2가 호출 자체를 삭제할 수 있다. 측정 결과 0.3ns 같은 값이 나오면 대개 아무것도 실행되지 않은 시간을 잰 것이다 |
| 3 | 상수 접기 | 입력이 컴파일 시점에 상수로 확정되면 계산 결과를 미리 구해 박아 넣는다. 역시 측정 대상이 사라진다 |
| 4 | 실행 환경의 상호 영향 | 같은 JVM에서 벤치마크 A를 먼저 돌리면 그때 수집된 프로파일과 클래스 로딩 상태가 B의 컴파일 결과에 영향을 준다. GC가 측정 구간 중간에 개입하는 것도 같은 문제다 |

JMH는 이 네 가지를 각각 워밍업 단계, Blackhole, @State, fork로 대응한다.

### 실행 모델

용어 계층. 위에서 아래로 포함 관계다.

```
fork (독립된 JVM 프로세스 1개)
 └─ iteration (정해진 시간 동안의 측정 구간, 예: 1초)
     └─ invocation (@Benchmark 메소드 1회 호출. JMH가 1초 동안 가능한 만큼 반복)
```

`@Fork(2) @Warmup(iterations=5, time=1) @Measurement(iterations=5, time=1)` 설정이면 다음 순서로 진행된다.

| 단계 | 내용 | 결과에 포함? |
|---|---|---|
| fork 1 시작 | 새 JVM 프로세스 기동 | 해당 없음 |
| 워밍업 iteration 1~5 | 각 1초씩 메소드를 계속 호출. JIT가 C2 컴파일을 끝내도록 유도 | 버림 |
| 측정 iteration 1~5 | 각 1초씩 호출하고 평균 시간 기록 | 포함 (표본 5개) |
| fork 1 종료, fork 2 시작 | JVM을 완전히 새로 띄워 위 과정 반복 | 포함 (표본 5개 추가) |
| 집계 | 표본 10개로 평균과 99.9% 신뢰구간 계산 | Score ± Error |

fork를 2개 이상 두는 이유가 왜곡 요인 4다. JVM을 새로 띄우면 이전 벤치마크가 남긴 컴파일 프로파일이 없는 상태에서 다시 측정하므로, 실행 순서에 따른 영향이 표본 간 차이로 드러난다.

### 코드에서 실제로 쓰는 어노테이션 (예시)

```java
@BenchmarkMode(Mode.AverageTime)          // 호출 1회 평균 시간을 잰다 (복잡도 테스트에 적합)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@State(Scope.Benchmark)                   // 아래 필드들을 "벤치마크 상태"로 등록
public class SeedGreedyBench {

    @Param({"30", "300", "3000"})         // n을 바꿔가며 자동으로 3회 측정
    int memberCount;

    List<Member> sorted;                  // 입력 데이터. 필드로 두면 상수 접기(요인 3)가 차단된다

    @Setup(Level.Trial)                   // fork당 1회, 측정 시간에 포함 안 됨
    public void setup() {
        sorted = makeMembers(memberCount);
    }

    @Benchmark                            // 측정 대상. 이 메소드 본문만 시간에 잡힌다
    public List<List<Member>> run() {
        return engine.seedGreedy(sorted, teamCount, capacity);
    }
}
```

각 요소의 존재 이유.

- @State + 필드 입력: 입력이 컴파일러에게 상수로 보이지 않게 한다 (요인 3 차단).
- 반환값을 return: JMH가 생성한 래퍼 코드가 반환값을 Blackhole이라는 객체에 넘겨 "이 값은 쓰인다"고 위장한다. 죽은 코드 제거(요인 2) 차단. 반환할 것이 여러 개면 파라미터로 `Blackhole bh`를 받아 `bh.consume(x)`를 직접 호출한다.
- @Setup: 데이터 준비 비용을 측정에서 분리한다. `Level.Invocation`(호출마다 실행)은 측정 대상이 입력을 파괴할 때만 쓴다. 예를 들어 `improve()`는 teams를 제자리에서 수정하므로 매 호출 전 복사본이 필요하고, 그때 이 레벨이 필요해진다.
- @Param: 같은 벤치마크를 파라미터 값별로 전부 다시(fork부터) 돌린다.

### 결과 읽는 법 (예시)

```
Benchmark            (memberCount)  Mode  Cnt   Score    Error  Units
SeedGreedyBench.run             30  avgt   10   1.213 ±  0.041  us/op
```

- Score: 표본들의 평균. us/op = 호출 1회당 마이크로초.
- Error: 99.9% 신뢰구간의 절반 폭. Score 대비 Error가 크면(예: 30% 이상) 그 측정은 신뢰하지 말 것.
- 복잡도 판정: n이 10배씩 늘 때 Score가 약 10배씩 늘면 O(n), 100배씩 늘면 O(n²), 거의 안 늘면 O(log n) 쪽.

### 설치와 실행

- 빌드 연동이 필요한 이유: JMH는 어노테이션 프로세서가 측정용 래퍼 코드를 생성해야 돌아간다.
- Gradle 기준 구성: 플러그인 하나로 끝난다(me.champeau.jmh).
- 벤치마크 클래스 위치: `src/jmh/java` 아래.
- 실행: `gradlew jmh`.
- 주의: 벤치마크는 반드시 이 방식(생성된 래퍼와 독립 실행)으로 돌린다. IDE에서 main 메소드처럼 그냥 실행하거나 테스트 코드 안에서 호출하면 왜곡 방지 장치가 전부 빠진 채 돈다.
- 이 프로젝트에서의 용도: P0-1의 `improve()` 최적화(프루닝, 재계산 축소, 병렬화) 전후 비교.

## 질문 2. 측정 왜곡 경로 네 가지를 기초부터 풀어 설명

**질문.** 시간 복잡도를 처음 학습한 상태라 배경 지식이 부족한 상황에서, 앞 답변의 "이 코드가 왜곡되는 경로 네 가지" 부분을 기초부터 풀어서 설명해 달라고 요청했다.

**답변.**

### 전제: 자바 코드는 두 번 번역된다

```
MyClass.java ──(javac, 빌드 시점)──▶ MyClass.class (바이트코드) ──(JVM, 실행 시점)──▶ 실제 CPU 명령어
```

1번째 번역(javac)은 빌드할 때 한 번 끝난다. 문제는 2번째 번역이다. JVM은 바이트코드를 CPU 명령어로 바꾸는 방법을 두 가지 갖고 있다.

| 방식 | 동작 | 속도 |
|---|---|---|
| 인터프리터 | 바이트코드를 한 줄씩 읽어서 그때그때 실행. 번역 결과를 저장하지 않음 | 느림 |
| JIT 컴파일러 | 메소드 전체를 CPU 명령어로 번역해 저장. 이후 호출은 저장된 것을 실행 | 빠름 (수십 배) |

- 처음부터 전부 JIT 컴파일하지 않는 이유: 번역 자체에 시간이 들고, 프로그램 코드 대부분은 몇 번 불리지 않아서 번역 비용을 회수하지 못한다.
- JVM의 전략: 일단 인터프리터로 시작하고, 호출 횟수를 세다가, 자주 불리는 메소드만 골라서 컴파일한다.
- 컴파일 단계: 한 번에 하지 않고 두 단계다. C1(빨리 번역, 적당히 최적화) 다음, 더 자주 불리면 C2(느리게 번역, 강하게 최적화).

그리고 중요한 원칙이 하나 있다. JIT 컴파일러(특히 C2)는 다음 원칙에 따라 동작한다.

> 프로그램의 최종 결과만 같다면, 코드를 어떻게 바꿔도 된다. 삭제해도 된다.

요인 2와 3은 모두 이 원칙에서 나온다.

### 요인 1. JIT 워밍업: 루프의 앞과 뒤가 다른 코드다

100,000회 루프로 seedGreedy를 재는 상황. 1회 호출 시간을 가정하면(수치는 예시):

| 구간 | 실행 방식 | 1회당 시간 | 소계 |
|---|---|---|---|
| 1 ~ 2,000회 | 인터프리터 | 2,000ns | 4,000,000ns |
| 2,001 ~ 10,000회 | C1 컴파일 코드 | 400ns | 3,200,000ns |
| 10,001 ~ 100,000회 | C2 컴파일 코드 | 100ns | 9,000,000ns |

측정한 평균 = (4,000,000 + 3,200,000 + 9,000,000) ÷ 100,000 = 162ns.

여기서 문제를 정리하면:

- 알고 싶은 값: 100ns (C2 상태의 값). 서버는 몇 시간씩 돌므로 실제 서비스에서 이 메소드는 사실상 항상 C2 상태로 실행되기 때문.
- 측정된 값: 162ns. 알고 싶은 값보다 62% 부풀려짐.
- 추가 문제: 루프를 늘리면 초반 느린 구간의 비중이 줄어 평균이 내려간다. 즉 측정값이 코드의 성질이 아니라 루프 길이에 따라 변한다. (정확한 의미는 질문 3에서 다시 다룬다.)

JMH의 대응: 측정 전에 워밍업 반복을 둔다. 몇 초간 돌리기만 하면서 C2 컴파일이 끝나기를 기다리고, 그 구간의 기록은 전부 버린다.

### 요인 2. 죽은 코드 제거: 결과를 안 쓰면 호출이 사라진다

위의 원칙("결과만 같으면 삭제 가능")이 적용된 결과다. C2의 추론을 단계로 펼치면:

1. seedGreedy의 반환값은 어떤 변수에도 담기지 않는다.
2. seedGreedy는 외부 상태를 바꾸지 않는다(파일 쓰기, 필드 수정 등 없음).
3. 따라서 이 호출이 있든 없든 프로그램의 최종 결과는 동일하다.
4. 원칙에 따라 호출을 삭제한다.

삭제 후에는 빈 루프만 남고, 빈 루프 역시 결과에 영향이 없으므로 루프째 삭제될 수 있다. 최종적으로 재는 것은 nanoTime() 두 번 사이의 간격, 즉 아무것도 아닌 시간이다.

측정이 잘못됐는지 알아보는 기준:

- 의심 신호: 결과가 1회당 0.3ns처럼 비정상적으로 작게 나온다.
- 근거: 3GHz CPU에서 0.3ns는 CPU 명령어 1개의 실행 시간이다.
- 결론: 팀 배정 계산이 명령어 1개로 끝날 수 없으므로, 실행이 안 된 것이다.

JMH의 대응: @Benchmark 메소드의 반환값을 JMH가 Blackhole이라는 객체에 강제로 넘긴다. Blackhole은 "이 값은 나중에 쓰인다"고 컴파일러가 믿을 수밖에 없게 만들어진 소비 장치다. 위 추론의 1번이 성립하지 않게 되어 삭제가 불가능해진다.

### 요인 3. 상수 접기: 입력이 고정이면 답을 미리 구해 박는다

같은 원칙의 다른 적용이다. 컴파일러는 입력이 상수로 확정되면 계산을 실행 시점이 아니라 컴파일 시점에 해 버린다. 가장 단순한 예:

```java
int x = 3 * 4;        // 소스에 쓴 것
int x = 12;           // 컴파일러가 실제로 만드는 것. 곱셈은 실행되지 않는다
```

벤치마크에서 발생하는 잘못된 측정의 형태:

- 상황: `return Math.sqrt(144.0);`처럼 입력이 코드에 박힌 상수다.
- C2의 판단: 결과가 항상 12.0이므로 `return 12.0;`으로 교체.
- 결과: 측정되는 것은 sqrt의 속도가 아니라 상수 하나를 반환하는 시간이다.
- 요인 2와의 관계: 요인 2는 결과를 안 써서 측정 대상이 사라졌고, 요인 3은 입력이 고정이라 사라진다. 나타나는 방향만 다르고 원인은 같다.

JMH의 대응: 입력을 @State 클래스의 필드에 담게 한다. 필드는 실행 중 다른 코드가 값을 바꿀 가능성이 있으므로, 컴파일러가 "항상 144.0"이라고 단정할 수 없어 미리 계산이 불가능해진다.

### 요인 4. 실행 환경의 상호 영향: 측정 순서가 결과를 바꾼다

성격이 다른 하위 문제 두 개를 분리한다.

(a) 프로파일의 영향.

- JIT는 번역할 때 "이 메소드가 지금까지 실제로 어떻게 실행됐는지"의 통계(프로파일)를 근거로 쓴다. 예: 이 if문이 관찰 결과 99% true였다면 true 경로를 빠르게 배치한다.
- 이 통계는 JVM 프로세스 전체에 누적된다.
- 문제: 같은 JVM에서 벤치마크 A를 먼저 돌리고 B를 돌리면, B 시점의 통계에 A의 기록이 섞여서 B를 위해 생성되는 기계어가 "B만 단독으로 돌렸을 때"와 달라진다.
- 결론: 코드는 그대로인데 측정값이 실행 순서에 좌우되면 그 값으로는 아무 결론도 낼 수 없다.

(b) GC의 개입. 가비지 컬렉터는 메모리를 회수할 때 프로그램 실행을 잠시 멈춘다(수 ms). 이 멈춤이 측정 구간 중간에 발생하면 그 구간의 값만 크게 벗어난다. 언제 발생하는지는 제어할 수 없다.

JMH의 대응:

- (a)에는 fork. 벤치마크(그리고 @Param 값)마다 JVM 프로세스를 새로 띄운다. 새 프로세스는 통계가 없는 초기 상태라 이전 벤치마크의 영향이 원천적으로 없다.
- (b)는 제거가 불가능하므로 드러나게 만든다. 측정을 여러 iteration과 여러 fork로 나눠 표본을 여러 개 만들면, GC가 개입한 표본은 다른 표본과 어긋나고 그 어긋남이 결과의 ± Error(신뢰구간)로 나타난다.

### 요약: 요인과 장치의 대응

| 요인 | 본질 | JMH 장치 |
|---|---|---|
| 1. JIT 워밍업 | 루프 초반과 후반이 다른 코드 | 워밍업 iteration (기록 버림) |
| 2. 죽은 코드 제거 | 결과를 안 쓰면 호출 삭제 | Blackhole (반환값 강제 소비) |
| 3. 상수 접기 | 입력이 고정이면 미리 계산 | @State 필드에서 입력 읽기 |
| 4a. 프로파일의 영향 | 먼저 돈 코드의 통계가 뒤에 영향 | fork (새 JVM 프로세스) |
| 4b. GC 개입 | 예측 불가한 멈춤이 일부 표본 값을 크게 흔듦 | 여러 표본과 ± Error로 노출 |

요인 2와 3의 공통 원인("결과만 같으면 바꿔도 된다"는 원칙)만 이해하면 나머지는 전부 그 원칙의 적용 사례다.

## 질문 3. "루프 길이에 따라 평균이 변한다" 부분의 이해 확인

**질문.** 앞 답변의 "루프를 늘리면 평균이 내려간다. 측정값이 코드의 성질이 아니라 루프 길이에 따라 변한다. 이것은 측정이 아니다"라는 부분에 대해, 다음 해석이 맞는지 확인을 요청했다. "서버를 장시간 운영하면 메소드가 여러 번 호출되어 결국 강한 최적화가 적용되므로, 그 진행 정도에 따라 테스트하는 시점마다 결과 값이 달라질 수 있다는 뜻인가." 최적화가 적용되는 기준이 무엇인지도 함께 질문했다.

**답변.** 거의 다 맞게 읽었고, 한 군데가 어긋나 있다.

### 맞게 이해한 부분

1. 반복 호출이 누적되면 결국 강한 최적화(C2) 상태에 도달한다.
2. 알고 싶은 값은 그 도달 이후의 값이다. 서버는 장시간 떠 있으므로 실제 운영 상태가 곧 C2 상태다.

괄호 안의 "최적화 기준"에 대한 답: 기준은 단순히 호출 횟수 카운터다. JVM이 메소드마다 호출 횟수를 세고(루프가 길면 루프 반복 횟수도 센다), 임계값을 넘으면 컴파일 대기열에 넣는다. 기본값 기준 대략 C1은 수백 회, C2는 수천에서 수만 회 수준이고, JVM 옵션으로 조정 가능한 값이라 정확한 숫자를 외울 필요는 없다.

### 어긋난 부분

- 아닌 것: "테스트 시점마다 결과 값이 달라진다."
- 문장이 실제로 말한 것: 시점(언제 돌리느냐)이 아니라 루프 횟수(몇 번 돌려서 평균 내느냐)가 값을 결정한다.
- 예: 같은 코드를 같은 기계에서 같은 날 돌려도, 실험자 A가 10만 회로 평균 내면 162ns, 실험자 B가 100만 회로 평균 내면 106ns가 나온다. 코드는 하나인데 숫자가 둘이다.

원인을 손으로 추적하면, 초반 느린 구간(인터프리터 2,000회와 C1 8,000회, 합쳐서 처음 10,000회)의 비용은 루프를 아무리 늘려도 변하지 않는 고정값이다.

> 고정 비용 = 2,000×2,000ns + 8,000×400ns = 7,200,000ns

루프를 늘리면 늘어나는 것은 C2 구간(1회 100ns)뿐이다.

| 루프 횟수 N | 느린 구간 비용 (고정) | C2 구간 비용 | 평균 = 합계 ÷ N |
|---|---|---|---|
| 100,000 | 7,200,000ns | 90,000회 × 100 = 9,000,000ns | 162.0ns |
| 1,000,000 | 7,200,000ns | 990,000회 × 100 = 99,000,000ns | 106.2ns |
| 10,000,000 | 7,200,000ns | 9,990,000회 × 100 = 999,000,000ns | 100.6ns |

식으로 정리하면 측정값 = 100ns + 6,200,000ns ÷ N. 뒤 항이 초반 구간이 만드는 오차이고, N은 실험자가 마음대로 정하는 수다.

"이건 측정이 아니다"라고 쓴 이유: 측정값이라면 대상(코드)의 성질을 반영해야 하는데, 이 숫자는 실험자가 임의로 고른 설계 파라미터(N)가 값을 결정한다. 재는 사람의 선택에 따라 결과가 달라지는 절차는 측정이라 부를 수 없다는 뜻이다.

### 표에서 하나 더 읽어낼 것

- 수렴: N을 키울수록 값이 100ns로 수렴한다(오차 항 6,200,000/N이 0으로 감). 즉 아주 오래 돌리면 대략 맞는 값이 나오기는 한다.
- JMH의 방식: 이 수렴을 기다리지 않는다. 고정 비용 구간(처음 10,000회)을 측정 범위에서 제외한다.
- 효과: 워밍업이 끝난 뒤부터만 재면 N이 작아도 처음부터 100ns가 나온다. 더 빠르고 더 정확하다.

덧붙여, "시점에 따라 달라지는 문제"도 실존하며 그것은 이 문단(요인 1)이 아니라 요인 4a(프로파일의 영향) 쪽 이야기다. 두 요인을 분리해 둘 것:

- 요인 1: 측정 범위 안에 느린 구간이 섞이는 문제.
- 요인 4a: 이전 실행의 통계가 다음 컴파일 결과를 바꾸는 문제. 같은 JVM에서 먼저 무엇을 돌렸느냐에 따라 나중 측정값이 달라진다.

## 질문 4. 빅오와 실측의 관계, 학습 범위 제한

**질문.** 두 가지 확인을 요청했다. 첫째, "빅오는 코드에서 직접 확인하며 잴 수 없기 때문에 실제 동작 시간을 JMH로 재는 것"이라는 이해가 맞는가. 둘째, 컴파일러 동작이나 C1, C2는 처음 보는 내용인데 별도로 학습해야 하는가. 취업 준비생으로서 포트폴리오의 근거로 쓰는 수준까지만 학습 범위를 제한하려는 의도였다.

**답변.** 판단 자체는 맞고, 이해한 문장 안에 두 개념이 접혀 있어 분리가 필요하다.

### 교정: 빅오와 실측은 별개 작업이다

1. 빅오 도출은 코드에서 손으로 하는 작업이다. 도구가 필요 없다. seedGreedy 기본 버전이면 바깥 루프 N명 × 안쪽 루프 K팀이므로 O(N·K). 우선순위 큐 버전이면 N명 × poll/offer가 log K이므로 O(N log K). 자료구조 문서들에서 해 오던 그 분석이고, 이것이 핵심 작업이다.
2. JMH는 그 도출이 실제로 맞는지 확인하는 실측 도구다. @Param으로 n을 늘려가며 실측 시간의 증가율이 이론과 일치하는지 본다. 추가로 빅오가 원리적으로 못 보는 것, 즉 상수 요인(예: O(N log K)가 O(N·K)를 실제로 이기기 시작하는 K는 몇부터인가)을 보여준다.

즉 "빅오를 잴 수 없어서 JMH를 쓴다"가 아니라, 빅오는 손으로 도출하고 JMH는 그 검증과 상수 확인용이다. 순서도 그 순서다.

### 학습 범위

기준: "JMH 결과를 신뢰할 수 있게 만들고, 설정을 왜 그렇게 했는지 한 줄로 설명할 수 있는 수준"까지.

필요한 것(이미 확보했거나 곧 확보됨).

- 빅오 손 분석. 지금 하고 있는 학습 그 자체.
- JMH 사용법: @Benchmark, @State, @Param, @Setup, fork/warmup/measurement 설정, Score ± Error 읽기.
- 왜곡 4요인은 각각 한 줄 수준이면 충분하다. 워밍업 = JIT 안정화 대기, return = 죽은 코드 제거 방지, @State = 상수 접기 방지, fork = 실행 간 영향 차단.

지금 불필요한 것(별도 주제로 미루기).

- C1/C2 티어 구조의 세부, 컴파일 임계값, 인라이닝, OSR 같은 JVM 내부 동작. 이것은 도구를 쓰는 지식이 아니라 도구가 왜 그렇게 만들어졌는지의 지식이라, JMH를 올바르게 쓰는 데 요구되지 않는다.

포트폴리오 관점에서도 이 경계가 적절하다. 채용 과정에서 보여줄 것은 "계측, 병목 확인, 개선, 재계측으로 개선폭 증명"이라는 과정이고, P0-1의 improve() 전후 비교와 seedGreedy 6버전 비교가 그 과정을 보여줄 실제 사례가 된다. JVM 내부 지식은 이 과정에 등장할 필요가 없다. (이 보류 결정은 협업 메모 CLAUDE.md의 "추후 학습 예정 사항"에 기록했다.)

## 질문 5. 예시 코드와 결과 표의 수치가 각각 무엇인지, 범위 정리

**질문.** 예시로 제시된 어노테이션 코드와 결과 표의 수치들이 각각 무엇을 의미하는지, 그리고 이 도구가 무엇을 어떤 기준으로 어떻게 재는지에 대한 정리를 요청했다. 실측을 진행하면서 하나씩 함께 학습하는 방식이 적절한지도 질문했다.

**답변.** 실측하면서 배우는 방식이 맞다. 실측 전에 "각 숫자가 무엇의 개수이고 무엇의 평균인지"만 확정한다.

### JMH가 재는 것의 정확한 정의

- 무엇을 재나: @Benchmark 메소드 본문 1회 실행.
- 어떻게 재나: 아래 절차로 (정해진 시간 동안의 반복 호출 횟수로 나눔).
- 시간 기준: OS의 고해상도 시계(나노초 단위). 시계는 JMH가 알아서 쓰고 사용자가 건드릴 일이 없다.

측정의 최소 단위부터 쌓으면:

```
invocation  = run() 1회 호출
iteration   = 정해진 시간(예: 1초) 동안 invocation을 최대한 반복. 표본 1개 생산
fork        = JVM 프로세스 1개 (워밍업 iteration들과 측정 iteration들을 수행)
```

iteration 하나가 표본 1개를 만드는 계산이 핵심이다.

> 1초(=1,000,000us) 동안 run()이 73,746번 호출됐다면
> 표본 = 1,000,000 ÷ 73,746 = 13.56 us/op (호출 1회당 평균)

스톱워치로 1회를 재는 것이 아니라, 정해진 시간에 몇 번 도는지를 세서 나누는 방식이다. 1회가 마이크로초 단위라 개별 측정은 오차가 크기 때문이다.

### 예시 코드의 숫자들

| 코드 | 숫자의 의미 |
|---|---|
| `@BenchmarkMode(Mode.AverageTime)` | 보고 형식 선택: 1회당 평균 시간. Throughput이면 같은 측정을 초당 횟수로 뒤집어 보고 |
| `@OutputTimeUnit(MICROSECONDS)` | 보고 단위. us로 표시하라는 것 |
| `@Param({"30", "300", "3000"})` | memberCount에 30을 넣고 전체 측정(fork부터)을 완주, 300으로 다시 완주, 3000으로 다시 완주. 실험 3세트 |
| `@Setup(Level.Trial)` | 이 메소드(데이터 생성)를 fork당 1회, 측정 시작 전에 실행. 여기 걸린 시간은 결과에 안 들어감 |
| `@Fork(2)` `@Warmup(iterations=5, time=1)` `@Measurement(iterations=5, time=1)` | JVM 2개 / 버리는 구간 1초×5 / 재는 구간 1초×5 |

### 출력 표의 숫자들 (한 행이 만들어지는 과정)

| 단계 | 일어난 일 | 산출물 |
|---|---|---|
| 1 | JVM 1번 기동, setup()이 데이터 생성 | 없음 |
| 2 | 워밍업 iteration 1~5 (각 1초). JIT 안정화 대기 | 기록 버림 |
| 3 | 측정 iteration 1: 1초간 run() 반복, 호출 수로 나눔 | 표본 1 |
| 4 | 측정 iteration 2~5 동일 반복 | 표본 2~5 |
| 5 | JVM 1번 종료, JVM 2번으로 1~4 반복 | 표본 6~10 |
| 6 | 표본 10개 집계 | 표의 한 행 |

- (memberCount): 이 행이 실험 3세트 중 어느 세트인지
- Mode avgt: AverageTime의 약자
- Cnt 10: 표본 개수 = fork 2 × 측정 iteration 5
- Score: 표본 10개의 평균
- Error: 99.9% 신뢰구간의 절반 폭. 실용 판정은 Score 대비 몇 %인지로 한다
- Units us/op: 마이크로초 매 호출당

### 범위 정리

1. 개념: 측정 계층(invocation, iteration, fork), Score/Error 읽기, 왜곡 4요인 한 줄씩. 이 문답으로 완료된 범위.
2. 실습: Gradle에 JMH를 붙이고 seedGreedy 벤치마크 1개를 실제로 돌려 출력을 한 줄씩 해석.
3. 적용: @Param으로 n을 바꿔 복잡도 확인, 이후 P0-1 improve() 전후 비교.

이 밖의 것(JVM 내부, 통계 이론의 수학적 근거, JFR/async-profiler 같은 다른 도구)은 전부 보류 목록이다. 매뉴얼 페이지의 JFR, jcmd, async-profiler는 "어디가 느린지 찾는" 프로파일링 도구라 "얼마나 빠른지 재는" JMH와 목적이 다르다. 지금 목적(복잡도 검증)에는 JMH만 있으면 된다.

## 질문 6. invocation, iteration, fork의 뜻

**질문.** invocation, iteration, fork 세 용어의 뜻에 대한 설명을 요청했다. fork는 운영체제 과목에서 접한 기억이 있는 상태였다.

**답변.** 작은 것에서 큰 것 순서로 간다.

### invocation = 메소드 호출 1회

영어 단어 뜻 그대로 "호출"이다. `engine.seedGreedy(sorted, 3, 2);` 이 한 줄이 실행되는 것이 invocation 1회. JMH 문서가 op(operation)라고 부르는 것도 같은 것이다. 결과 단위 us/op은 "invocation 1회당 마이크로초"다.

### iteration = 1초짜리 측정 블록 1개

주의할 것: 일반 프로그래밍에서 iteration은 루프 1바퀴를 뜻하지만, JMH에서는 다른 뜻으로 쓴다.

- 일반 용어: for문 1회전
- JMH 용어: 정해진 시간 동안 invocation을 반복하는 블록 하나 (표본 1개를 만드는 단위)

JMH의 iteration 1개를 명령형 코드로 펼치면 이것이 실체다.

```java
// "측정 iteration 1개 (time=1초)"의 실체
long deadline = 지금시각() + 1_000_000_000L;   // 1초 뒤
long count = 0;

while (지금시각() < deadline) {
    run();          // invocation 1회
    count++;
}
// 1초가 끝나면:
double 표본 = 1_000_000us / count;    // count가 73,746이면 표본 = 13.56 us/op
```

iteration 1개 안에 invocation 수만 개가 들어 있고, iteration이 끝날 때마다 표본 숫자 하나가 나온다.

### fork = JVM 프로세스를 새로 하나 띄우는 것

운영체제 수업에서 들은 것이 맞다. 거기서 fork()는 새 프로세스를 만드는 시스템 콜이었고, JMH의 fork도 같은 계열의 뜻이다. 자바 프로그램(JVM)을 별도 프로세스로 새로 실행한다.

- 프로세스: 실행 중인 프로그램 1개. 각자 독립된 메모리 공간을 가진다.
- 이미 매일 보는 것: IntelliJ에서 Run 버튼을 누르면 java 프로세스가 1개 뜬다. 그것이 JVM 1개다. 작업 관리자에서 java.exe로 보이는 그것.
- `@Fork(2)`의 뜻: 이 벤치마크를 위해 java 프로세스를 2번, 차례로 새로 실행하라. Run 버튼을 두 번 누르는 것과 같은 상황을 JMH가 자동으로 해 준다.

이렇게 하는 이유:

1. 프로세스는 메모리가 독립이므로, JIT의 누적 통계(프로파일)도 그 프로세스 안에만 존재한다.
2. 프로세스를 새로 띄우면 그 통계가 없는 초기 상태에서 시작한다.
3. 따라서 이전 실행의 영향을 지우는 방법이 "프로세스를 버리고 새로 만들기"다.

### 셋을 합친 전체 그림

`@Fork(2)`, 워밍업 5×1초, 측정 5×1초, @Param 값 하나 기준.

```
벤치마크 실행 (memberCount=300)
│
├─ fork 1 ── java 프로세스 1번째를 새로 실행
│    ├─ setup()          : 300명 데이터 생성
│    ├─ 워밍업 iteration 1~5 : 각각 1초 블록 (블록마다 invocation 수만 회). 전부 버림
│    └─ 측정   iteration 1~5 : 각각 1초 블록. 표본 5개
│    (프로세스 종료 = 메모리와 JIT 통계 소멸)
│
└─ fork 2 ── java 프로세스 2번째를 완전히 새로 실행
     └─ 위 과정 전체 반복. 표본 5개 추가

집계: 표본 10개의 평균 = Score, 흩어짐 = ± Error
```

수량으로 확인: invocation 1회가 약 13.56us라면 1초 블록 하나에 약 73,700회, 프로세스 하나가 (5+5)개 블록이면 약 74만 회, fork 2개 합치면 run()이 총 150만 번쯤 호출되고, 그중 결과에 들어가는 것은 측정 블록 10개가 만든 숫자 10개다.

포함 관계 요약: fork(프로세스) ⊃ iteration(1초 블록) ⊃ invocation(호출 1회). 표본은 iteration당 1개, Score는 표본들의 평균.

## 질문 7. 벤치마크 적용 요청과 private 제거의 이유

**질문.** seedGreedy 메소드를 대상으로 벤치마크 적용을 요청했다. 조건은 두 가지였다. 주석 처리된 다른 버전들은 수정하지 않을 것, 현재 활성 버전에만 적용할 것. 이어서 private을 왜 제거해야 하는지, 벤치마크는 어디에서 호출하는 것인지 질문했고, 이 답변을 확인한 뒤에 제거를 진행하도록 했다.

**답변.**

### 누가 호출하며, private이 왜 걸림돌인가

- 호출 주체: 새로 만드는 벤치마크 클래스(SeedGreedyBench). src/jmh/java 아래의 별도 파일이다.
- 구조: JMH는 측정 대상을 @Benchmark가 붙은 메소드 안에서 호출하게 한다.
- TeamFormationEngine 안에 벤치마크 코드를 넣지 않는 이유: 운영 클래스에 측정용 코드와 의존성이 섞인다. 또한 JMH가 벤치마크 클래스를 원본 삼아 래퍼 코드를 생성하므로 분리하는 것이 표준이다.

자바의 접근 제어자 규칙:

| 제어자 | 호출 허용 범위 |
|---|---|
| private | 같은 클래스 안에서만 |
| (없음 = 패키지-프라이빗) | 같은 패키지의 클래스들 |
| protected | 같은 패키지 + 자식 클래스 |
| public | 어디서나 |

- 지금까지 private으로 문제가 없었던 이유: 유일한 호출자인 form()이 같은 클래스 안에 있어서다.
- 문제: SeedGreedyBench는 다른 클래스이므로 private 메소드를 호출하는 코드는 컴파일 자체가 안 된다.
- 해결: private을 지우면 패키지-프라이빗이 되고, 벤치마크 클래스를 같은 패키지(com.exercisemanagement.challenge.service)에 두면 호출할 수 있다.
- 성격: public까지 열 필요가 없는 최소 완화이고, 테스트 접근을 위한 실무 관행이기도 하다.

### 적용한 내용

1. TeamFormationEngine.java: 활성 seedGreedy의 private만 제거(패키지-프라이빗화). 헤더 주석에 사유 한 줄 추가. 주석 처리된 버전 2~6은 요청대로 건드리지 않음. 나중에 다른 버전으로 교체할 때는 그 버전의 private도 지워야 벤치마크가 돈다.
2. build.gradle: me.champeau.jmh 플러그인(0.7.2)과 jmh 설정 블록(jmhVersion 1.37, 중복 리소스 충돌 방지) 추가.
3. SeedGreedyBench.java 신규 작성 (src/jmh/java, 같은 패키지): @Param N = 30/300/3000, K = 3 고정, @Fork(2), 워밍업 5×1초, 측정 5×1초. 각 줄에 존재 이유를 주석으로 기록. (전문은 실측 보고서 4.3절 참조)

실행 방법: IntelliJ에서 Gradle 새로고침 후, 프로젝트 루트 터미널에서 `gradlew jmh`. 예상 소요는 3파라미터 × 2포크 × 10초로 약 2분 내외. 결과에서 볼 것은 memberCount 30 → 300 → 3000 행의 Score가 약 10배씩 커지는지(O(N) 검증)와 Error가 Score의 몇 %인지.

## 질문 9. 측정 결과 전체에 대한 설명 요청

**질문.** 측정이 완료된 터미널 화면을 공유하고, 결과 전체에 대한 설명을 요청했다.

**답변.**

### 최종 결과 표와 복잡도 판정

```
Benchmark          (memberCount)  Cnt   Score    Error  Units
SeedGreedyBench.run           30   10   0.391 ±  0.020  us/op
SeedGreedyBench.run          300   10   4.276 ±  0.302  us/op
SeedGreedyBench.run         3000   10  46.940 ±  0.732  us/op
```

| 구간 | N 증가 | Score 증가 | 판정 |
|---|---|---|---|
| 30 → 300 | ×10 | 4.276 ÷ 0.391 = ×10.9 | 선형 |
| 300 → 3000 | ×10 | 46.940 ÷ 4.276 = ×11.0 | 선형 |

- 판정: N을 10배 늘릴 때 시간이 약 10배씩 늘었다. O(N) 검증 성공(K=3 고정이므로 O(N·K)의 N축 확인).
- 10이 아니라 10.9~11.0인 이유: 데이터가 커지면 CPU 캐시 적중률 하락, 객체 할당 증가 같은 하드웨어 수준 효과가 더해진다.
- 의미: 빅오는 이런 상수 요인을 원리적으로 안 보므로, 이 초과분이 실측이 빅오에 더해서 보여주는 것이다.

Error 품질: 0.020/0.391 = 5%, 0.302/4.276 = 7%, 0.732/46.940 = 1.6%. 전부 양호. 이 숫자들은 믿어도 된다.

### Result 블록의 통계 용어

```
46.940 ±(99.9%) 0.732 us/op [Average]
(min, avg, max) = (46.378, 46.940, 47.767), stdev = 0.484
CI (99.9%): [46.209, 47.672]
```

전부 표본 10개(Cnt 10 = fork 2 × 측정 iteration 5)에 대한 요약이다. min/avg/max는 표본 10개 중 최소/평균/최대. stdev는 표준편차(표본들의 흩어짐 정도). CI는 신뢰구간인데 Score ∓ Error다. 46.940 − 0.732 = 46.209, 46.940 + 0.732 = 47.672. 읽는 법: "참값은 이 사이에 있다고 봐도 된다(99.9% 신뢰)".

### 로그에서 이론이 그대로 보이는 지점

```
# Fork: 2 of 2
# Warmup Iteration   1: 64.414 us/op    ← 첫 1초 블록: 아직 JIT 컴파일 진행 중
# Warmup Iteration   2: 46.255 us/op    ← 컴파일 완료, 안정 상태 진입
```

- 64.4에서 46.3으로 떨어지는 순간이 요인 1(JIT 워밍업)이 실시간으로 보인 것이다.
- fork 2는 새 JVM이라 컴파일을 처음부터 다시 하므로 첫 블록이 다시 느리다. fork가 왜 초기 상태에서 시작하는지도 여기서 확인된다.
- 워밍업 5개를 버렸기 때문에 측정 블록들은 전부 46~48 사이에서 안정적이다.

`# Run progress: 83.33% complete`: 전체 실행 = 3파라미터 × 2포크 = 6개 단위, 83.33% = 5/6 완료 시점. 총 소요 1분 25초.

### 나머지 출력물

- REMEMBER 문단: JMH가 항상 붙이는 정형 경고. "숫자는 데이터일 뿐, 왜 그런지는 따로 파악하라."
- NOTE (Compiler Blackholes): Blackhole을 이 JVM이 컴파일러 수준에서 지원해 더 정확하다는 안내. 조치 불필요.
- 결과 파일: `build\results\jmh\results.txt`에 표가 저장됐다.
- Deprecated Gradle features 경고: 플러그인들이 쓰는 구식 API 알림. 빌드에 영향 없음.
- `us/opNG` 같은 표기는 콘솔 출력이 겹쳐 찍힌 것이다. (정확한 원인은 질문 19에서 확정)

### 다음 단계 제안

N축(선형)은 확인됐으니 다음 의미 있는 실험은 K축이다. 활성 버전은 사람마다 팀 전체를 스캔(O(K))하지만 버전 2(우선순위 큐)는 O(log K)라, K를 4 → 64 → 1024로 키우면 두 버전의 차이가 벌어지는 것이 보인다. 버전 6개를 만들어 둔 이유이기도 하다.

## 질문 11. 워밍업이 구체적으로 무엇인가

**질문.** 진행 로그 구간에 나오는 워밍업이 구체적으로 무엇인지 설명을 요청했다.

**답변.**

### 정의와 오해 교정

워밍업 = 측정 시작 전에, 측정 대상 코드를 결과 기록 없이 그냥 실행만 하는 구간.

가장 중요한 사실: 워밍업 블록과 측정 블록은 하는 일이 완전히 동일하다. 둘 다 1초 동안 run()을 최대한 반복 호출하고, 둘 다 "경과 시간 ÷ 호출 횟수"를 계산해서 화면에 찍는다. 유일한 차이는 하나뿐이다.

| | 워밍업 iteration | 측정 iteration |
|---|---|---|
| 동작 | 1초간 run() 반복 | 1초간 run() 반복 (동일) |
| 값 계산 | 함 | 함 (동일) |
| 최종 집계(Score) 포함 | 안 함 (버림) | 함 (표본) |

즉 워밍업이라는 특수한 준비 동작이 따로 있는 것이 아니다. 워밍업 = 버려지는 측정이다. 로그에서 `#` 붙은 Warmup 줄에도 숫자가 찍히는 이유가 이것이다.

### 왜 "그냥 실행"이 준비가 되는가

1. JVM은 메소드마다 호출 횟수 카운터를 갖고 있다.
2. 호출될 때마다 카운터 증가. 임계값을 넘으면 컴파일 요청이 들어간다.
3. 컴파일은 백그라운드에서 진행되고, 끝나면 그다음 호출부터 기계어(빠른 코드)로 실행된다.

핵심: 컴파일을 일으키는 유일한 방법이 "많이 호출하는 것"이다. JVM에 "이 메소드 미리 컴파일해 둬"라고 지시하는 스위치는 없다(일반적인 사용에서는). 그래서 준비 방법도 실행뿐이고, 그 실행 구간이 워밍업이다.

### 실제 로그로 추적 (fork 2 구간)

```
# Fork: 2 of 2                          ← 새 JVM. 카운터도 컴파일 결과도 없는 초기 상태
# Warmup Iteration   1: 64.414 us/op    ← 이 1초 안에서 컴파일이 일어나는 중
# Warmup Iteration   2: 46.255 us/op    ← 컴파일 완료. 이후 전부 기계어 실행
# Warmup Iteration   3: 46.438 us/op
# Warmup Iteration   4: 46.605 us/op
# Warmup Iteration   5: 48.510 us/op    ← 약간 벗어남 (GC 등 일시 간섭으로 추정)
Iteration   1: 47.767 us/op             ← 측정 시작. 워밍업 후반과 같은 수준
```

Warmup 1의 64.414가 나온 과정을 그 1초 블록 내부로 쪼개면:

- 앞부분 호출들: 인터프리터와 C1(컴파일 진행 중)이라 느림.
- 뒷부분 호출들: C2 기계어라 빠름(약 47us).
- 블록 평균: 그 둘이 섞여 64.414.
- Warmup 2부터: 1초 내내 기계어만 실행되므로 46~48에서 안정.
- 호출 횟수로도 확인된다: 64.414us/op이면 1초에 약 15,500회, 안정 후 46.9us/op이면 약 21,300회. 같은 1초인데 도는 횟수가 다르다.

질문 3에서 표로 계산했던 "고정 비용 구간을 측정 범위에서 제외한다"가 실제로 일어난 것이다. 느린 구간은 Warmup 1 안에서 끝났고, 측정은 전부 안정 상태만 쟀다.

### 충분/부족 판단법

- 충분: 워밍업 후반 값들이 서로 비슷하고(수렴), 측정값과 같은 수준. 이번 로그가 정확히 이 경우다.
- 부족: Warmup 5까지도 값이 계속 내려가는 중이면, 컴파일이 덜 끝난 상태로 측정에 들어간 것. @Warmup(iterations = 10) 등으로 늘리고 다시 돈다.

### 설정과의 대응

`@Warmup(iterations = 5, time = 1)`: iterations = 5가 로그의 Warmup Iteration 1~5, time = 1이 블록 하나의 길이 1초. fork마다 워밍업을 처음부터 다시 하는 이유는 새 JVM 프로세스는 카운터와 컴파일 결과가 없는 초기 상태이기 때문이다. fork 2의 Warmup 1이 다시 64로 커진 것이 그 증거다.

## 질문 12. us/op이 무엇인가

**질문.** us/op 표기가 무슨 뜻인지 질문했다.

**답변.** 단위 표기다. 분해하면:

- us = 마이크로초(microsecond). 원래 기호는 µs인데 콘솔에서 그리스 문자 µ를 못 찍어서 u로 대체한 것. 어디서 정해졌나: 벤치마크 클래스의 @OutputTimeUnit(TimeUnit.MICROSECONDS).
- op = operation = @Benchmark 메소드 1회 실행. invocation과 같은 것.
- / = "매 ~당".

따라서 46.940 us/op = "run() 1회 실행에 평균 46.940마이크로초".

| 단위 | 크기 | 46.940us를 환산하면 |
|---|---|---|
| s (초) | 1 | 0.00004694 s |
| ms (밀리초) | 1/1,000 초 | 0.04694 ms |
| us (마이크로초) | 1/1,000,000 초 | 46.940 us |
| ns (나노초) | 1/1,000,000,000 초 | 46,940 ns |

역산으로 확인: 1회에 46.94us면 1초(=1,000,000us)에 1,000,000 ÷ 46.94 ≈ 21,300회. us/op(1회당 시간)와 "1초당 횟수"는 서로 역수 관계고, @BenchmarkMode를 Throughput으로 바꾸면 후자로 찍힌다. 같은 측정의 표기 방향만 다른 것.

## 질문 13. Result 블록의 숫자를 표본에서 직접 재현

**질문.** 1번 항목(진행 로그 구간)은 어려운 내용이 없음을 확인하고, 다음 항목으로 진행을 요청했다.

**답변.** 1번이 정리됐으므로 2번(Result 블록)으로 넘어간다. 여기가 이 출력에서 유일하게 계산이 들어가는 곳이고, 화면에 표본 10개가 전부 찍혀 있어서 Result 블록의 모든 숫자를 직접 재현할 수 있다.

### 사용할 표본 10개 (memberCount=3000)

| # | 출처 | 값 (us/op) |
|---|---|---|
| 1 | fork 1, Iteration 1 | 47.726 |
| 2 | fork 1, Iteration 2 | 46.494 |
| 3 | fork 1, Iteration 3 | 47.091 |
| 4 | fork 1, Iteration 4 | 46.644 |
| 5 | fork 1, Iteration 5 | 46.878 |
| 6 | fork 2, Iteration 1 | 47.767 |
| 7 | fork 2, Iteration 2 | 46.378 |
| 8 | fork 2, Iteration 3 | 46.537 |
| 9 | fork 2, Iteration 4 | 47.031 |
| 10 | fork 2, Iteration 5 | 46.858 |

### avg (= Score) 재현

> 합 = 469.404, 469.404 ÷ 10 = 46.940 (Result 블록의 46.940과 일치)

### min, max 재현

- min = 표본 7의 46.378
- max = 표본 6의 47.767

10개 중 최소와 최대다.

### stdev(표준편차) 재현

각 표본이 평균(46.940)에서 얼마나 떨어졌는지(편차)를 구하고 제곱해서 합친다.

| # | 값 | 편차 = 값 − 46.940 | 편차² |
|---|---|---|---|
| 1 | 47.726 | +0.786 | 0.617 |
| 2 | 46.494 | −0.446 | 0.199 |
| 3 | 47.091 | +0.151 | 0.023 |
| 4 | 46.644 | −0.296 | 0.088 |
| 5 | 46.878 | −0.062 | 0.004 |
| 6 | 47.767 | +0.827 | 0.683 |
| 7 | 46.378 | −0.562 | 0.316 |
| 8 | 46.537 | −0.403 | 0.163 |
| 9 | 47.031 | +0.091 | 0.008 |
| 10 | 46.858 | −0.082 | 0.007 |

> 편차² 합 = 2.108, 2.108 ÷ 9 = 0.234, √0.234 = 0.484 (Result 블록의 stdev와 일치)

10이 아니라 9로 나누는 것은 "표본으로 추정할 때는 n−1로 나눈다"는 통계 관례다. 지금은 관례로만 받아들이면 된다.

읽는 법: stdev 0.484 = 표본들이 평균에서 평균적으로 ±0.5us쯤 흔들렸다. 평균 46.9 대비 1%로 매우 고른 측정.

### Error(± 0.732) 재현

공식: Error = 상수 × stdev ÷ √표본수

- stdev ÷ √10 = 0.484 ÷ 3.162 = 0.153
- 상수 = 4.78 (통계표에서 "신뢰수준 99.9%, 표본 10개"에 해당하는 값. 외울 필요 없음)
- 0.153 × 4.78 = 0.732 (Result 블록의 ±0.732와 일치)

직관: 표본이 많을수록(√n으로 나눔), 표본이 고를수록(stdev가 작을수록) Error가 작아진다. 측정을 더 믿게 만드는 방법이 "더 많이, 더 고르게"라는 뜻이다.

### CI 재현

> 46.940 − 0.732 = 46.209, 46.940 + 0.732 = 47.672 → [46.209, 47.672] (일치)

### 결론

Result 블록의 숫자 전부(46.940, 46.378, 47.767, 0.484, 0.732, [46.209, 47.672])가 화면에 찍힌 Iteration 줄 10개에서 산수로 그대로 재현됐다. 신비한 것이 하나도 없다. JMH는 측정 블록 10개의 숫자를 모아 평균, 최소, 최대, 표준편차, 신뢰구간을 계산해 주는 것뿐이다.

## 질문 14. Result 블록 세 줄의 해석

**질문.** "2. Result 블록 (파라미터 하나가 끝날 때마다 나오는 요약)" 항목에 대한 설명을 요청했다.

**답변.**

### 이 블록은 무엇인가

파라미터 값 하나(예: memberCount=3000)의 fork 2개가 모두 끝난 직후, 그 파라미터의 표본 10개를 요약해서 찍는 중간 결산이다. 파라미터가 3개니까 이 블록도 실행 중 3번 나왔고, 맨 끝의 최종 표는 이 블록 3개를 한 줄씩으로 압축한 것이다. Result 블록이 상세판, 최종 표가 요약판이며 같은 데이터다.

### 1줄: 무엇을 쟀고, 결론값은 얼마인가

```
Result "com.exercisemanagement.challenge.service.SeedGreedyBench.run":
  46.940 ±(99.9%) 0.732 us/op [Average]
```

| 조각 | 의미 |
|---|---|
| `"...SeedGreedyBench.run"` | 어느 벤치마크 메소드의 결산인지 |
| `46.940` | 표본 10개의 평균. 이 블록의 결론값이고 최종 표의 Score로 그대로 간다 |
| `±(99.9%) 0.732` | 오차 폭(Error). 괄호의 99.9%는 계산에 쓴 신뢰수준 |
| `us/op` | 단위 |
| `[Average]` | 집계 방식 라벨. @BenchmarkMode(AverageTime)를 썼다는 표시 |

### 2줄: 표본 10개가 어떻게 흩어져 있었나

```
  (min, avg, max) = (46.378, 46.940, 47.767), stdev = 0.484
```

| 조각 | 의미 | 용도 |
|---|---|---|
| min 46.378 | 표본 중 최솟값 | min~max 폭으로 크게 벗어난 표본이 있었는지 확인 |
| avg 46.940 | 평균 (1줄의 결론값과 동일) | 없음 |
| max 47.767 | 최댓값 | 폭 = 1.389us, 평균 대비 3%로 벗어난 표본 없음 |
| stdev 0.484 | 표준편차 | 흩어짐의 표준 요약 |

min/max를 같이 주는 이유: 평균과 stdev만으로는 표본 하나가 크게 벗어났는지가 안 보일 수 있다. GC가 측정 블록 하나에 개입하면 max만 커진다. 그것을 확인하는 용도다.

### 3줄: 결론값을 구간으로 다시 쓴 것

```
  CI (99.9%): [46.209, 47.672] (assumes normal distribution)
```

| 조각 | 의미 |
|---|---|
| CI | Confidence Interval, 신뢰구간 |
| [46.209, 47.672] | 46.940 ∓ 0.732. 1줄의 "46.940 ± 0.732"를 구간 형태로 펼쳐 쓴 것. 새 정보 아님 |
| 읽는 법 | 같은 조건으로 다시 측정해도, 진짜 평균은 이 구간 안에 있다고 99.9% 수준으로 신뢰 |
| (assumes normal distribution) | 구간 계산의 가정 각주. 표본이 평균을 중심으로 대칭(종 모양)으로 흩어진다고 가정했다는 뜻. 표본이 심하게 비대칭이면 구간이 부정확해질 수 있어서 2줄의 min/max를 함께 본다 |

### 실전 독법 (보는 순서)

1. Score (46.940): 결론값
2. Error ÷ Score (0.732 ÷ 46.940 = 1.6%): 10% 미만이면 신뢰
3. min~max 폭 (1.389us, 3%): 크게 벗어난 표본이 없는지 확인

세 검사를 모두 통과했으므로 이 측정은 문제가 없다. 나머지 항목들은 위 세 판단의 근거 자료이므로 이상이 있을 때만 확인한다.

## 질문 15. 신뢰구간(Confidence Interval)이 무슨 말인가

**질문.** 신뢰구간(Confidence Interval)이 무슨 뜻인지 질문했다.

**답변.**

### 출발 문제: 46.940은 참값이 아니다

표본 10개는 46.378 ~ 47.767 사이에서 흔들렸다. 같은 코드, 같은 기계인데 흔들리는 이유는 통제 불가능한 잡음이 매 순간 다르게 개입하기 때문이다:

- OS가 다른 프로그램에 CPU를 잠깐 넘긴다.
- GC가 개입한다.
- CPU 온도에 따라 클럭이 바뀐다.

여기서 개념 두 개를 분리한다.

| 개념 | 값 | 알 수 있나 |
|---|---|---|
| 표본 평균 | 46.940 | 계산됨. 그러나 벤치마크를 다시 돌리면 매번 조금씩 다른 값이 나온다 |
| 참 평균 | ? | 잡음이 전부 상쇄되도록 무한히 측정했을 때 나올 값. 영원히 정확히는 알 수 없다 |

정말 알고 싶은 것은 참 평균인데, 확보한 것은 표본 10개뿐이다.

### 신뢰구간 = 참값을 점이 아니라 범위로 답하는 방식

참값을 정확히 제시하지 못하는 대신 이렇게 답한다. "참 평균이 정확히 몇인지는 모른다. 하지만 [46.209, 47.672] 이 범위 안 어딘가에 있다." 이 범위가 신뢰구간이다.

- 계산: 표본 평균 ∓ Error. Error는 표본들의 흩어짐(stdev)과 개수(√n)에서 나왔다.
- 직관: 표본들이 심하게 흔들렸으면 참값이 어디 있는지 자신이 없으니 범위를 넓게 잡고, 고르게 나왔으면 좁게 잡는다.

### "99.9%"의 뜻

실용 독법: "참값이 이 구간 안에 있다는 주장이 틀릴 가능성이 0.1%". 일상적으로는 이렇게 읽으면 된다.

정확한 뜻: 확률이 걸리는 대상은 참값이 아니라 절차다.

- "측정 10개를 모아서 구간을 만든다"는 절차를 1,000번 반복하면 구간이 1,000개 나온다.
- 그중 약 999개는 참값을 포함하고 1개쯤은 빗나간다. 이 절차의 성공률이 99.9%라는 뜻이다.
- 참값은 움직이지 않고, 구간이 실험마다 조금씩 다르게 그려진다.

### 왜 배우나 (실용 두 가지)

1. 정밀도 표시. 구간 폭이 좁다 = 측정이 정밀하다. "Error가 Score의 10% 미만인지 보라"던 규칙이 이 폭 검사다.
2. 비교 판정. 버전 1과 버전 2를 비교할 때의 판정 규칙.

| 상황 | 예 | 판정 |
|---|---|---|
| 두 구간이 안 겹침 | 버전 1: [46.2, 47.7] / 버전 2: [31.0, 32.1] | "버전 2가 빠르다"고 말할 수 있음 |
| 두 구간이 겹침 | 버전 1: [44, 49] / 버전 2: [46, 51] | 차이가 잡음 수준. 빠르다고 단정하면 안 됨 |

Score만 보면 차이가 있어 보여도, 구간이 겹치면 그 차이는 측정 잡음일 수 있다. 신뢰구간은 "이 차이가 진짜냐 잡음이냐"를 가르는 도구다.

### 한 줄 요약

신뢰구간 = "표본으로는 참값을 확정할 수 없다. 대신 참값이 있을 범위를 제시하고, 그 제시가 틀릴 확률(0.1%)까지 같이 명시한다"는 통계의 표준 답변 형식이다.

### 우리 상황에 대입

| 권고 | 우리 상태 |
|---|---|
| 2. 왜를 추적 | 충족. 측정 전에 코드에서 O(N·K)를 도출했고 측정은 그 검증이었다. 초과분(캐시 효과)도 짚었다 |
| 3. 프로파일러 | 보류 목록. JFR, async-profiler가 이것인데 "어디가 느린지 찾기"가 필요해질 때(P0-1 본격화) 쓴다 |
| 4. 요인 실험 | 진행 중인 방식 그대로. 이번엔 K 고정에 N만 이동, 다음엔 N 고정에 K 이동 |
| 5. baseline/negative | 나중에 버전 비교 때 적용 가능. 같은 버전을 두 번 측정해 구간이 겹치는지 확인(negative) |

## 질문 17. 최종 결과 표의 컬럼별 해석

**질문.** "5. 최종 결과 표" 항목을 컬럼 단위로 하나씩 설명해 달라고 요청했다.

**답변.**

### 이 표는 무엇인가

Result 블록 3개(파라미터 값마다 하나씩)를 한 줄씩으로 압축해 모은 요약판이다. 한 행 = 파라미터 값 하나에 대한 실험 전체(fork 2개, 표본 10개 포함). 실행이 아무리 길어도 마지막엔 이 표만 남고, `build\results\jmh\results.txt`에 저장되는 것도 이것이다.

```
Benchmark            (memberCount)  Mode  Cnt   Score    Error  Units
SeedGreedyBench.run             30  avgt   10   0.391 ±  0.020  us/op
SeedGreedyBench.run            300  avgt   10   4.276 ±  0.302  us/op
SeedGreedyBench.run           3000  avgt   10  46.940 ±  0.732  us/op
```

### 컬럼 하나씩

| 컬럼 | 이 값이 정해진 곳 | 의미 |
|---|---|---|
| Benchmark | @Benchmark를 붙인 메소드 | 측정 대상의 이름. 벤치마크 메소드를 여러 개 만들면 이름별로 행이 늘어난다 |
| (memberCount) | @Param. 필드 이름이 그대로 컬럼 제목이 됨 | 이 행이 어느 파라미터 값의 실험인지. 괄호가 파라미터 컬럼이라는 표시. @Param 필드를 하나 더 만들면 괄호 컬럼이 하나 더 생기고, 행 수는 두 파라미터의 조합 수만큼 늘어난다 |
| Mode | @BenchmarkMode(Mode.AverageTime) | avgt = AverageTime의 축약. 다른 선택지는 thrpt(초당 횟수), sample, ss(1회성) |
| Cnt | fork 수 × 측정 iteration 수 = 2 × 5 | Score 계산에 들어간 표본 개수. 워밍업 10개는 안 들어감 |
| Score | 표본 10개의 평균 (Result 블록 1줄의 값 그대로) | 표에서 가장 중요한 값. 호출 1회당 평균 시간 |
| ± | 구분 기호 | 데이터 아님 |
| Error | 상수 × stdev ÷ √10 (질문 13에서 0.732를 재현한 그 계산) | 신뢰구간의 절반 폭 |
| Units | @OutputTimeUnit + 모드 | us/op. 모드가 thrpt였다면 단위가 역수로 뒤집힌다 |

컬럼 8개 중 측정에서 나온 숫자는 Score와 Error 둘뿐이고, 나머지 6개는 전부 "이 숫자가 어떤 조건에서 나왔는지"를 밝히는 정보다.

### 행 읽기

1. 1행: N=30일 때 seedGreedy 1회 = 평균 0.391us (±0.020)
2. 2행: N=300일 때 4.276us (±0.302)
3. 3행: N=3000일 때 46.940us (±0.732)

### 이 표로 하는 일 두 가지

신뢰도 검사 (Error ÷ Score):

| 행 | 계산 | 판정 |
|---|---|---|
| 30 | 0.020 ÷ 0.391 = 5.1% | 양호 |
| 300 | 0.302 ÷ 4.276 = 7.1% | 양호 |
| 3000 | 0.732 ÷ 46.940 = 1.6% | 양호 |

복잡도 판정 (행 간 Score 비율):

| 구간 | N | Score | 비율 |
|---|---|---|---|
| 1행 → 2행 | ×10 | 0.391 → 4.276 | ×10.9 |
| 2행 → 3행 | ×10 | 4.276 → 46.940 | ×11.0 |

N이 10배가 될 때 시간이 10.9~11.0배. 선형(O(N)) 확인. O(N²)였다면 약 100배씩, O(N log N)이었다면 약 12~13배쯤 나왔을 것이다.

### 버전 비교 때 이 표의 모양 (예고)

벤치마크 메소드 2개 × @Param teamCount 3개 값으로 돌리면 행 6개짜리 표가 된다. 행끼리 Score를 비교하되, 신뢰구간([Score−Error, Score+Error])이 겹치면 차이로 인정하지 않는다.

## 질문 18. Error가 이해되지 않는 이유의 진단

**질문.** Error 항목이 여전히 이해되지 않는 상태에서, 이해되지 않는 이유가 무엇인지 진단을 요청했다.

**답변.** 짚이는 원인이 두 개 있다.

### 원인 1: 단어가 다른 뜻으로 읽히고 있다

프로그래머에게 error는 "오류(무엇인가 잘못됨, 빨간 글씨)"다. 그런데 이 표의 Error는 오류가 아니라 "오차(측정의 불확실한 정도)"다. 같은 영어 단어의 전혀 다른 두 번역이고, 매일 보는 앞쪽 뜻으로 계속 읽고 있을 가능성이 크다.

| | 오류 (error) | 오차 (error) |
|---|---|---|
| 뜻 | 무엇인가 잘못됨 | 잘못된 것 없음. 측정값이 원래 갖는 흔들림의 폭 |
| 값이 있다는 것은 | 나쁜 신호 | 정상. 모든 측정에는 오차가 있다 |
| 0이 되나 | 되어야 함 | 현실에서는 0이 되지 않는다 (잡음은 항상 있으므로) |

표의 Error 0.732는 "실패 0.732개"가 아니라 "측정값의 흔들림 폭이 0.732us"라는 뜻이다. 아무것도 잘못되지 않았다.

### 원인 2: "측정값이 숫자 두 개"라는 형식 자체가 낯설다

일상에서 측정은 숫자 하나다("몸무게 70kg"). 그런데 과학과 공학의 측정 보고는 항상 숫자 두 개다. 값 하나, 그리고 그 값을 얼마나 믿어도 되는지 하나.

체중계로 확인하면 바로 잡힌다. 세 번 올라가면 70.1, 70.4, 70.2처럼 매번 조금 다르게 나온다. 누가 몸무게를 물으면 자연스럽게 이렇게 답하게 된다. "70.2 정도. 잴 때마다 ±0.2 안에서 조금씩 다르게 나온다."

- "70.2 정도" = Score (여러 번 잰 것의 평균)
- "±0.2 안" = Error (흔들림의 폭)

JMH 표의 46.940 ± 0.732는 이 문장을 표 형식으로 쓴 것이다. "1회당 평균 46.940us 걸리고, 흔들림 폭은 ±0.732 이내다."

### Error가 어디서 나오는지 한 줄로

표본 10개는 서로 일치하지 않았다(46.378 ~ 47.767). Error는 그 불일치의 정도를 숫자 하나로 요약한 것이다. 극단으로 확인하면:

- 표본 10개가 전부 정확히 46.940이었다면: Error는 0에 가깝다 (완벽히 재현되는 측정).
- 표본이 20 ~ 80 사이에서 크게 흔들렸다면: Error가 수십이 된다 (이 평균은 믿을 수 없다).

계산식(stdev, √n, 신뢰수준)은 이 요약을 만드는 절차일 뿐이다. 남겨야 할 것은 하나다.

> Error = Score를 얼마나 믿어도 되는가. 작을수록 확실.

## 질문 19. 원본 텍스트 재검증

**질문.** 스크린샷 전달 과정에서 값을 부정확하게 읽었을 가능성이 있어, 콘솔 출력의 원본 텍스트를 다시 전달하고 재검증을 요청했다.

**답변.** 확인 결과, 이전 분석에 사용한 숫자는 전부 원본과 일치한다.

- 최종 표: 0.391 / 4.276 / 46.940, Error 0.020 / 0.302 / 0.732. 일치.
- N=3000의 표본 10개와 Result 블록의 min/avg/max/stdev/CI: 일치.
- 그 표본으로 손 재현한 계산(질문 13): 유효.

정정 1개와 새로 보이는 정보가 있다.

### 정정: 깨진 표기의 원인

`us/opING`, `us/opNG`, `us/ops]`가 무엇인지 텍스트로 확정됐다.

- 원인: Gradle이 콘솔 맨 아래에 상태 줄(`> EXECUTING [27s]` 형태)을 계속 덮어쓰는데, JMH 출력이 그 줄 위에 찍히면서 상태 줄의 끝부분(`ING [27s]`, `NG [1m 9s]`, `s]`)이 지워지지 않고 남았다.
- 실제 JMH 출력: `0.380 us/op`까지다.
- 정정: `[27s]`를 앞서 "벤치마크 누적 경과 시간"이라고 설명했는데, 정확히는 Gradle 빌드의 경과 시간(상태 줄의 남은 부분)이다. 값의 의미는 비슷하지만 출처가 JMH가 아니라 Gradle이다.

### 처음 보인 상단부

빌드 단계:

```
> Task :jmhRunBytecodeGenerator
Processing 1 classes from ...build\classes\java\jmh with "reflection" generator
Writing out Java source to ...build\jmh-generated-sources ...
```

"JMH가 벤치마크 클래스를 원본 삼아 래퍼 코드를 생성한다"는 설명이 실제로 확인되는 부분이다. SeedGreedyBench 1개를 읽어 측정용 자바 소스를 build\jmh-generated-sources에 만들었다. test 클래스 폴더도 스캔했지만(플러그인 기본 동작) @Benchmark가 없어 결과물 없음.

파라미터 구간마다 반복되는 `#` 헤더 블록:

| 줄 | 의미 |
|---|---|
| `# JMH version: 1.37` | build.gradle의 jmhVersion 그대로 |
| `# VM version: JDK 17.0.11, HotSpot` | 측정에 쓰인 실제 JVM. 비교는 같은 JVM끼리만 해야 하므로 기록해 둘 값 |
| `# VM invoker: C:\...\jdk-17\bin\java.exe` | fork로 실행한 java 실행 파일 경로 |
| `# VM options: -Dfile.encoding=x-windows-949 ...` | fork JVM에 걸린 옵션들 (한국어 Windows 환경 설정값) |
| `# Blackhole mode: compiler (auto-detected...)` | NOTE 문단이 말하던 것. Blackhole을 컴파일러 수준으로 자동 적용 중 |
| `# Timeout: 10 min per iteration` | 블록 하나가 10분을 넘기면 강제 중단하는 안전장치 |
| `# Threads: 1 thread` | 단일 스레드 측정 |
| `# Benchmark mode: Average time, time/op` | avgt 모드 확인 |
| `# Parameters: (memberCount = 30)` | 이 구간이 어느 파라미터 세트인지 |

### 전체 텍스트에서 새로 보인 관찰 3개

1. fork 간 차이의 실제 사례 (N=30). fork 1 표본 평균 약 0.379, fork 2 약 0.403으로 약 6% 차이. 같은 코드라도 JVM 프로세스에 따라 JIT 컴파일 결과가 조금씩 달라질 수 있다는 직접 증거이고, fork를 2개 이상 두고 섞어 평균 내는 이유다. fork 1개짜리 측정이었다면 0.379나 0.403 중 하나를 "그 값"으로 믿었을 것이다.
2. 크게 벗어난 값이 워밍업 구간에서 걸러진 사례 (N=30, fork 1). Warmup Iteration 4에서 0.889가 찍혔다(평소 0.37~0.46의 2배 이상, GC나 백그라운드 간섭 추정). 워밍업 구간이라 그대로 버려졌다. 측정 블록에 들어갔다면 Error를 키웠을 값이다.
3. JIT 하락이 fork 1에서도 확인 (N=3000). 66.959 → 46.447. fork 2(64.414 → 46.255)와 같은 패턴. 두 fork 모두 첫 워밍업 블록만 느리고 즉시 안정. 워밍업 5개가 충분하다는 재확인.

### 결론은 그대로

증가율 ×10.9, ×11.0으로 O(N) 판정, Error 비율 5.1% / 7.1% / 1.6%로 신뢰 가능. 원본 텍스트로 바뀌는 결론은 없다. N=300이 셋 중 가장 오차가 컸는데(Error 7.1%, fork 1 초반 4.5~4.7us) 이 정도는 정상 범위다.

## 부록 B. 보류한 학습 범위

의도적으로 미룬 주제들. JMH를 올바르게 쓰는 데는 필요하지 않다고 판단했다.

1. JVM JIT 내부 동작: 티어드 컴파일 C1/C2의 세부, 컴파일 임계값, 인라이닝, OSR. 필요 수준(왜곡 4요인 각 한 줄)은 이미 확보.
2. 통계 이론의 수학적 근거: 표준편차를 n−1로 나누는 이유, 신뢰구간 상수(4.78)의 유도, 정규분포 가정의 성립 조건.
3. 프로파일링 도구: JFR, jcmd, async-profiler. "어디가 느린지 찾기"가 필요해지는 P0-1 본격화 때 학습.

## 부록 C. 다음 단계

1. K(팀 수)를 파라미터로 하는 실험으로 버전 1(선형 스캔, O(K))과 버전 2(우선순위 큐, O(log K))를 비교. 판정은 신뢰구간 겹침 여부로 한다.
2. P0-1 improve() 최적화 전후 비교.
3. 측정 환경 수칙 적용: 전원 연결, 무거운 프로그램 종료, 비교 대상은 같은 세션에서 연달아 측정.
