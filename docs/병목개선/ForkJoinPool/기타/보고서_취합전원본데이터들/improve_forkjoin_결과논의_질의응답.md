## 측정 대상과 테스트 조건

### 측정 대상

1. `TeamFormationEngine.improve()`는 팀 배정을 마친 뒤 팀 사이의 실력 분포를 더 고르게 다듬는 후처리다.
2. 두 팀에서 한 명씩 맞바꿔 보고, 팀 사이의 분포 편차가 줄어들면 그 교환을 채택한다.
3. 병렬화 범위는 스캔 한 번의 후보 전수 조사뿐이다. 스캔을 반복하는 while문은 순차로 둔다.
4. 병렬판이 순차판과 같은 결과를 낸다는 것은 40케이스 동일성 검증으로 이미 확인했다.

### 고정 입력과 거기서 나오는 개수

1. 입력은 인원 200명, 정원 10명, 시드 42, 허용폭 10%, 시작 배정은 greedy다.
2. 팀 개수는 200 나누기 10으로 20개다.
3. 짝의 개수는 서로 다른 팀 두 개를 고르는 경우의 수이고, 20 곱하기 19 나누기 2로 190개다.
4. 짝 하나의 후보 수는 두 팀이 각각 10명이므로 10 곱하기 10으로 100가지다.
5. 스캔 한 번의 평가 횟수는 190 곱하기 100으로 19,000회다.
6. 스캔 반복 횟수는 45바퀴다. 교환 44번과 더 이상 개선이 없어 끝나는 마지막 1번을 합한 값이고, 설정값이 아니라 이 입력에서 나온 결과값이다.
7. improve() 호출 한 번의 평가 횟수는 19,000 곱하기 45로 855,000회다.
8. 그중 합 필터를 통과해 분포 편차 계산까지 간 횟수는 352,485회다.

### 평가 1회의 정의

가장 안쪽 반복문 몸통이 한 번 실행되는 것이고, 과정은 여섯 단계다.

1. 두 팀에서 한 명씩 맞바꾼다 (`swap`).
2. 팀 사이의 합 편차를 계산한다 (`sumDeviation`).
3. 합 필터로 통과 여부를 판정한다.
4. 통과한 경우에만 팀 사이의 분포 편차를 계산한다 (`distributionDeviation`).
5. 최선 후보를 갱신할지 판정한다.
6. 맞바꾼 두 사람을 원래대로 되돌린다 (`swap`).

### 분할 개수와 동시 실행 말단 개수

1. 말단 작업은 짝 구간을 더 나누지 않고 직접 평가하는 fork-join 작업이다. 시작할 때 팀 배정 전체를 복사해 자기 것으로 하나 만들고, 담당 짝 구간을 전부 평가한 뒤 부분 최선 1건을 반환한다.
2. 분할 개수는 짝 190개를 몇 개의 말단 작업으로 나눌지를 정한다. 프로브가 호출 인자로 직접 지정한다 (`improveBySplitCount`).
3. 몇으로 나누든 같은 스캔 안의 말단이 맡은 평가를 전부 더하면 19,000회다. 분할은 나누는 방식만 바꾸고 총량은 바꾸지 않는다.
4. 동시 실행 말단 개수는 분할 개수와 풀 병렬도 중 작은 쪽이다. 병렬도 6에 분할 12를 주면 동시에 도는 말단은 6개이고 나머지 6개는 앞의 것이 끝난 뒤에 실행된다.

### 이 논의에서 쓴 측정 결과 두 가지

이 문서에 나오는 값 이름은 전부 프로브가 콘솔에 찍는 열 이름이다. 뜻을 여기서 한 번 밝히고 뒤에서는 그대로 쓴다.

**프로브 표 로그**

improve() 호출 하나를 한 줄로 담는다.

| 열 이름 | 무엇을 재나 |
|---|---|
| elapsed | 호출 하나가 시작해서 끝날 때까지 실제로 흐른 시간이다 |
| procCPU | 그 구간에 프로세스의 모든 스레드가 코어에서 실행된 시간의 합이다. 여럿이 동시에 돌면 각각 더해진다 |
| busyCore | procCPU를 elapsed로 나눈 값이다. 그 구간에 평균 몇 개 코어가 동시에 실행됐는지를 뜻하고, 상한은 논리 프로세서 수인 12다 |
| speedup | 순차 elapsed를 병렬 elapsed로 나눈 값이다 |
| mainCPU | main 스레드가 쓴 CPU 시간이다 |
| workerCPU | fork-join 워커들이 쓴 CPU 시간의 합이다 |
| 기타 자바 스레드 | main도 워커도 아닌 Java 스레드가 쓴 CPU 시간의 합이다 |
| 자바 아닌 스레드 | procCPU에서 Java 스레드 CPU 합을 뺀 나머지다. GC 작업 스레드와 JIT 컴파일러 스레드와 VM Thread 등이 들어간다 |
| GC | 그 구간에 GC가 쓴 시간의 증가분이다. CPU 시간이 아니라 실제 흐른 시간 기준이다 |
| 평가 횟수 | 가장 안쪽 반복문 몸통이 실행된 총횟수다 |
| 통과 횟수 | 그중 합 필터를 통과해 분포 편차 계산까지 간 횟수다 |
| 복사 합 | 말단들이 팀 배정 복사본을 만드는 데 쓴 시간의 합이다 |
| 평가 반복문 합 | 말단들이 4중 루프 안에서 보낸 시간의 합이다. 여러 말단이 동시에 돌면 겹치는 시간이 각각 더해진다 |
| 평가 1회당 워커 CPU | workerCPU를 평가 횟수로 나눈 값이다 |

**상세 로그**

말단 하나하나와 스캔 한 바퀴 한 바퀴를 개별 기록으로 담는다. 그 기록을 묶어 만든 값이 다음 넷이다.

| 값 이름 | 무엇을 재나 |
|---|---|
| 평가 1회당 루프 시간 | 4중 루프 시간 합을 평가 횟수 합으로 나눈 값이다 |
| 루프 시간 총합 | 그 설정의 말단들이 4중 루프에 쓴 시간을 전부 더한 값이다 |
| sumDev 1회당 시간 | 합 편차 계산 호출 한 번의 평균 시간이다 |
| distDev 1회당 시간 | 분포 편차 계산 호출 한 번의 평균 시간이다 |

**두 기록에 공통으로 해당하는 것**

1. 두 기록은 프로브를 한 번 돌려서 함께 나왔다.
    1. 프로브는 실행하면서 콘솔에 두 가지를 찍는다. 하나는 설정마다 한 줄인 표이고, 다른 하나는 말단과 스캔마다 한 줄인 상세 기록이다.
    2. 그 콘솔 출력을 파이썬 스크립트 두 개로 각각 엑셀로 옮긴 것이 이 두 파일이다.
    3. 그래서 같은 실행의 같은 순간을 두 각도에서 본 값이다. 서로 다른 날 잰 값을 맞대는 것이 아니다.
2. 이번 실행에서 잰 설정은 30개이고 설정마다 5회씩 돌렸다.
    1. 풀 병렬도는 6과 12 두 점이다.
    2. 분할 개수는 1부터 12까지와 18, 24, 36으로 15점이다.
    3. 2 곱하기 15로 설정이 30개다.
    4. 설정 하나마다 워밍업 2회를 버리고 그다음 5회를 재서 평균을 냈다.
3. 이번 실행의 값은 이전 실행의 값과 절대값을 맞대지 않는다.
    1. 이번 실행에는 계측 코드가 들어가 있다. 평가할 때마다 시각을 2회에서 4회 읽어서 두 편차 계산 메서드가 각각 얼마나 걸렸는지를 기록한다 (`System.nanoTime`).
    2. 시각을 읽는 일 자체에도 시간이 들기 때문에, 이번 실행의 모든 값에는 그만큼이 더해져 있다. 크기는 전체의 1%에서 2% 수준으로 본다.
    3. 그래서 "분할 12에서 18,425ns였다" 같은 값을 계측 코드가 없던 이전 실행의 값과 나란히 놓으면 안 된다.
    4. 다만 그 몫은 30개 설정 전부에 똑같이 붙는다. 설정끼리 비교하는 것, 예를 들어 분할 1과 분할 12를 나눠 배수를 내는 것은 그대로 유효하다.
    5. 이 문서의 판정은 전부 설정끼리의 비교다.
4. 값이 어느 파일의 어느 시트에서 나왔는지는 부록 B에 모았다.

## 관찰 1. 응답 시간은 줄었는데 CPU 시간 총합이 늘어났다

스윕 결과에서 눈에 띈 것이 셋이고, 그것을 어떻게 좁혀 나갈지가 하나다.

1. 응답 시간은 줄었는데 프로세스 전체 CPU 시간 총합은 크게 늘어났다.
2. 논리적 작업량이 같은데 중첩 반복문 구간의 시간이 늘어났다.
3. 분할 개수가 1에서 2로 갈 때는 효율이 좋았는데 2에서 3부터 급격히 떨어진다.
4. 원인이 캐시 쪽인지 메모리 대역폭인지 다른 것인지 좁혀 나갈 순서를 정해야 한다.

아래는 그 넷을 하나씩 확인해 나간 내용이다.

### 관찰된 현상을 숫자로 먼저 확인한다

값은 병렬도 12에서 분할을 1과 12로 두었을 때다.

| 항목 | 분할 1 | 분할 12 | 변화 |
|---|---:|---:|---|
| elapsed(ns) | 4,445,291,920 | 1,520,811,360 | 2.92배 짧아졌다 |
| procCPU(ns) | 4,434,375,000 | 14,318,750,000 | 3.23배 늘어났다 |

평가 1회당 루프 시간도 함께 본다. 병렬도 12 구간이다.

| 분할 개수 | 평가 1회당 루프 시간(ns) |
|---:|---:|
| 1 | 5,192 |
| 2 | 6,255 |
| 3 | 7,482 |

### 워커 밖 후보를 지운다

병렬도 12에 분할 1인 설정과 병렬도 12에 분할 12인 설정을 비교했다.

**GC**

1. 실측 값은 분할 1에서 23ms, 분할 12에서 20ms다.
2. 비교할 elapsed는 분할 1에서 4,445ms, 분할 12에서 1,521ms다.
3. 분할 1은 23 나누기 4,445로 0.5%다.
4. 분할 12는 20 나누기 1,521로 1.3%다.
5. 크기가 작고, 분할을 늘렸는데 23ms에서 20ms로 오히려 줄었다. 늘어난 시간을 설명하지 못한다.

**기타 자바 스레드**

1. main도 fork-join 워커도 아닌 Java 스레드가 쓴 CPU 시간의 합이다.
2. 실측 값은 두 설정 모두 0이다.
3. 이 호출 구간에 CPU를 쓴 다른 Java 스레드가 없었다.

**자바 아닌 스레드**

1. procCPU에서 Java 스레드 CPU 합을 뺀 나머지다. GC 작업 스레드와 JIT 컴파일러 스레드와 VM Thread 등이 들어간다.
2. 실측 값은 분할 1에서 53,125,000ns, 분할 12에서 78,125,000ns다.
3. 분할 1은 53,125,000 나누기 4,434,375,000으로 1.2%다.
4. 분할 12는 78,125,000 나누기 14,318,750,000으로 0.55%다.
5. 분할을 늘렸는데 비중이 1.2%에서 0.55%로 줄었다. 원인이 아니다.

**teams 복사**

1. 말단들이 복사본을 만드는 데 쓴 시간의 합이다.
2. 실측 값은 분할 1에서 94,720ns, 분할 12에서 3,791,680ns다.
3. 비교할 값은 말단들이 4중 루프에 쓴 시간의 합이고, 분할 1에서 4,439,431,620ns, 분할 12에서 15,753,343,920ns다.
4. 분할 1은 94,720 나누기 4,439,431,620으로 0.0021%다.
5. 분할 12는 3,791,680 나누기 15,753,343,920으로 0.024%다.
6. 분할 개수에 비례해서 늘어나는 것은 맞지만 크기가 전체의 1만분의 2 수준이다. 논의 이전에 사용자가 이미 실측으로 접은 항목이고 이번에도 같은 결론이다.

**워커 스레드 개수 자체**

2. 풀 크기와 스레드 생성 비용은 원인이 아니다. 값을 정하는 것은 동시 실행 말단 개수다.
3. 값이 오르다 멈추는 지점도 병렬도와 일치한다. 병렬도 6은 분할 6에서 멈추고 병렬도 12는 분할 12에서 멈춘다.

    5. 분할 5는 4.70과 4.59다.
    6. 분할 6은 5.45와 5.53이다.
2. 분할 7부터 두 병렬도의 값이 벌어진다.
    1. 병렬도 6은 4.66에서 5.45 사이에 머무른다.
    2. 병렬도 12는 6.40, 7.33, 8.13으로 계속 오른다.
    3. 워커가 6개뿐이면 동시에 도는 말단이 6을 넘지 못하기 때문이다.
3. 병렬도 12도 분할 12에서 멈춘다.
    1. 분할 12에서 9.42다.
    2. 분할 18은 8.87, 분할 24는 9.22, 분할 36은 9.64로 더 오르지 않는다.
    3. 논리 프로세서가 12개이기 때문이다.
4. 코어가 얼마나 찼는지는 병렬도 12 값을 분할 개수로 나눠서 본다.
    1. 분할 2는 1.96 나누기 2로 98%다.
    2. 분할 4는 3.72 나누기 4로 93%다.
    3. 분할 6은 5.53 나누기 6으로 92%다.
    4. 분할 12는 9.42 나누기 12로 79%다.
    5. 분할 6까지는 거의 꽉 차 있고, 분할 12에서 노는 시간이 21% 생긴다.
5. 그 21%로는 개별 말단의 평가 1회 시간이 3.55배가 된 것을 설명할 수 없다. 주된 원인이 아니다.

1번과 2번의 모양이 바로 앞 항목에서 확인한 것과 같다. 값을 정하는 것은 풀에 지정한 워커 수가 아니라 그 순간 실제로 동시에 도는 말단 개수다.

**서로 다른 값인데 같은 캐시 덩어리에 있어서 생기는 지연 (false sharing)**

1. 캐시는 값 하나 단위가 아니라 64바이트 덩어리 단위로 코어와 메모리 사이를 오간다.
2. 워커 둘이 서로 다른 변수를 고치더라도 그 두 변수가 같은 덩어리 안에 들어 있으면, 한쪽이 고칠 때마다 다른 쪽 코어가 들고 있던 덩어리가 못 쓰게 된다. 같은 값을 나눠 쓰지 않는데도 나눠 쓰는 것처럼 느려진다.
3. 이번에는 실측으로 확인하지 않았다. 이 항목은 하드웨어 성능 카운터가 있어야 값이 보인다.
4. 그래서 지우지도 남기지도 않고 추후 확인 항목으로 넘긴다. 확인 방법은 테스트 절에 적었다.

### 워커가 대기였는지 실행이었는지 확인한다

같은 4중 루프 구간을 두 가지 방식으로 잰 값이 있다. 두 값이 재는 것이 다르다.

| 재는 방식 | 측정 대상 |
|---|---|
| 경과 시간 | 말단이 4중 루프에 들어간 시각과 나온 시각의 차이를 더한 값이다. 스레드가 쉬고 있어도 늘어난다 |
| CPU 시간 | 워커가 코어 위에서 실제로 실행된 시간을 더한 값이다. 스레드가 코어에서 내려가 있으면 늘지 않는다 |

두 값을 나누면 그 구간에서 워커가 실제로 실행 중이었던 비율이 나온다.

| 설정 | 경과 시간 | CPU 시간 | 나눈 값 |
|---|---:|---:|---:|
| 병렬도 12, 분할 1 | 4,439.4ms | 4,371.9ms | 0.98 |
| 병렬도 12, 분할 12 | 15,753.4ms | 14,237.5ms | 0.90 |
| 병렬도 6, 분할 6 | 10,651.4ms | 10,393.8ms | 0.98 |

1. 루프 안에서 흐른 시간의 90%에서 98%가 코어 위에서 실제로 실행된 시간이다.
2. 세이프포인트 대기, 다른 프로그램에 밀려 쉰 시간, GC 정지로 설명될 몫은 10% 이하다.
3. 워커는 멈춰 있던 것이 아니라 계속 돌면서 같은 일에 시간을 더 쓰고 있다.

### 여기까지 지우고 남은 결론

**워커가 코어 위에서 실행되고 있고, 같은 명령어를 처리하는 데 더 많은 시간을 쓰고 있다.** 그러면 후보는 메모리 계통과 CPU 클럭 둘로 좁혀진다.

### 관찰 3번(2에서 3의 급감)에 대한 판정

분할을 하나 늘리면 두 가지가 동시에 바뀌고 성질이 서로 다르다.

1. 말단 하나가 맡는 평가 횟수가 줄어든다. 이것이 이득이다.
2. 평가 1회에 걸리는 시간이 늘어난다. 이것이 손해다.

두 배수를 곱하면 elapsed가 몇 배가 되는지 나온다.

| 구간 | 평가 횟수 배수 (이득) | 평가 1회당 시간 배수 (손해) | 두 배수의 곱 | 실제 elapsed 배수 |
|---|---:|---:|---:|---:|
| 분할 1에서 2 | 0.500 | 1.205 | 0.602 | 0.615 |
| 분할 2에서 3 | 0.667 | 1.196 | 0.798 | 0.811 |
| 분할 3에서 4 | 0.750 | 1.209 | 0.907 | 0.927 |
| 분할 4에서 5 | 0.800 | 1.223 | 0.979 | 0.991 |
| 분할 5에서 6 | 0.833 | 1.136 | 0.946 | 0.948 |

평가 횟수 배수는 나눗셈 하나다. 분할 개수 c에서 c+1로 갈 때 c 나누기 (c+1)이다. 총 평가 횟수 855,000은 분할과 무관하게 고정이고 말단 개수만 늘어나므로, 말단 하나가 맡는 몫이 그 비율로 준다. 분할 2에서 3이면 2 나누기 3으로 0.667이다.

**판정: 분할 3은 특별한 지점이 아니다.** 손해는 매 단계 1.2배 근처로 같게 붙는데 이득만 계속 1에 가까워져서, 두 값이 3 근처에서 상쇄되기 시작한 것이다. 이 판정으로 질문이 하나로 좁혀졌다. 왜 손해 쪽에 매번 1.2배가 붙는가.

### 관찰 1번(CPU 총합 증가)에 대한 답

프로브가 workerCPU를 평가 횟수로 나눠 계산해 둔 값이 있다.

1. 실측 값은 분할 1에서 5,113ns, 분할 12에서 16,652ns다.
2. 검산하면 855,000 곱하기 5,113은 4,371,615,000ns이고 workerCPU 4,371,875,000과 0.006% 안에서 맞는다.
3. 855,000 곱하기 16,652는 14,237,460,000ns이고 workerCPU 14,237,500,000과 0.0003% 안에서 맞는다.
4. 증가 배수는 분할 12의 16,652를 분할 1의 5,113으로 나눈 3.257배다.

CPU 총합이 늘어난 것은 일을 더 해서가 아니다. 평가 횟수는 고정인데 평가 1회에 드는 워커 CPU 시간이 3.26배가 되었기 때문이다. 응답 시간이 줄어든 것과 총합이 늘어난 것은 서로 어긋나지 않는다. 여럿이 나눠 하니 끝나는 시각은 앞당겨지고, 각자가 더 오래 걸리니 합계는 커진다.

### 평가 1회가 무슨 일을 하는지 확인한다

1. 합 편차를 구하는 메서드는 팀 20개를 돌면서 각 팀의 10명 실력을 더한다 (`sumDeviation`). 실력값을 double로 바꾸는 호출이 200회다.
2. 분포 편차를 구하는 메서드는 팀 20개를 돌면서 각 팀을 두 번 훑는다 (`distributionDeviation`). 평균을 구할 때 한 번, 편차의 제곱을 구할 때 한 번이라 호출이 400회다.
3. 4중 루프 시간에서 두 메서드가 차지하는 몫이다.

| 설정 | sumDev 비중 | distDev 비중 | 나머지 비중 |
|---|---:|---:|---:|
| 병렬도 12, 분할 1 | 52.7% | 46.3% | 1.0% |
| 병렬도 12, 분할 12 | 55.4% | 44.1% | 0.5% |

55.4 더하기 44.1로 99.5%다. 평가 1회는 사실상 두 편차 계산 메서드가 전부다. swap 두 번과 합 필터 판정과 최선 후보 갱신과 반복문 제어와 계측 코드를 다 합쳐도 0.5%에서 1.0%다.

### 추적 순서 제안

드는 노력이 적은 것부터 네 단계로 정했다. 앞의 결과가 뒤의 해석을 바꾸므로 순서를 지킨다. 표와 절차는 테스트 절의 "재야 할 것 넷"에 있다.

### 측정 방식에서 함께 확인한 두 가지

**풀을 호출마다 새로 만들고 정리하지 않는다**

1. improve() 몸통이 호출마다 새 풀을 만든다 (`new ForkJoinPool(parallelism)`).
2. 그리고 풀을 정리하는 줄이 주석 상태다 (`pool.shutdown()`). 프로브가 호출 뒤에 워커별 CPU 시간을 읽으려면 워커가 살아 있어야 하기 때문이다.

**병렬도 6에서 분할 7의 부하 불균형**

아래 값은 모두 병렬도 6에서 잰 improve() 호출 1회의 경과 시간이다.

1. 분할 6은 1,917,228,920ns이고 분할 7은 2,152,991,640ns다.
2. 2,152,991,640 나누기 1,917,228,920으로 1.123배이고 12.3% 나빠졌다.
3. 원인은 워커 6개에 말단 7개이므로 마지막 하나가 한 바퀴를 더 도는 것이다.
4. 분할을 더 늘리면 되돌아온다.
    1. 분할 12는 1,983,726,160ns다.
    2. 분할 18은 1,957,059,320ns다.
    3. 분할 24는 1,944,089,860ns다.
    4. 분할 36은 1,930,119,600ns다.
5. 분할 개수는 워커 수의 배수로 두거나 충분히 크게 두는 편이 낫다.

### 이 논의 밖에 있지만 함께 나온 이야기

1. 지금 배율이 안 나오는 이유는 병렬화 구현이 아니라 평가 한 번의 내용에 있다.
2. 평가 1회에 합 편차 계산이 팀 20개와 인원 200명을 전부 다시 훑고, 통과하면 분포 편차 계산이 같은 범위를 두 번 더 훑는다.
3. 교환은 팀 두 개만 바꾸는데 200명 전체를 다시 계산하는 구조다.
4. 로드맵 P0-1의 2번(증분 재계산)을 하면 평가 1회의 비용이 팀 수 곱하기 인원에서 정원 수준으로 떨어진다.

## 관찰 2. 두 메서드가 만드는 메모리 양

두 편차 계산 메서드가 만드는 할당 바이트를 재고 그 값이 무엇으로 이루어져 있는지 확인한 측정이다 (이 절의 값은 사용자 기계가 아니라 다른 환경의 JDK 21에서 잰 것이라, 사용자 기계에서 다시 재야 한다).

### 측정 방법

1. 값을 읽은 곳은 스레드 하나가 지금까지 새로 만든 메모리의 누적 바이트를 돌려주는 메서드다 (`com.sun.management.ThreadMXBean.getThreadAllocatedBytes`).
2. 누적값이므로 두 번 읽어서 뺀 차이를 쓴다. 프로브가 procCPU를 호출 앞뒤로 읽어 빼는 것과 같은 방식이다.
3. 순서는 다섯 단계다.
    1. 두 편차 계산 메서드를 한 글자도 고치지 않고 옮겼다.
    2. 입력을 같게 맞췄다. 팀 20개, 팀당 10명, `BigDecimal` 실력값이다.
    3. JIT이 안정될 때까지 먼저 여러 번 돌리고 버렸다. 프로브의 워밍업 2회와 같은 이유다.
    4. 할당 바이트를 읽고 200만 번 호출한 뒤 다시 읽어서, 뺀 값을 200만으로 나눴다.
    5. 결과가 없어지지 않도록 `volatile` 변수에 계속 더했다. 프로브의 `sink` 변수와 같은 이유다.

### 측정 결과

| 측정 대상 | 호출 1회당 할당(바이트) | 호출 1회당 시간(ns) |
|---|---:|---:|
| `sumDeviation` (엔진 코드 그대로) | 5,760 | 2,183 |
| `distributionDeviation` (엔진 코드 그대로) | 12,320 | 5,891 |
| `sumDeviation`을 명령형 for문으로 바꾼 판 | 0 | 1,137 |
| `distributionDeviation`을 명령형 for문으로 바꾼 판 | 0 | 1,989 |

for문으로 바꿨을 때 합 편차 계산은 2,183 나누기 1,137로 1.92배, 분포 편차 계산은 5,891 나누기 1,989로 2.96배 빨라진다.

### 팀 하나당으로 나누기

두 메서드 모두 팀 20개를 도는 반복문 하나로 되어 있으므로 20으로 나눈다.

1. 합 편차 계산은 5,760 나누기 20으로 288바이트다.
2. 분포 편차 계산은 12,320 나누기 20으로 616바이트다.

### 288바이트의 구성

합 편차 계산의 팀 하나 처리는 다음 한 줄이다.

```java
double sum = team.stream().mapToDouble(m -> m.skill().doubleValue()).sum();
```

이 줄을 왼쪽부터 한 조각씩 늘려 가며 각각 얼마를 만드는지 쟀다.

| 실행 구간 | 할당(바이트) | 앞 단계보다 늘어난 몫 |
|---|---:|---:|
| `team.spliterator()` 까지 | 32 | 32 |
| `team.stream()` 까지 | 88 | 56 |
| `team.stream().mapToDouble(...)` 까지 | 144 | 56 |
| `.sum()` 까지 (전체) | 288 | 144 |

늘어난 몫이 무슨 일에 쓰이는지다.

1. 32바이트는 목록을 앞에서 뒤로 훑어 줄 도구 하나다. 원소가 몇 개 있고 지금 어디까지 봤는지를 기억한다.
2. 56바이트는 스트림의 시작 단계다. 이 목록이 원본이라는 정보를 담는다.
3. 다음 56바이트는 변환 단계다. 각 원소에 이 람다를 적용해 double로 바꾼다는 단계가 객체로 만들어진다 (`mapToDouble`).
4. 마지막 144바이트는 합계를 실제로 실행하는 객체들이다 (`sum`). 더하기라는 연산을 담은 객체, 값을 받아 모으는 객체, 중간 합계를 담을 작은 배열이 여기 들어간다.

이 객체들은 합계가 끝나는 순간 전부 쓸모가 없어진다. 그래서 GC가 치우는 데 드는 시간은 짧다. 다만 만드는 일 자체는 호출할 때마다 해야 한다.

### 할당량은 인원 수와 무관하다

같은 한 줄을 팀 인원만 바꿔 가며 쟀다.

| 팀 인원 | 할당(바이트) |
|---:|---:|
| 2명 | 288 |
| 10명 | 288 |
| 50명 | 288 |
| 200명 | 288 |
| 1000명 | 288 |

1. 인원이 2명이든 1000명이든 288바이트로 같다.
2. 할당량은 데이터가 얼마나 많으냐로 정해지지 않는다. 스트림을 몇 번 만드느냐로 정해진다.
3. 위 네 조각은 스트림 한 번에 한 벌씩만 만들어지고, 그 뒤로는 원소가 몇 개든 같은 객체를 다시 쓴다.
4. 그래서 세어야 할 것은 인원이 아니라 스트림 호출 횟수다. 합 편차 계산은 팀 20개를 도니까 20번이고, 분포 편차 계산은 팀마다 두 번씩이니까 40번이다.

### 616바이트가 288의 두 배가 아닌 이유

분포 편차 계산은 팀당 스트림을 두 번 쓰므로 288 곱하기 2로 576이어야 할 것 같은데 616이다. 40바이트가 더 붙는다. 이유는 둘이다.

**이유 1: 합계와 평균이 만드는 객체가 다르다.** 평균은 합계뿐 아니라 개수도 세야 해서 담을 곳이 더 필요하다.

**이유 2: 람다가 다르다.**

```java
m -> m.skill().doubleValue()                                    // 바깥에서 가져오는 값이 없다
m -> { double d = m.skill().doubleValue() - mean; return d*d; } // mean을 가지고 다녀야 한다
```

1. 위쪽 람다는 바깥에서 가져오는 값이 없어서 자바가 객체 하나를 만들어 두고 계속 다시 쓴다.
2. 아래쪽 람다는 `mean` 값을 안에 담고 다녀야 해서, `mean`이 바뀔 때마다 새 객체를 만들어야 한다.
3. 분포 편차 계산은 팀마다 `mean`을 새로 계산하므로 팀마다 새로 만든다.
4. 이 값도 직접 쟀다. 바깥 값을 안 가져오는 람다로 평균을 구하면 264바이트이고, 매번 바뀌는 값을 가지고 다니는 람다로 구하면 288바이트다. 차이 24바이트가 그 람다 객체 하나의 크기다.

### 값이 흔들리는 범위

1. 팀 하나로 쪼개서 잰 값들은 측정을 어떻게 감싸느냐에 따라 264에서 296바이트 사이로 약 30바이트 흔들렸다.
2. 이유는 JIT이 어떤 객체를 없애 주고 어떤 것을 남기는지가 상황마다 달라지기 때문이다.
3. 그래서 기준으로 쓰는 값은 엔진 코드를 그대로 옮겨 잰 5,760과 12,320이다.

### 초당 얼마인지로 바꿔 본다

1. 평가 1회당 할당은 10,839바이트다. 855,000회 전부에 5,760바이트가 붙고 통과한 352,485회에만 12,320바이트가 더 붙으므로, 두 총량을 더한 9,267,415,200바이트를 855,000으로 나눈 값이다.
2. 평가 1회가 5,192ns 걸리므로 10,839 나누기 5,192는 2.088바이트/ns다.
3. 1바이트/ns는 초당 1GB이므로 말단 하나가 초당 약 2.09GB를 새로 만든다.
4. improve() 호출 한 번의 총 할당량은 약 9.27GB다.
5. 스트림 생성 횟수는 호출 1회에 약 3,120만 번이다.

### GC 시간이 작은 것과 어긋나지 않는다

호출 한 번에 9.27GB를 만드는데 GC 시간이 20ms뿐이라는 것이 서로 어긋나 보일 수 있다. 어긋나지 않는다.

1. GC 시간은 만들어진 객체를 치우는 데 든 시간이다. 여기서 만드는 객체는 전부 즉시 죽으므로 치울 일이 거의 없다.
2. 시간이 드는 곳은 치우는 쪽이 아니라 쓰는 쪽이다. 9.27GB를 메모리에 쓰는 일 자체는 GC 시간에 잡히지 않는다.
3. 그래서 GC 시간이 작다는 것은 수집에 든 시간이 짧다는 뜻이지 할당이 적다는 뜻이 아니다.

## 테스트. CPU 바운드 구간에서 발생한 3.73배의 원인을 찾기 위해 재야 할 것

연산 내용과 연산에 쓰이는 데이터가 같은데 시간이 3.73배가 되었다. 이 절은 그 원인을 두고 실측으로 어디까지 말할 수 있는지와, 남은 것을 무엇으로 어떻게 재야 하는지를 적는다.

### 실측으로 말할 수 있는 데까지

1. 명령어 개수는 분할과 무관하게 같다. 합 편차 계산 한 번이 하는 일이 분할 1이든 12이든 한 줄도 안 바뀐다.
2. 걸린 시간은 명령어 개수와 명령어 하나에 걸리는 시간의 곱이다. 개수가 같은데 시간이 3.73배가 되었으므로, 명령어 하나에 걸리는 시간이 3.73배가 되었다.

### 후보는 둘이고 이번 데이터로는 어느 쪽인지 알 수 없다

둘 다 이 기계에서 확인하지 않았다. 후보로만 남긴다.

1. 캐시와 메모리 계통이다. 같은 명령어라도 값이 어느 층에 있느냐에 따라 걸리는 시간이 다르고, 동시에 도는 개수가 늘면 먼 층까지 가는 일이 잦아진다.
2. CPU 클럭이다. 코어 여럿이 동시에 바쁘면 클럭이 내려간다. 동시에 도는 스레드 개수가 늘 때 이 기계의 CPU가 실제로 느려지는지는 확인하지 않았고, 확인해야 한다.
3. 어느 쪽이든 명령어 개수는 같고 평가 1회당 시간만 늘어난다. 그래서 지금 가진 결과로는 둘 중 어느 쪽인지 알 방법이 없다.

### 재야 할 것 넷

드는 노력이 적은 것부터 순서대로 넷이다. 앞의 결과가 뒤의 해석을 바꾸므로 순서를 지킨다.

| 순서 | 작업 | 드는 노력 | 판정 대상 |
|---:|---|---|---|
| 1 | 분할 1과 분할 12에서 CPU 클럭을 읽는다 | 코드 수정 없음 | 3.73배 중 클럭 몫 |
| 2 | 프로브에 할당 바이트 측정을 넣는다 | 코드 몇 줄 | 할당량의 실제 값 |
| 3 | 두 메서드를 for문으로 바꾸고 같은 스윕을 다시 돌린다 | 메서드 두 개 수정, 동일성 검증, 재측정 | 1.2배가 할당 때문인가 |
| 4 | 성능 카운터로 캐시와 메모리를 본다 | 도구 설치와 학습 | 어느 층에서 막히나 |

**1단계, CPU 클럭**

1. 확인할 것은 둘이다.
    1. 동시 실행 개수가 늘 때 이 기계의 CPU 클럭이 내려가는가.
    2. 내려간다면 분할 1과 분할 12에서 각각 몇 GHz인가.
2. 이것을 재야 하는 이유는 클럭이 내려가면 명령어 개수가 같아도 시간이 늘기 때문이다. 그 몫을 빼기 전에는 3.73배를 메모리 탓으로 볼 수 없다.
3. 하는 일은 프로브를 실행하는 동안 작업 관리자 성능 탭의 CPU 속도나 HWiNFO의 코어 클럭을 읽는 것이다. 코드 수정과 설정 변경이 없다.
4. 읽는 시점은 세 곳이다.
    1. 병렬도 6에 분할 1인 설정이다. 동시 실행 1이다.
    2. 병렬도 6에 분할 6인 설정이다. 동시 실행 6이다.
    3. 병렬도 12에 분할 12인 설정이다. 동시 실행 12다.
5. 판정 방법은 세 단계다.
    1. 동시 실행 1일 때 클럭을 A, 6일 때를 B라고 한다.
    2. 클럭만으로 설명되는 값은 4,836 곱하기 (A 나누기 B)다.
    3. 이 값이 실측 12,458에 가까우면 클럭이 대부분을 설명하고, 실측보다 작으면 그 차이가 다른 원인의 몫이다.
6. 동시 실행 6과 12의 클럭이 비슷하다면, 12,563에서 18,425로 오른 몫은 클럭이 아니라 SMT다.

**2단계, 할당 바이트**

1. 확인할 것은 사용자 기계의 JDK 17에서도 5,760바이트와 12,320바이트가 나오는지다. 이 두 값은 다른 환경의 JDK 21에서 잰 값이다.
2. 이것을 재야 하는 이유는 두 값 위에 네 개의 계산이 올라가 있기 때문이다.
    1. 평가 1회당 10,839바이트다.
    2. 호출 1회당 9.27GB다.
    3. 말단 하나가 초당 2.09GB다.
    4. 분할 12에서 요구량이 25.1GB다.
3. 하는 일은 프로브가 이미 스레드 id를 하나씩 돌면서 CPU 시간을 읽는 그 지점에서 할당 바이트도 읽는 것이다 (`snapshotAllThreadCpu`).
4. 값을 읽는 곳은 관찰 2와 같다 (`com.sun.management.ThreadMXBean.getThreadAllocatedBytes`). 읽는 방식은 improve() 호출 앞뒤로 두 번 읽어 빼는 것이고, 지금 procCPU를 다루는 방식과 같다.
5. 판정은 둘이다.
    1. 호출 1회당 총 할당이 9.27GB 근처인가.
    2. 그 값이 분할 개수를 바꿔도 같은가. 같아야 맞는다. 할당량은 분할과 무관하기 때문이다.
6. 교차 검산으로 젊은 세대 수집 횟수를 함께 보면 총 할당량과 대조할 수 있다 (`-Xlog:gc`).

**3단계, for문 대조군**

1. 확인할 것은 분할을 하나 늘릴 때 붙는 1.2배가 할당 때문인지다.
2. 하는 일은 두 편차 계산 메서드를 스트림에서 명령형 for문으로 바꾸는 것이다. 관찰 2에서 할당이 0바이트가 되고 시간도 1.92배와 2.96배 빨라졌다.
3. 결과 동일성은 유지된다. 더하는 순서가 같으므로 결과가 비트 단위로 같고, 이미 만들어 둔 검증 프로그램으로 확인하면 된다 (`ImproveEquivalenceCheck`). 이 프로그램은 40케이스 통과 상태다.
4. 판정은 두 갈래다.
    1. 1.2배가 함께 줄면 원인은 할당과 메모리 계통으로 좁혀진다.
    2. 절대값만 줄고 1.2배가 그대로면 원인은 다른 곳이고 4단계로 넘어간다.

**4단계, 성능 카운터**

1. 확인할 것은 둘이다.
    1. 어느 층에서 막히는지다. L1인지 L2인지 L3인지 메인 메모리인지다.
    2. 워커들이 함께 고치는 값들이 같은 64바이트 덩어리에 몰려 서로의 캐시를 무효로 만들고 있는지다 (false sharing). 이 코드에서 워커들이 함께 고치는 값은 정적 카운터 네 개와 기록 큐다 (`evalCount`, `passCount`, `copyTimeNs`, `evalLoopTimeNs`, `detailLog`).
2. 쓰는 도구는 Intel CPU이므로 VTune Profiler의 Microarchitecture Exploration이다.
3. 하는 일은 분할 1과 분할 12를 각각 프로파일해서 비교하는 것이다.
4. 볼 값은 다섯이다.
    1. Instructions Retired가 두 설정에서 거의 같아야 한다. 명령어 개수가 같다는 것의 직접 확인이다.
    2. CPI(명령어당 사이클)가 올랐으면 사이클을 더 쓴 것이다.
    3. Memory Bound를 L1, L2, L3, DRAM Bound로 나눈 값에서 어느 층이 늘었는지 나온다.
    4. DRAM Bandwidth의 실제 GB/s를 이 기계의 한계와 비교한다.
    5. 다른 코어가 고쳐 놓은 덩어리를 가져온 횟수를 본다 (`MEM_LOAD_L3_HIT_RETIRED.XSNP_HITM`).
5. 이 단계는 마지막이다. 앞의 셋을 하고도 1.2배가 그대로 남을 때 진행한다.

## 부록 A. 이번에 다루지 않은 것

이번 논의에서 다루지 않기로 하거나 뒤로 미룬 항목이다.

1. SMT 몫을 따로 떼어 내는 것이다. 병렬도 12에서 동시 실행이 6을 넘는 구간은 한 물리 코어의 논리 프로세서 두 개에 스레드가 올라가는 상태다. 클럭을 재고 나서 남는 몫으로 판정한다.
2. 터보를 끄고 다시 재는 것이다. 클럭 값이 심하게 흔들려 읽지 못할 때만 진행한다.
3. BIOS에서 SMT를 끄는 것이다. 부담이 커서 보류했다.
4. JIT 컴파일 시간 계측이다. 2026-07-28 결정으로 측정 계획에서 제외했고 관련 코드는 주석으로 보존되어 있다.
5. ForkJoinPool의 작업 훔치기 설계 원리다. 측정 작업이 끝난 뒤에 본다.
6. 운영 경로의 풀 병렬도를 얼마로 할지다. 병렬도 12가 elapsed는 짧지만 CPU 시간 총합은 크다.
7. 계측 두 가지를 언제 비활성화하고 문서용 시간 확정 측정(JMH)으로 넘어갈지다.
8. 풀을 정리하는 줄을 언제 복원할지다 (`pool.shutdown()`). 워커별 CPU 시간을 더 읽지 않아도 되는 시점이다.

**이 논의 밖이지만 함께 나온 방향**

실행 여부는 정하지 않았다. 사실만 적는다.

1. 로드맵 P0-1의 순서는 1번 프루닝, 2번 증분 재계산, 3번 병렬화다. 지금은 1번과 2번을 하지 않은 채 3번을 다루고 있다.
2. 엔진 주석에 개선안이 적혀 있다. 교환은 팀 두 개만 바꾸므로 팀별 합과 제곱합을 저장해 두면 두 메서드의 전량 재계산을 피할 수 있다.
3. 실측에 따르면 4중 루프 시간의 99.5%가 그 두 메서드에 있다.
4. 할당량은 스트림 호출 횟수로 정해지므로, 두 메서드의 호출 자체가 줄면 할당량도 함께 줄어든다.

## 부록 C. 실측 원본 데이터

원본 파일 두 개에 무엇이 들어 있는지와 값이 어떤 모양인지만 적는다. 전체 값은 파일을 연다.

### C.1 프로브 표 파일

경로는 `docs/병목개선/ForkJoinPool/테스트/프로브표로그_4.1계측스윕_N200_20260730.xlsx`이고 `정리` 시트 한 장이다.

행마다 설정 하나의 결과가 들어 있고 순차 1개와 병렬 30개다. 열은 A부터 V까지 넷으로 묶인다.

1. A부터 I까지는 설정과 기본 결과다. N, 팀당 인원, 구현, 병렬도, 작업 분할 개수, elapsed, speedup, procCPU, busyCore다.
2. J부터 N까지는 procCPU를 나눈 값이다. mainCPU, workerCPU, 기타 자바 스레드, 자바 아닌 스레드, GC다.
3. O부터 S까지는 계측 카운터다. 평가 횟수, 통과 횟수, 복사 합, 평가 반복문 합, 평가 1회당 워커 CPU다. 순차 행은 비어 있다.
4. T부터 V까지는 워커별로 따로 읽은 값이다. 활동 워커 수, 워커 CPU 시간 합, 최대 나누기 최소다. 이 세 열은 본 표와 다른 실행에서 나왔고 워밍업 없이 1회만 돌린 값이라 이번 판정에 쓰지 않았다.
