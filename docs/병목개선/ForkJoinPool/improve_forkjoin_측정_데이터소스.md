## 1. 이 문서가 담는 것

1. 회차마다 무엇을 어떤 조건에서 쟀는지와, 그 회차에 어떤 계측이 들어가 있었는지.
2. 회차별 측정값 전량.
3. 값을 다룰 때 지킬 것과 이 값들의 한계.

담지 않는 것이 둘이다.

1. 판정과 해석. 추적 기록 문서에 있다.
2. JFR 할당 측정값. JFR 측정 데이터 소스 문서에 있다. 그 회차가 어디에 있는지는 14절에 적었다.

## 2. 용어

1. **평가 1회**: 말단 4중 루프의 가장 안쪽 반복문 몸통이 한 번 실행되는 것이다.
    - 과정은 여섯 단계다. 두 팀에서 한 명씩 맞바꾸고 (`swap`), 팀 사이의 합 편차를 계산하고 (`sumDeviation`), 합 필터로 통과 여부를 판정하고, 통과한 경우에만 팀 사이의 분포 편차를 계산하고 (`distributionDeviation`), 최선 후보를 갱신할지 판정하고, 맞바꾼 두 사람을 되돌린다.
2. **짝**: 서로 다른 팀 두 개를 묶은 것 하나다. 교환은 항상 두 팀 사이에서만 일어나므로 후보 전수 조사에는 어느 두 팀끼리 비교할 것인가의 목록이 필요하고, 그 목록의 원소 하나가 짝이다.
3. **말단 작업**: 짝 구간을 더 나누지 않고 직접 평가하는 fork-join 작업이다.
    - 시작할 때 팀 배정 전체를 복사해 자기 것으로 하나 만들고, 담당 짝 구간을 전부 평가한 뒤 부분 최선 1건을 반환한다 (`ImproveTaskResult`).
    - 담당 범위는 짝 번호 lo번부터 hi − 1번까지다. [lo, hi) 표기는 lo는 포함하고 hi는 제외한다는 뜻이다.
4. **분할 개수**: 짝을 몇 개의 말단 작업으로 나눌지를 정하는 값이다. 프로브가 호출 인자로 직접 지정한다 (`improveBySplitCount`).
5. **workSize**: 말단 작업 하나가 맡는 짝의 개수다. 담당 구간이 이 값보다 길면 반으로 나눠 내려간다.
    - 기준 측정에서만 이 값을 직접 바꿨다. 분할 개수별 측정부터는 분할 개수를 직접 지정하는 방식으로 바꿨다.
    - 원래 식은 짝 수를 논리 프로세서 개수로 나눈 것이다 (`Math.max(1, pairCount / cpuCount)`). 이 기계에서 cpuCount는 12다.
6. **동시 실행 말단 개수**: 그 순간 실제로 함께 돌고 있는 말단 작업의 개수다. 분할 개수와 풀 병렬도 중 작은 쪽이다.
    - 병렬도 6에 분할 12를 주면 동시에 도는 말단은 6개이고 나머지 6개는 앞의 것이 끝난 뒤에 실행된다.
7. **스캔**: 팀 배정 하나를 놓고 모든 짝의 모든 후보를 한 번 전수 조사하는 바퀴다.
    - 스캔 한 바퀴는 최선 교환 1건만 실제로 적용하고 끝난다. 바뀐 배정에서 다시 전수 조사하므로 스캔이 여러 바퀴 돈다.
8. **통과 횟수**: 평가 중 합 필터를 통과해 분포 편차 계산까지 실행한 횟수다.
9. **통과율**: 통과 횟수를 평가 횟수로 나눈 값이다.

## 3. 프로브가 찍는 값의 뜻

프로브(`ImproveCpuUtilizationProbe`)가 콘솔에 찍는 것은 둘이다.

1. 설정마다 한 줄인 표.
2. 말단과 스캔마다 한 줄인 상세 기록. 상세 기록 측정 회차부터 붙었다.

### 3.1 표에 찍히는 값

| 열 이름 | 재는 것 |
|---|---|
| N(명) | 전체 인원 수 |
| 팀당 인원(명) | 팀 하나에 배정한 인원 수(정원) |
| 구현 | 순차(`improveSequential`) 또는 병렬(`improve`) |
| 스레드(개) | 풀 병렬도. 순차 행은 비어 있다 |
| 작업 분할 개수(개) | 이 설정에서 실제로 만들어지는 말단 작업 수 |
| elapsed | 호출 하나가 시작해서 끝날 때까지 실제로 흐른 시간 |
| speedup | 순차 elapsed를 병렬 elapsed로 나눈 값 |
| procCPU | 그 구간에 프로세스의 모든 스레드가 코어에서 실행된 시간의 합. 여럿이 동시에 돌면 각각 더해진다 |
| busyCore | procCPU를 elapsed로 나눈 값. 그 구간에 평균 몇 개 코어가 동시에 실행됐는지를 뜻하고 상한은 논리 프로세서 수인 12다 |
| mainCPU | main 스레드가 쓴 CPU 시간 |
| workerCPU | fork-join 워커들이 쓴 CPU 시간의 합. 그 호출 구간의 증가분이다 |
| 기타 자바 스레드 | main도 워커도 아닌 Java 스레드가 쓴 CPU 시간의 합 |
| 자바 아닌 스레드 | procCPU에서 Java 스레드 CPU 합을 뺀 나머지. ThreadMXBean이 id를 주지 않아 스레드별로 잴 수 없는 몫이고, GC 작업 스레드와 JIT 컴파일러 스레드와 VM Thread 등이 들어간다 |
| GC | 그 구간에 GC가 쓴 시간의 증가분. CPU 시간이 아니라 실제 흐른 시간 기준이다 |
| 평가 횟수 | 가장 안쪽 반복문 몸통이 실행된 총횟수 |
| 통과 횟수 | 그중 합 필터를 통과해 분포 편차 계산까지 간 횟수 |
| 복사 합 | 말단들이 팀 배정 복사본을 만드는 데 쓴 시간의 합 |
| 평가 반복문 합 | 말단들이 4중 루프 안에서 보낸 시간의 합. 여러 말단이 동시에 돌면 겹치는 시간이 각각 더해진다 |
| 평가 1회당 워커 CPU | workerCPU를 평가 횟수로 나눈 값. 재는 값이 아니라 계산값이다 |
| 총 할당 | 호출 1회 동안 새로 만든 객체의 누적 바이트. for문 대조 측정부터 찍힌다 |

값을 읽을 때 쓰는 계측 API는 다섯 가지다. 모두 호출 직전과 직후에 한 번씩 읽어 뺀 증가분이다.

1. `OperatingSystemMXBean.getProcessCpuTime()`은 프로세스의 누적 CPU 시간(ns)을 준다. 종료된 스레드 몫까지 들어간다.
2. `ThreadMXBean.getCurrentThreadCpuTime()`은 이 코드를 실행 중인 스레드(main)의 누적 CPU 시간(ns)을 준다.
3. `ThreadMXBean.getThreadCpuTime(id)`은 스레드 하나의 누적 CPU 시간(ns)을 준다. 이름이 "ForkJoinPool"로 시작하는 스레드들의 증가분을 합한 것이 workerCPU다.
4. `ThreadMXBean.getAllThreadIds()`와 `getThreadInfo(id)`는 살아 있는 Java 스레드의 id와 이름을 준다.
5. `com.sun.management.ThreadMXBean.getThreadAllocatedBytes(id)`는 스레드 하나가 지금까지 새로 만든 객체의 누적 바이트를 준다.

자바 아닌 스레드는 메서드가 아니라 계산값이다. procCPU 증가분에서 Java 스레드 CPU 증가분의 합을 뺀 나머지다.

### 3.2 상세 기록에서 나오는 값

상세 기록은 말단 하나하나와 스캔 한 바퀴 한 바퀴를 개별 줄로 담는다. 그 줄들을 묶어 만든 값이 넷이다.

| 값 이름 | 재는 것 |
|---|---|
| 평가 1회당 루프 시간 | 4중 루프 시간 합을 평가 횟수 합으로 나눈 값 |
| 루프 시간 총합 | 그 설정의 말단들이 4중 루프에 쓴 시간을 전부 더한 값 |
| sumDev 1회당 시간 | 합 편차 계산 호출 한 번의 평균 시간 |
| distDev 1회당 시간 | 분포 편차 계산 호출 한 번의 평균 시간 |

## 4. 고정 입력에서 나오는 개수

인원 200명에 정원 10명일 때의 값이다. 통과 횟수와 통과율만 상세 기록 측정의 실측이고 나머지는 고정 입력에서 나오는 개수다.

| 값 | 개수 | 낸 방법 |
|---|---:|---|
| 팀 개수 | 20개 | 200 나누기 10 |
| 짝 개수 | 190개 | 20 곱하기 19 나누기 2 |
| 짝 하나의 후보 수 | 100가지 | 10 곱하기 10 |
| 스캔 한 번의 평가 횟수 | 19,000회 | 190 곱하기 100 |
| 스캔 반복 횟수 | 45바퀴 | 교환 44번과 더 이상 개선이 없어 끝나는 마지막 1번 |
| 호출 1회의 평가 횟수 | 855,000회 | 19,000 곱하기 45 |
| 호출 1회의 통과 횟수 | 352,485회 | 실측값이다 |
| 통과율 | 0.412263 | 352,485 나누기 855,000 |

표의 낸 방법 열이 각 값의 계산식이다.

스캔 반복 횟수 45는 설정값이 아니라 이 입력에서 나온 결과값이다.

|---|---|---|---|---|
| 기준 측정 | 2026-07-24 정리 | JMH 배율 6점, 프로브 네 설정 | 없다 | 8절 |

| 클럭 측정 | 2026-08-03, 2026-08-04 | 15점의 CPU 클럭 | 상세 기록에 시작 시각 추가 | 13절 |

2. 카운터 측정과 상세 기록 측정은 같은 30설정을 잰 서로 다른 실행이고 값이 다르다.
3. 이후의 판정은 전부 상세 기록 측정의 값으로 했다.

## 6. 값을 다룰 때 지킬 것

1. 회차 사이의 절대값은 비교하지 않는다. 계측 조건이 다르기 때문이다. 비교는 각 회차 안에서 배수끼리 한다.
2. 계측이 들어간 실행의 값에는 시각 읽기가 포함되어 있다. 크기는 전체의 1%에서 2% 수준이다.
3. 기록 도구를 켠 실행의 시간 값은 판정에 쓰지 않는다. JFR을 켠 실행도 같다.
4. 실측이 뒷받침하지 않는 것은 후보로만 적는다.
5. 프로브는 진단용이고 JMH가 아니다. 문서용 확정 배율은 JMH로 따로 잰다.

## 7. 엔진에 넣은 계측의 설계

카운터 측정부터 엔진의 말단 구간에 임시 계측이 들어갔다. 무엇을 어디서 재는지와 왜 그 방식을 골랐는지를 적는다.

### 7.1 카운터가 재는 값

| 값 | 재는 것 | 재는 방법 | 단위 |
|---|---|---|---|
| 평가 횟수 | 평가가 실제로 실행된 횟수 | 가장 안쪽 반복문에서 지역 변수에 1씩 더한다 | 회 |
| 통과 횟수 | 그중 합 필터를 통과한 횟수 | 합 필터를 통과한 분기 안에서 지역 변수에 1씩 더한다 | 회 |
| 복사 구간 시간 | 복사 블록이 걸린 시간 | 블록 앞뒤에서 `System.nanoTime()`을 읽어 차이를 구한다 | ns |
| 평가 반복문 구간 시간 | 4중 루프 전체가 걸린 시간 | 블록 앞뒤에서 `System.nanoTime()`을 읽어 차이를 구한다 | ns |

1. 말단 작업이 끝나는 지점에서 지역 변수 네 개를 정적 카운터 네 개로 옮겨 더한다.
2. 카운터는 `AtomicLong`이다. 하나의 카운터에 여러 워커가 동시에 더하기 때문이다.
3. 프로브가 호출 직전에 카운터를 0으로 만들고 직후에 읽어 그 호출 한 번의 총합을 얻는다.

### 7.2 통과 횟수를 함께 재는 이유

1. 평가 1회의 비용은 한 종류가 아니다.
    - 모든 평가는 맞바꾸기를 하고 합 편차를 계산한다. 순회 인원은 말단 작업의 크기와 무관하게 팀 20개 곱하기 팀당 10명으로 200명 고정이다.
    - 합 필터에서 걸러진 평가는 여기서 끝나고 원상 복구만 한다.
    - 합 필터를 통과한 평가는 분포 편차 계산까지 더 실행한다. 이 메서드는 팀마다 평균 계산과 분산 계산으로 두 번씩 순회하므로 400명 분량이다.
2. 그래서 평가 1회당 평균 CPU 시간은 걸러진 평가와 통과한 평가가 섞인 비율에 따라 달라진다. 통과율을 모르고 평균만 보면 그 차이를 동시 실행 때문이라고 잘못 읽게 된다.
3. 통과 횟수가 설정 사이에서 같다고 확인되면 일의 양뿐 아니라 일의 구성도 같다는 것이 확정된다. 그래야 설정끼리 평가 1회당 시간을 비교하는 것이 정당해진다.

### 7.3 합 편차 계산과 분포 편차 계산을 따로 재지 않았던 이유

카운터 측정까지는 두 메서드의 시간을 나눠 재지 않았다. 이유가 셋이다.

1. 두 연산의 시간은 평가 반복문 구간 시간과 workerCPU 안에 전부 들어간다. 하지 않은 것은 그 시간을 연산별로 나누는 일뿐이다.
2. 나누려면 계측이 가장 안쪽 반복문 안으로 들어가야 한다. 두 연산은 스캔당 수만 번 불리므로 시각 읽기가 그만큼 끼면 실행이 느려진다.
3. 반복문 안에 계측 코드가 들어가면 JIT 컴파일 결과가 달라질 수 있다.

상세 기록 측정에서 이 계측을 실제로 넣었고, 그 대가로 그 회차의 모든 값에 시각 읽기 몫이 1%에서 2% 더해져 있다.

### 7.4 계측이 값에 더하는 몫

1. 재는 블록이 측정 행위보다 충분히 커야 한다. 시각 읽기 한 쌍은 수십 ns다.
2. 말단 단위는 수백 ms이므로 복사 구간과 평가 반복문 구간의 왜곡은 사실상 0이다.
3. 더하기 한 번은 CPU 덧셈 명령 하나이고 1ns가 안 된다. 평가 1회는 수천 ns이므로 카운터 두 개는 값을 바꾸지 못한다.
4. 스레드 CPU 시간 API는 Windows에서 15.625ms 단위로만 갱신되므로 말단보다 작은 블록에는 쓰지 않았다. 블록별로는 경과 시간을 재고 CPU 시간은 워커별 기록으로 본다.
5. 시각 읽기 몫은 30개 설정 전부에 똑같이 붙는다. 설정끼리 나눠 배수를 내는 것은 그대로 쓸 수 있다.

## 8. 기준 측정

### 8.1 실행 조건

1. 측정 대상은 병렬판(`improve`)과 순차 대조군(`improveSequential`)이다.
2. JMH 배율은 JMH 1.37로 쟀다. 평균 시간 방식이고 단위는 ms/op이며, fork 2회, 워밍업 5회 1초, 측정 5회 3초로 설정당 표본 10개다. 적힌 값은 그 10개의 평균이다.
3. JMH의 op 1회는 호출 1회이고 스캔 반복 전체를 포함한다. 호출마다 같은 greedy 시작 배정을 새 복사본으로 떠서 넘기며, 그 복사는 측정 구간 밖에서 한다.
4. JMH가 벤치 메서드를 부르는 스레드는 1개다. 병렬로 도는 것은 그 안에서 만들어지는 fork-join 풀이라, 이 1과 풀 병렬도 12는 서로 다른 값이다.
5. 프로브는 워밍업 2회를 버리고 5회를 재서 평균을 냈다.
6. 이 회차에는 엔진 계측이 들어 있지 않다.
7. N이 60 이하인 프로브 측정은 프로세스 CPU 타이머 해상도에 묻혀 제외했다.

### 8.2 JMH 배율

1. 풀 병렬도는 여섯 행 전부에서 12로 같다. 벤치마크가 인자 두 개짜리 호출을 쓰고 그 호출이 `availableProcessors()` 값을 그대로 병렬도로 넘기기 때문이고, 이 기계에서 그 값은 12다.
2. workSize는 짝 수를 12로 나눈 값이라 인원 200명이면 15이고 인원 300명이면 36이다.

### 8.8 N=120을 설정 비교에 쓰지 않는 이유

1. N=120에서는 두 workSize 설정이 같은 실험이 된다. 짝 수가 66개이고 workSize는 12개 설정에서 5이며 6개 설정에서 6이다.
2. 구간이 workSize보다 길면 반으로 나누는데, 두 설정이 같은 지점에서 멈춘다.

| 나눈 횟수 | 구간 길이 |
|---:|---|
| 0 | 66 |
| 1 | 33 |
| 2 | 17과 16 |
| 3 | 9와 8 |
| 4 | 5와 4 |

각 줄은 앞 줄의 구간을 반으로 나눈 것이고, 마지막 줄의 5와 4가 기준 5와 6 모두보다 짧아 거기서 분할이 끝난다. 구간 길이는 코드를 읽어 낸 값이다.

3. 말단 작업 개수는 두 설정 모두 16개이고 각 말단이 맡는 짝 구간도 같다.
4. 분할이 같고 스레드 수도 같은데 실제로 걸린 시간이 달랐다. 스레드 12에 workSize 12개 설정이 131.66ms이고 workSize 6개 설정이 183.60ms로 약 39% 벌어졌다.
5. 같은 조건을 두 번 실행한 것과 다르지 않은데 벌어졌으므로 설정의 효과가 아니다. 실행 시간이 130에서 200ms로 짧아 값이 흔들린 것이다.
6. 그래서 설정 사이의 비교는 N=200 값으로만 한다.

## 12. 할당 실측과 for문 대조

### 12.1 실행 조건

1. 프로브에 할당 바이트 계측을 더했다. 스레드별 CPU를 읽는 그 자리에서 누적 할당 바이트를 함께 읽고, 증가분을 main과 워커와 그 밖의 Java 스레드로 나눠 담는다.
2. 할당은 CPU 증가분 검사보다 앞에서 더한다. Windows CPU 해상도가 15.625ms라 CPU가 0으로 잡히는 스레드도 할당은 했을 수 있기 때문이다.
3. 할당 실측은 분할 36 한 점이고 병렬도 6과 12, 그리고 순차까지 세 경우다.
4. for문 구현 측정은 병렬도 6과 12에 분할 15점으로 설정 30개를 한 번의 실행으로 돌렸다. 말단 기록은 70,200건이다.
5. 설정마다 워밍업 2회를 버리고 5회를 잰다.
6. 판정은 두 구현 사이의 절대값이 아니라 각 구현 안에서 분할 1을 기준으로 한 배수로 한다.

### 12.2 스트림 구현의 할당량

### 12.4 순차 값이 알려 주는 것

2. 그래서 순차의 총량 9,517.9MB가 두 메서드의 몫이다.
3. 병렬도 12가 순차보다 더 만든 3,470,162바이트는 팀 배정 복사본과 작업 객체와 기록 문자열의 몫이다. 순차 총량의 0.036%다.

### 12.5 for문 전환에서 드러난 제약

1. 스트림의 합계와 평균은 값을 차례로 더하기만 하는 것이 아니다. 반올림으로 어긋난 몫을 따로 두었다가 다음 덧셈에서 되돌리는 보정 계산을 함께 한다 (Kahan 방식).
2. 그래서 단순 누적 for문으로 바꾸면 값이 달라진다. 같은 입력으로 팀 400,000개를 잰 결과다.

| 계산 | 비트가 어긋난 팀 수 |
|---|---:|
| 합계 | 162,161 |
| 평균 | 141,500 |

전체 400,000개 중에서 센 것이고, for문 전환 과정에서 메서드 단위로 대조해 잰 값이다. 프로브 회차의 값이 아니다.

3. 그래서 보정 계산까지 그대로 옮겼다. 마지막 단계는 누적 합에서 보정 항을 빼는 것이다. 처음에 더하기로 썼다가 분산 계산에서 87건이 어긋나는 것을 실측으로 확인하고 뺄셈으로 고쳤다.

### 13.5 이 회차의 한계

1. 클럭 CSV는 논리 프로세서별 값이다. 어느 스레드가 어느 프로세서에서 돌았는지는 기록되지 않는다.
2. 그래서 스레드와 클럭의 대응은 활동 구간 단위까지만 된다. 13.2절의 값은 그 구간에 걸린 표본의 전체 프로세서 평균이고 특정 코어의 클럭이 아니다.
3. 표본 간격이 1초다. 구간이 10초 남짓인 설정은 표본이 10개에서 12개뿐이다.
4. 백분율을 GHz로 옮기는 데 쓴 기본 클럭 2.69GHz는 곱하는 상수다. 이 값이 틀리면 GHz가 모두 같은 비율로 틀리고, 구간 사이의 비는 바뀌지 않는다.
5. 이 회차는 클럭 수집과 상세 기록을 함께 켠 실행이다. 그래서 13.4절의 시간 값은 판정에 쓰지 않는다.
6. 구간에는 워밍업 2회가 들어 있고 병렬 구간에는 워커별 CPU를 읽는 호출 1회가 더 있다. 구간 평균 클럭은 그 호출들까지 포함한 평균이다.

## 15. 이 값들의 한계

1. 프로브는 진단용이고 JMH가 아니다. 문서용 확정 배율은 JMH로 따로 잰다.
2. 회차마다 계측 수준이 달라 회차 사이의 절대값을 그대로 비교할 수 없다.
3. 카운터 측정과 상세 기록 측정은 같은 30설정을 잰 서로 다른 실행이다. 값이 다르고, 판정에 쓴 것은 뒤쪽이다.
4. 워커별 CPU 요약은 본 표와 다른 실행에서 나왔다. 상세 기록 측정의 것은 워밍업 없이 1회만 돌린 값이라 최대와 최소의 비가 크게 흔들리고 판정에 쓰지 않았다.
5. Windows 스레드 CPU 시간 해상도가 15.625ms다. 작은 값은 0으로 잡히거나 계단처럼 나온다.
6. GC 시간은 CPU 시간이 아니라 실제 흐른 시간 기준의 근사값이다.
7. 두 편차 계산 메서드의 조각별 할당 바이트는 다른 환경 JDK 21에서 잰 값이다. 총량은 이 기계에서 다시 쟀고 2.7% 차이가 어느 메서드의 몫인지는 나누지 못했다.
8. 병렬도 12에 분할 12인 설정은 측정 5회의 최대와 최소 비가 1.42다. 평균값으로 해석하지 않는다.
9. 호출마다 새 풀을 만들고 정리하지 않는다.
    - 풀을 정리하는 줄이 주석 상태이고, 프로브가 호출 뒤에 워커별 CPU를 읽으려면 워커가 살아 있어야 한다.
    - 상세 기록 측정의 호출 횟수는 설정 30개에 8회씩으로 240회다.
    - 실행 순서 때문에 값이 흐르는지 확인했다. 병렬도 6이 먼저 실행되고 12가 나중에 실행되는데 두 병렬도의 분할 1부터 6까지 값이 서로 2%에서 7.4% 안에서 같아, 뒤에 실행된 설정이 계속 나빠지는 흐름은 보이지 않았다.

값의 모양을 보이는 예시를 한 줄씩 적는다.

1. 프로브 콘솔 로그는 설정마다 표 한 행이 찍히고, 그 아래에 계측 줄과 워커별 CPU 줄이 들여쓰기로 붙는다.
2. 상세 기록은 `IMPLOG,leaf,`로 시작하는 말단 줄과 `IMPLOG,scan,`으로 시작하는 스캔 줄이 쉼표로 구분되어 이어진다.
3. 클럭 CSV는 시각 열 하나와 논리 프로세서별 클럭 열이 이어지는 형식이다.

1. 상세 기록 측정의 원본이 테스트 폴더에 있는 것은 다른 회차와 다르다.
2. 그 회차의 콘솔 로그가 원본데이터 폴더로 옮겨지지 않았기 때문이고, 이 문서는 있는 자리를 그대로 적는다.
