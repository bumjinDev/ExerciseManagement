팀 편성 개선 알고리즘 병렬화
실행 시간은 줄었는데 CPU 시간은 오히려 늘어난 이유를 후보를 하나씩 지우며 좁혔다. 병렬 효율을 정한 것은 코어 개수가 아니라 검사마다 새로 만들어지는 객체였고, 편차 계산을 바꾸자 병렬 이전의 순차부터 빨라졌다
문제
개선 알고리즘은 서로 다른 두 팀에서 한 명씩 맞바꿔 보고 배정이 좋아지는지 확인하는 검사를 되풀이한다. 정원이 차는 순간 곧바로 실행되기 때문에, 수 초가 걸리는 이 계산이 끝날 때까지 참가자가 편성을 기다린다.
병렬화 설계
검사는 같은 배정을 놓고 후보 하나를 맞바꿔 보고 되돌리는 일이라, 검사끼리는 순서도 없고 서로 기다릴 일도 없다. 그래서 검사 목록을 여러 갈래로 나눠 동시에 실행했다. 다만 가장 좋은 교환을 골라 적용하고 나면 배정이 바뀌므로, 그 위에서 다시 도는 전수 검사의 되풀이는 순차로 남겼다.
그런데 개선 알고리즘의 실행 시간은 줄었지만, CPU 시간 합은 오히려 늘었다

2. 왜 이 배치인가

이 장의 척도는 프로세스 CPU 시간 합과 워커 CPU 시간 합이다. 호출 시간이 얼마나 줄었는가는 결과이고, 원인 추적이 실제로 따라간 값은 같은 결과를 내는 데 CPU 시간을 얼마나 썼는가다. 그래서 이음 줄이 이 두 값의 어긋남(시간은 줄고 CPU 시간 합은 1.78배)으로 문제를 열고, 추적 스텝 넷이 전부 이 척도 위에서 후보를 지우며, 성과에도 프로세스 CPU 시간 합의 전후를 둔다. 순차 대비 배율과 평균 바쁜 코어 수는 본문에서 내려 발표자 노트에 둔다. 이음 줄은 서술형 문장 대신 리드 한 줄과 값 조각 셋으로 나눠, 발표할 때 리드를 말하고 조각을 하나씩 짚는 순서로 읽히게 했다. 조각마다 측정 당시의 워커 스레드와 분할 개수가 붙어 있다.

C와 D의 카드에는 판단에 쓰인 데이터 조각을, E에는 그 판단이 나온 데이터 패턴을 둔다. 카드 안의 데이터 줄 하나로는 판정이 맞는지 검증할 수 없다. 늘어난 시간이 워커 안에 있다는 판정은 분할을 늘리는 내내 프로세스 CPU 시간 합과 워커 CPU 시간 합이 거의 같은 값으로 함께 커진다는 패턴에서 나왔고, 클럭이 원인이 아니라는 판정은 클럭이 분할 6에서 멈춘 뒤 더 내려가지 않는 패턴에서 나왔다. 그래서 E의 표 1은 분할 다섯 지점(1, 3, 6, 9, 12)의 추이를 값 종류별 행으로 늘어놓아 그 패턴이 눈으로 확인되게 했고, 첫 열에 확인한 것의 이름(CPU 동작 시간, 검사 횟수, 클럭, 검사 1회당 시간)을 붙여 C의 스텝 순서와 짝이 맞게 했다. 판정 이름을 그대로 열에 쓰면 제외 같은 말이 표에서 따로 읽혀 뜻이 닿지 않으므로, 표의 첫 열은 잰 것의 이름으로 적는다. 보고서의 표 전량을 옮길 수는 없으므로, 다섯 지점은 패턴을 인지할 수 있는 최소로 골랐다.

표 2는 확정과 해결의 근거다. 원인 확정은 편차 계산 구현만 바꾼 세 실행을 같은 조건(워커 스레드 6개, 분할 36)에서 나란히 놓아야 보인다. 객체를 만들지 않는 반복문으로 바꾸자 프로세스 CPU 시간 합이 함께 내려간 것이 원인 확인의 근거이고, 증분 재계산이 반복문보다도 수십 배 가벼워진 것(편차 계산 1회 1,373ns 대 49ns)이 개선 확인의 근거다. 두 판정이 같은 세 열 비교 안에서 읽히므로 표 하나로 묶었다. 성과의 워커 6개에 분할 36은 전후를 같은 저울에 놓기 위한 비교용 측정 조건이고, 영향 문장의 워커 12개에 분할 9는 개선 뒤 설정별 실측에서 고른 운영 배포 설정이라 서로 다른 값이 맞다. 이 구분을 두 문장의 라벨로 밝혀 충돌로 읽히지 않게 했다.

성과의 첫 항목은 개선 알고리즘 전체 실행 시간이다. 잰 것은 개선 알고리즘 하나가 시작해서 끝날 때까지 실제로 흐른 시간 전체이고, 안의 전수 검사(탐색) 구간만 잘라 잰 값이 아니다. 그 구분이 이름에서 읽히도록 전체 실행 시간이라고 적고, 조건 줄에 시작부터 끝까지 1회라는 것을 밝혔다. 4,137.2ms와 59.1ms 모두 순차 실행의 값이라 실행 방식도 조건 줄에 두었다.

다섯 구역이 트러블슈팅 서술 순서를 그대로 위에서 아래로 편 것이다. 헬스장 지인 피드백 7절이 권한 순서가 문제 정의, 왜 문제였는지, 선택한 해결책, 선택 근거, 개선 전후 수치, 서비스에 미친 영향이다. 이 장은 그 순서에 원인 추적 구역과 판정 근거 데이터를 더한 것이고, 발표할 때도 위에서 아래로 읽으면 그대로 발표가 된다. 아이트리소프트 면접 피드백 1번이 지적한 것이 발표자가 발표하기 힘든 구성이었으므로, 시선 동선과 발표 동선을 일치시켰다. C의 구역 제목과 확정 방법 줄에 표 1과 표 2를 가리키는 말을 넣어, 본문과 데이터가 오가는 길을 명시했다.

상단 A는 주제형 제목과 결론을 담은 보조 문장이다. 제목은 이 페이지가 무엇을 다루는지 말하는 팀 편성 개선 알고리즘 병렬화이고, 결론 문장은 제목이 아니라 그 아랫줄에 녹였다. 지인 피드백 9절이 요구한 페이지 상단 주제 영역의 역할을 제목이 맡고, 현직자 피드백 A-6의 2초에서 7초 훑기에는 보조 문장 안의 강조색 결론 구절(병렬 효율을 정한 것은 코어 개수가 아니라 검사마다 새로 만들어지는 객체였고)이 걸리게 했다. 이 구절이 이 장에서 강조색을 쓰는 유일한 자리다.

B에 설계 구역을 따로 두었다. 현직자 피드백 A-7이 꼽은 세 가지 중 하나가 설계에 대한 이야기가 너무 없다는 것이고, 아이트리소프트 피드백 4번도 중요한 것은 트러블슈팅이 아니라 설계와 의사결정이라고 했다. 문제 옆의 상자 하나가 그 자리이고, 검사끼리는 독립이라 나눠 돌릴 수 있고 가장 좋은 교환을 적용한 뒤의 되풀이는 앞 결과에 묶여 순차로 남긴다는 판단 하나만 쉬운 말로 적었다. 복사본 격리와 병합 규칙, 40가지 경우의 결과 동일성 검증은 발표자 노트에 있다. 이 장이 성능 이야기로만 읽히지 않게 하는 자리다.

표 1은 분할 개수 스윕 전체가 아니다. 현직자 피드백 B-5가 Chunk 몇 개가 제일 빠를까 같은 실험은 트러블슈팅이 아니라 그냥 테스트해 본 것이고 오히려 마이너스라고 했다. 표 1의 행은 호출 시간이 아니라 판정에 쓰인 값 종류이고, 첫 열이 확인한 것의 이름이라 어느 분할이 빠른가를 고르는 표로 읽히지 않는다. 열다섯 지점 스윕의 목적과 표 전량은 발표자 노트와 별첨에 그대로 둔다.

구간별 데이터 출처와 측정 환경은 발표자 노트에 있다. 이음 문장과 원인 추적의 수치는 워커 스레드 12개 계열이고 해결과 성과는 워커 스레드 6개에 분할 36이라는 계열 구분, 그리고 전후가 계측이 서로 다른 측정이라 규모로 말한다는 규칙은 슬라이드에서 내려 발표자 노트에 보관한다. 표 1과 표 2의 제목과 열 이름이 각자의 측정 조건을 이미 담고 있어, 본문에는 따로 줄을 두지 않는다. 다만 포트폴리오가 발표자 없이 PDF로만 읽히는 경우를 대비해, 별첨 첫 장에 측정 조건 상자를 둔다. 문안은 8절에 있다.

본문에 도구 이름과 클래스 이름이 없다. 아이트리소프트 피드백 2번이 듣는 사람은 그 기술이 무엇인지 모르고 궁금하지도 않다고 했다. 그래서 본문은 최종 보고서가 이미 풀어 쓴 말(말단 작업, 분할, 검사, 워커)만 쓰고, ForkJoinPool과 JMH와 JFR 같은 이름은 발표자 노트로 내려 꼬리질문 재료로 쓴다. 코드 조각도 지인 피드백 8절에 따라 넣지 않는다.

3. 구역별 문안 전문

슬라이드에 그대로 옮겨 쓸 수 있는 문안이다. 수치는 전부 최종 보고서와 성능 분석 편에서 대조했고 출처는 4절 표에 있다.

A. 상단 주제 영역

라벨 트러블슈팅 1 제목 팀 편성 개선 알고리즘 병렬화 보조 문장 실행 시간은 줄었는데 CPU 시간은 오히려 늘어난 이유를 후보를 하나씩 지우며 좁혔다. 병렬 효율을 정한 것은 코어 개수가 아니라 검사마다 새로 만들어지는 객체였고(이 구절만 강조색 굵게), 편차 계산을 바꾸자 병렬 이전의 순차부터 빨라졌다

B. 문제와 병렬화 설계

[문제] 개선 알고리즘은 서로 다른 두 팀에서 한 명씩 맞바꿔 보고 배정이 좋아지는지 확인하는 검사를 되풀이한다. 정원이 차는 순간 곧바로 실행되기 때문에, 수 초가 걸리는 이 계산이 끝날 때까지 참가자가 편성을 기다린다. [병렬화 설계 · 상자 하나] 검사는 같은 배정을 놓고 후보 하나를 맞바꿔 보고 되돌리는 일이라, 검사끼리는 순서도 없고 서로 기다릴 일도 없다. 그래서 검사 목록을 여러 갈래로 나눠 동시에 실행했다. 다만 가장 좋은 교환을 골라 적용하고 나면 배정이 바뀌므로, 그 위에서 다시 도는 전수 검사의 되풀이는 순차로 남겼다. [이음 줄 · 리드 문장 하나와 값 조각 셋. 조각은 제목 줄과 값 줄 두 줄] 리드 그런데 개선 알고리즘의 실행 시간은 줄었지만, CPU 시간 합은 오히려 늘었다 값 조각 1 개선 알고리즘 전체 실행 시간 (워커 스레드 12개 · 분할 16개) / 3,378.91ms → 764.76ms로 줄었다 값 조각 2 모든 스레드가 쓴 CPU 시간의 합 (같은 실행) / 3,375.00ms → 6,006.25ms, 순차의 1.78배로 늘었다 값 조각 3 말단 분할을 12개로 늘리면 / CPU 시간 합이 분할 1의 3.23배(14,318.8ms)까지 늘었다

C. 원인 추적 · 스텝 넷 (질문 / 답 / 근거 데이터 / 판정)

구역 제목 원인 추적 · 늘어난 CPU 시간의 후보를 실측으로 하나씩 지웠다 1. 워커 밖에서 쓴 시간이 늘었는가 GC, 다른 스레드, 말단마다 팀 배정 복사본을 만드는 시간을 하나씩 쟀지만, 늘어난 CPU 시간의 99.8%는 워커가 쓴 시간이었다 데이터: 프로세스 +9,884ms 중 워커 +9,866ms [제외] 2. 검사 횟수가 늘었는가 말단을 어떻게 나눠도 개선 작업 한 번의 검사 횟수와 통과 횟수가 완전히 같다 데이터: 검사 855,000회 · 통과 352,485회 [제외] 3. CPU 클럭이 내려갔는가 클럭이 내려가긴 하지만, 늘어난 검사 시간에서 클럭 하락으로 설명되는 몫은 최대 4.6%다 데이터: 클럭 4.257 → 4.081GHz (4.1% 하락) [제외] 4. 검사 한 번의 CPU 시간이 커졌다 검사 시간의 99% 안팎을 쓰는 합 편차·분포 편차 계산이 검사할 때마다 객체를 새로 만들고, 그 양이 개선 작업 한 번에 9.5GB다 데이터: 검사 1회당 워커 스레드 시간 총합 5,113 → 16,652ns [원인 확정] 확정 방법 편차 계산을 객체가 생기지 않는 반복문으로 바꾸자, 분할 1 대비 프로세스 CPU 시간 합의 배수가 3.23에서 1.04로 내려왔다

D. 해결과 성과

[해결 · 편차 계산을 증분 재계산으로] 한 번의 교환으로 값이 바뀌는 팀은 스무 개 중 두 개뿐이다. 전수 검사 한 바퀴를 시작할 때 팀별 합과 제곱합을 계산해 두고, 검사마다 맞바꾼 두 팀의 값만 고쳐 편차를 구한 뒤 되돌린다. 데이터: 합 편차 계산 1회 소요 시간 1,373 → 49ns · 분포 편차 계산 1회 소요 시간 3,175 → 82ns [성과 · 개선 작업 한 번당, 전은 스트림 구현이고 후는 증분 재계산] 개선 알고리즘 전체 실행 시간 4,137.2ms → 59.1ms (시작부터 끝까지 1회 · 순차 실행) 병렬의 프로세스 CPU 시간 합 11,728.1ms → 71.9ms (전후 비교용 동일 조건 · 워커 스레드 6개 · 분할 36) 새로 만드는 객체 9,522.1MB → 4.44MB [영향] 인원 200명 기준, 참가자가 기다리던 편성 시간이 4초 규모에서 60ms 규모가 되었다. 운영 배포 설정은 이와 별도로, 개선 뒤 설정별 실측에서 가장 빨랐던 워커 스레드 12개에 분할 9를 쓴다.

5. 본문에서 내린 것과 내려간 자리

본문에 넣지 않기로 한 것들이다. 버리는 것이 아니라 자리를 옮기는 것이고, 커뮤니티 피드백 통합본 5-6절이 경고한 대로 이걸 빼면 얕아 보이지 않나 하는 판단으로 도로 넣지 않는다.

8. 별첨 첫 장의 측정 조건 상자 문안

발표자 없이 PDF로만 읽히는 경우를 대비한 상자다. 별첨 첫 장 맨 위에 두고, 뒤로 측정 회차별 표 전량을 붙인다. 인위적 상황 의심(현직자 피드백 B-1과 B-2)과 테스트 전제 지적(Wherehouse 통합 분석서 4.2절)에 대한 방어가 이 상자의 역할이다.

[측정 조건] 고정 입력 인원 200명, 정원 10명, 시드 42, 허용폭 10%, 시작 배정 greedy 측정 방식 인위적인 제약 없이 운영 경로 그대로 측정. 설정마다 워밍업 2회를 버리고 측정 5회를 평균, 배율을 잰 벤치마크 값은 표본 10개 평균 측정 환경 개인 PC(i5-11400H, 물리 코어 6개, 논리 프로세서 12개), JDK 17, Windows, 로컬 실행 읽는 규칙 계측 코드가 서로 다른 측정의 값은 정밀한 배수 대신 규모로 읽는다 [한계] 서버 환경이 아니고 여러 사용자의 요청이 겹치는 조건도 아니다. 인원이 적으면 병렬이 오히려 느려서, 인원 20명에서는 순차 0.090ms에 병렬 0.315ms다.
